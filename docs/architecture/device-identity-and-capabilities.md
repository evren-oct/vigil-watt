# 设备身份与能力声明规范

> 状态：规范生效；身份与能力模型已有实现，主动查询的全路径能力门控仍在 M2。
> 本文定义“设备是谁、这条接口是否匹配、能声明什么能力”的长期边界；插件契约、目录字段与 JSON 写法继续引用现有文档。
> 基线：2026-11-23，`dev` 分支 `d117b59`。

## 1. 两个概念不能混

**设备身份**回答“这是哪台物理/逻辑设备”；**协议匹配**回答“这条 HID 接口是不是本插件、本协议的通道”。

- 同一只鼠标可以同时暴露鼠标集合、底座集合、配置集合；只有插件实际认领的那条接口能借用该型号的能力声明。
- 接收器 PID 命中只说明“这颗接收器属于某族”，不等于接收器下当前挂着哪台设备。
- 协议自报 VID/PID 是本体身份线索，不自动替代 USB 枚举身份，也不参与认领，除非插件明确设计并验证。

身份与匹配必须分开存储、分开使用。`DeviceStatus.Usb`、`Reported`、`Receiver` 是三个身份快照，不能合成一个“型号”字段。

手动目标探测中的 `TargetSelection` 也不等于设备身份：用户选择某个接口、接收器或槽位，只表示本次操作目标；`ProbeResult` 只能提供证据，不能直接写成已确认的 `DeviceIdentity`。见 [手动目标探测设计](../reviews/2026-11-24-manual-target-probing-design.md)。

## 2. 识别依据

可用依据按证据强度排列：

| 依据 | 用途 | 边界 |
|---|---|---|
| VID/PID | 目录命中、插件候选过滤 | 共用 PID 不能反推型号 |
| Usage Page / Usage | 接口分类 | 同页可能多形态，必须结合长度 |
| 输入/输出/Feature 长度 | 接口指纹 | 声明长度不等于本次实际读到长度 |
| `reportId` | 输出通道识别 | 指接口输出 report ID，不是帧首字节 |
| `pathContains` | 区分同一设备的多条集合 | 路径随 USB 口/枚举变化，不能当稳定身份 |
| ContainerId | 聚合“一台物理设备”的多接口 | 读不到时才退回 VID/PID |
| 序列号 | 有线/无线归一、稳定 ID | 不是所有设备都有 |
| 接收器槽位 | 多设备接收器身份 | 槽位在位不等于设备在线 |
| 协议自报身份 | 显示名、型号辅助 | 只用于已实现自报的插件，不参与认领 |

识别顺序默认是“目录优先，接口指纹校验，未收录才按插件白名单兜底”。不要把显示名、产品串或 PID 邻近当成身份证据。

## 3. 多接口、接收器与连接模式

### 3.1 多接口设备

- 同一物理设备的多个 HID 集合必须按 ContainerId 或明确的接口指纹分组。
- 插件只认领自己的那条接口；能力查询必须与认领同源，接口不符返回 `Unverified`。
- 同一设备插线后多出接口时，用 `SkipPathsForThisPass` 等机制摘掉接收器/无线接口，优先保留可读本体。

### 3.2 接收器与设备本体

- 接收器身份描述“传输通道属于哪一族”，不是设备本体身份。
- 接收器在位、槽位 Ping 成功、配置通道可读，都只能作为推断证据；链路来源记 `Inferred`，等设备自报再升级。
- 一个接收器多台逻辑设备时，身份键必须包含接收器稳定路径与槽位；换 USB 口不应产生新设备。

### 3.3 有线、无线与不同连接模式

- 有线/无线两个 PID 通过 `pairedPid` + `wired` 配对；每组恰有一条 `wired: true`，不按 PID 大小猜。
- 同型号多通道归一只能靠目录显式 `group`；不按系列、名字或 PID 邻近推导。
- 连接方式变化不应改变设备身份；身份规则变化会改变历史库键，必须单独评估迁移。

## 4. 已登记、未登记与未知身份

| 状态 | 处理 |
|---|---|
| **已登记且接口匹配** | 可以认领；按目录协议解析；能力按设备条目声明 |
| **已登记但接口不匹配** | 不认领；能力 `Unverified`；不得借用同 VID/PID 其它接口的声明 |
| **`implementation=none`** | 目录收录但不适配；`Resolve` 返回 null，不认领 |
| **未登记但插件白名单 + 接口指纹命中** | 允许按协议兜底认领；能力默认 `Unverified`，不得主动查询 |
| **未知身份** | 只允许被动读取或诊断采集；不得主动查询 |

未验证型号不要先塞进 `devices[]` 占位。目录优先，一有记录就会按它认领并顶掉 fallback 显示名；未验证信息放 `officialDevices` 或品牌文档。

## 5. 身份归一规则

默认 `DeviceStatus.Id` 来自插件名 + 稳定路径哈希；需要更强身份时只覆写 `BuildDeviceId`，不要在调用点另算一套。

| 场景 | 规则 |
|---|---|
| 同一鼠标有线/无线两个 PID | 目录型号 + SN；没有 SN 回落路径哈希 |
| 同型号多通道 | 只认目录显式 `group`，且必须通过接口匹配 |
| 接收器多设备 | 接收器稳定路径哈希 + 槽位；直连用独立标识 |
| 协议自报身份 | USB 身份与自报身份分开存；探测成功才写缓存 |

硬规则：

- 一个物理设备只保留一条记录；
- 插线双连接优先保留可读本体；
- 不按型号系列、PID 邻近、显示名相似度合并；
- 黑名单、历史、上报、认领必须共用同一个 ID；
- 改身份规则必须评估历史库、黑名单、自定义名与产品图匹配的影响。

## 6. 能力声明

唯一合法位置：`devices[].capabilities`。协议层没有这个字段；写到协议层或 `override` 任意层级，加载器会报错。

| 状态 | 含义 | 证据要求 |
|---|---|---|
| `supported` | 已实现，且当前适配与连接方式下有足够证据 | 真机读数，或被单测钉住的真实录制帧 |
| `unsupported` | 已确认当前 VigilWatt 适配不提供 | 有明确接口/协议证据 |
| `unverified` | 尚未验证或证据不足 | 默认态；省略即此值 |

规则：

- 不继承：`extends`、`override`、共享协议引用都不会把能力带过去。
- 判据与认领同源：VID/PID 命中后还要过接口指纹；未收录、接口不符、`implementation=none` 一律 `unverified`。
- 能力只描述“这个型号、当前适配、当前连接方式下”的事实，不是厂商理论规格。
- 能力不携带数值；DPI 上限、电池容量等规格数据不属于能力。
- 只读能力才允许声明。`DeviceCapability` 里仍有历史成员 `DpiWrite` / `RateWrite`，但当前没有写入实现，目录不得声明为 `supported`；是否删枚举另开任务。

## 7. 能力如何约束运行时

- 认领落地时，插件把 `CapabilitiesOf(info)` 写进 `DeviceStatus.Capabilities`。
- `ProtocolEngine.CapabilityOf` / `CapabilitiesOf` 是纯配置查询：不开句柄、不发帧、不动解析状态。
- UI 用能力区分“能读但还没读到（未获取）”和“不支持（字段不出现）”。
- 主动查询用能力做设备级授权：`supported` 才允许对应写入；`unverified` / `unsupported` 一律不授权。
- 能力只决定“能不能说未获取”，不决定“有值时是否显示”；`unverified` 但有可靠值时仍可显示，来源按遥测规则标注。
- 连接方式、充电状态、DPI、回报率各自独立，不从电量能力外推。

## 8. 禁止跨型号继承

以下做法禁止：

- 因为共用同一套协议，就把 VT3 的 DPI 能力继承给同族所有鼠标；
- 因为 VID/PID 相同，就把接收器的能力借给设备本体；
- 因为产品串相似，就把一个型号的充电能力套到另一个型号；
- 因为某个字段能解析，就把它声明为 `supported`，却没有真机或录制帧证据；
- 把 `DpiRead` 的 `supported` 当成 `DpiLevelRead` 或 `RateRead` 的授权。

同一协议族可以共用解析字段，但能力必须逐设备声明；协议级解析不等于能力已验。

## 9. 当前缺口与后续

- 北通之外，主动查询尚未统一使用设备级能力门控（M2）。
- `MchoseDeviceCatalog` 的传输通道能力与 `ProtocolSpecLoader` 的设备能力是两套读取路径，需要继续明确边界。
- 能力证据与 [`support-matrix.md`](../hardware/support-matrix.md)、品牌文档的指针关系需要统一；`supported` 必须能追溯到证据。
- `DpiWrite` / `RateWrite` 与只读原则的冲突已记录，处理方式另开任务。
