# 注释规范

> **一句话**：代码注释只回答"**为什么这么写**"，且只在这个 why **不写就会踩坑**时才写。
> 任何"是什么 / 曾经怎样 / 怎么验证的 / 帧长什么样"的内容，一律进 `docs/`。
>
> 立此文档的原因：2026-10-09 做了一次注释精简，发现全仓注释占 17.5%（2106/12009 行），
> 其中大量内容是**文档级的协议细节与历史战报**被写进了代码——`BetopCodec.cs` 注释占比一度到 49.6%，
> 且与 `docs/hardware/protocols.md` 近乎逐字重复。重复一旦分叉，代码里的那份就会变成误导。

## 1. 写之前先问三个问题

1. **这段内容换个文件还成立吗？**（协议布局、历史事故、实测数据）→ 成立就进 `docs/`，代码里留指针。
2. **不写这行注释，下一个人会不会改错？**→ 不会就别写。
3. **这句话能否用标识符表达？**（`BatteryOffset`、`MaxFailures`）→ 能就别用注释。

## 2. 该写（且只写这些）

| 类别 | 例子 | 长度 |
|---|---|---|
| **安全红线** | "关掉开关后探测路径仍会写帧，待修" / "别用 `quiet` 掩盖真正的写入故障" | 1–2 行 |
| **魔法值的含义** | "0x50 = 手柄未连接占位值，不是电量" | 1 行 |
| **非显然的 why** | "必须小于轮询周期，否则冷却相位会让重试间隔翻倍" | 1–2 行 |
| **对外契约** | 日志格式约定、settings.json 取值、ID 稳定性要求 | ≤4 行 |
| **指针** | `详见 docs/hardware/brands/betop.md §1.4.1` | 同一行内 |

## 3. 不该写（发现即删/搬）

| 反模式 | 处置 |
|---|---|
| 复述成员名：`/// <summary>帧总长度。</summary>` 挂在 `FrameLength = 20` 上 | 删 |
| 历史战报 / 复盘：`2026-10-06 用户复报…`、日志时间线、对照表 | 搬进 `docs/`（见 §4），代码留结论 1 行 |
| 协议字节布局、命令表、编码公式 | 搬进 `docs/hardware/protocols.md` |
| 调试手法、API 差异、踩坑记录 | 搬进 `docs/dev/runtime-pitfalls.md` / `docs/hardware/debugging.md` |
| 运行时数据流、调用顺序、参数取舍理由 | 搬进 `docs/project/code-flow.md` |
| 模块职责与设计决策 | 搬进 `docs/project/architecture.md` |
| 装饰性分隔线、`// ---- xxx ----` 之外的纯噪声 | 删 |
| 已过期的计划/待办（"阶段 2 再做"） | 删（计划不进代码） |

## 4. 内容该放哪：一张对照表

| 你想写的内容 | 去哪 |
|---|---|
| 帧结构、字节偏移、命令号、编码公式、真机样本帧 | `docs/hardware/protocols.md` |
| 硬件安全规则、写入闸门、事故复盘 | `docs/hardware/safety.md` |
| 抓包/直测/日志考古手法 | `docs/hardware/debugging.md` |
| 运行时数据流（谁调谁、什么顺序、什么线程） | `docs/project/code-flow.md` |
| 模块划分、依赖方向、设计决策与取舍 | `docs/project/architecture.md` |
| 某次事故的根因与修法、API 行为差异 | `docs/dev/runtime-pitfalls.md` |
| 构建/发布/环境坑 | `docs/dev/build.md` |
| 日志格式契约与分级管控 | `docs/dev/logging.md` |
| 经验教训、"下次接类似项目怎么做" | `docs/project/experience.md` |
| 当前状态、未完成待办（全文 ≤ 120 行，见 `AGENTS.md` §3） | `docs/project/handoff.md` |
| 某日改了什么、为什么（每条一两句，见 `AGENTS.md` §3） | `docs/project/changelog.md` |
| 还没修的审查项（`open` / `doing`，全文 ≤ 120 行） | `docs/reviews/BACKLOG.md` |
| 已关闭的审查项（`done` / `wontfix`） | `docs/reviews/archive/BACKLOG-CLOSED.md` |
| 代码该守的红线、审查流程 | `docs/dev/review-standard.md` |

**判断不了就先 grep `docs/`**：很多结论早就在里面了，只是代码里又抄了一遍。

## 5. 硬性要求

1. **写完注释，回头把对应内容补进 `docs/`**——代码里留指针，不要留孤本。
2. **指针必须指向真实存在的小节**。引用小节号前先确认；若小节可能变动，就写"`docs/xxx.md` 的格式契约一节"这类不绑号的说法。
3. **注释与行为不符时，优先改注释使其如实**（或改代码），**绝不允许留一句漂亮的谎**。
   历史上 `BetopPlugin` / `AppSettings` 的"关掉即完全静默（不认领、不写入）"就是这么误导了一轮维护者。
4. **注释不是变更日志**。改了行为就把注释改成"现在是什么"，不要写成"以前是 A、现在是 B"。
   需要保留演进脉络的，写进 `docs/project/changelog.md`（**不是** handoff——那里只放当前状态）。
5. **测试类的类头摘要**保留一句"覆盖什么 + 哪个用例是哪个 bug 的回归"，其余删。

## 6. 参考：本次精简的判定模板

类头就是下面的文件头。why 只在不写就会踩坑时加一行；指针能代替长说明。

```csharp
/// <summary>
/// 功 能： 这个类型做什么（一句话）
/// 2026/10/14 10:08:00 xliu
/// </summary>
```

类头 ≤ 5 行，方法/属性 ≤ 2 行，字段 ≤ 1 行。超出这个量，说明内容该进 `docs/`。

## 7. 文件头

`src/` 下新建 `.cs` 时，主要类型（与文件名相同的那个；否则文件里第一个最外层类型）正上方写：

```csharp
/// <summary>
/// 功 能： 这个类型做什么（一句话）
/// 2026/10/14 10:08:00 xliu
/// </summary>
```

- 两行内容都从 `///` 后一个空格开始，日期行不多缩进。
- 「功 能：」是这一类型的一句话职责。
- 第二行是创建当时的本机时间，格式 `yyyy/MM/dd HH:mm:ss`（月、日补零），加上当时的 Windows 用户名。用户名创建时读取，不写死。
- 放在 `using` 和 `namespace` 之后、类型声明之前。中间可以有特性，不要插 `//` 注释，否则 CS1587。
- 还需要 why 时，在时间行下加一行，使类头不超过 5 行。
