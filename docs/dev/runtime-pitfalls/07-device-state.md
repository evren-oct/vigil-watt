# 运行时坑 · 设备状态与内存

> 正文分册。索引与其余分册见 [runtime-pitfalls.md](../runtime-pitfalls.md)；**§N 是稳定编号**，代码与文档一律按 `runtime-pitfalls.md §N` 引用。

## 12. 休眠伪读数：电量突然变 1 或 0 → 误报低电量（2026-10-06 加固）

**症状**：键盘（或鼠标）休眠、或快休眠前，监控里电量突然变成 `1`（偶尔 `0`），弹出低电量告警，一会儿又恢复。

**根因**：设备进入休眠/关机的瞬间，dongle 会推一帧**占位读数**——真机 66% 时推 `pct=1`。旧代码只在解析层挡了 `pct == 0`，`1` 直接漏进 UI 和低电量判定。更深层的问题是：**整条链路对"电量突变"没有任何合理性校验**，任何解析出的数字都会被无条件采信。

**加固三层（都在代码里，改协议解析时别绕过）**：

0. **真凶已抓到（2026-10-06 12:02 实测）**：休眠帧不是"电量位=1"，而是一个**类型位不同的推送帧**——
   正常电量推送 `13 0A 01 00 04 **05** 42 01 …`（0x05=电量，[6]=66%），休眠时推
   `13 0A 01 00 04 **02** 01 …`（0x02=设备状态通知，[6]=0x01 是 payload 不是电量）。
   旧代码不看下标 5 的类型位、直接读下标 6，于是把 payload 的 0x01 显示成 1%。
   **正确做法：先认类型位**（`MchoseV1Codec.ParsePush`），并把这个 0x02 帧当"设备已休眠"信号
   立即标离线（基类 `RequestOffline`）。原始帧两边的校验和都对得上，可自洽验证。
1. **解析层**（`MchosePlugin` + `MchoseV1Codec`）：按类型位识别（见上）；另有 `InvalidPercentFloor = 1`
   兜底（≤1 一律无效）。判无效后返回 null → 计入熔断失败 → 3 次后设备标离线，符合"键盘确实睡了"。
2. **基类层**（`BatteryPluginBase.Poll` → `BatteryReadingFilter`）：每设备一个过滤器实例，两条规则——① 数值低于 2（即 0/1）或 >100 直接判无效，永不采信；② 与上次采信值相比涨跌超过 20 点则本轮不采用，需**持续 5 分钟**才采信（回弹即清零计时）。这是通用的，挡所有插件的任意异常值，涨跌双向都管。基准**不随离线清空**。
3. **告警层**（`DeviceManager.CheckLowBattery`）：低电量值比上次已知值低超过 20 点时暂缓提醒一轮。最后一道闸。

**注意**：`0` 和 `1` 都不会是真实电量——低电量阈值是 20%，正常放电到 1% 之前早就提醒过了，所以拒绝它们不会漏掉任何真实告警。

**单测**：`src/tests/VigilWatt.Core.Tests/`（xUnit，18 个用例），帧解析用例全用真机原始帧，含休眠帧回归用例。改解析或过滤器后跑 `dotnet test src/tests/VigilWatt.Core.Tests`，全绿即通过。

## 23. 设备睡醒后电量不刷新：退避档位只升不降 + 没有被动监听的插件享受不到 CR-53（2026-10-27 实修）

**症状**：ATK F1 Ultimate 2.0 鼠标静置几分钟（固件自动休眠）后动一下，电量卡在旧值不动；
去设备页点「刷新」也不一定变，过好几分钟才自己跳一次。键盘（走 VIA、一直插着）全程正常。

**日志证据**（`app-2026-10-27.log`，同一天内反复出现）：

```
18:22:33 收到设备休眠/关机通知，立即标记离线
18:23:31 停写退避期满（30 秒），恢复查询
18:25:33 连续 3 次查询失败，熔断停写（第 2 次，退避 60 秒）
18:33:33 收到设备休眠/关机通知，立即标记离线
18:42:33 熔断停写（第 2 次，退避 60 秒）
18:46:33 熔断停写（第 3 次，退避 120 秒）
18:51:33 熔断停写（第 4 次，退避 240 秒）
18:56:02 停写退避期满（240 秒），恢复查询      ← 4 分 29 秒没有一次读数
18:56:02 设备重新上线: ATK F1 Ultimate 2.0
```

注意 18:56:01 那三条「打开主窗口被调用」：用户以为是自己点刷新救回来的，
其实退避**正好**在 1 秒后到期——纯属巧合。

**根因（三条叠加，缺一条都不会这样）**：

1. **退避档位只升不降**。`WriteBackoff.For(trips)` 是 30s→1m→2m→4m→5m，而 `BreakerTrips` 只在
   `ReportPollAnswered`（读到应答）时清零。鼠标每睡一次就失败 3 轮 → 顶高一档。用户一天睡几十次，
   档位轻松爬到第 4 档（240 秒）。等他真去用鼠标时，正好撞在最长的那段退避里。
2. **熔断期内一帧都不发**。`CanWrite` 未到期直接 `return false`，`PollDevice` 早退 → 设备醒了
   也没人问它，只能干等退避到期。
3. **CR-53 的 bypass 通道对纯查询型插件无效**。`MaybeHalfOpenBreaker` / `RunPendingConfirm` 都跑在
   **被动监听线程的空闲 tick**（约 500ms 一次）上；ATK 没有 `SupportsPassiveListen`（FF02 口只在
   收到查询帧后才回包，没有自发流），根本没有那条线程。所以"退避期满立刻核实"对它是空转。

**修法**：给"纯查询型插件"补一条独立的**半开探活**通道，与正式轮询的退避解耦。

| 改动 | 位置 |
|---|---|
| `BreakerProbeInterval`（默认 `Zero` = 关闭，行为与旧版完全一致） | `BatteryPluginBase` |
| `TrackedDevice.HalfOpenProbe`；`CanWrite` 放行；`ReportPollFailure` 见到它**直接 return**（失败不记账、不升档） | 同上 |
| `NudgeHalfOpen()`：对每个熔断中的设备按间隔发一帧核实，成功即由插件自己的 `ReportPollAnswered` 解除熔断 | 同上 |
| `Poll()` 里加 halfOpen 分支：熔断期内按间隔把这一轮当探活发（60 秒保底） | 同上 |
| 15 秒发现节拍调 `NudgeHalfOpen()` | `DeviceManager.DiscoverOnlyAsync` |
| `SupportsDiscoveryProbe = true` + `BreakerProbeInterval = 30s` | `AtkPlugin` |

**与 CR-53 那条通道的分工**（两条别混）：`RunPendingConfirm` / `MaybeHalfOpenBreaker` 跑在**被动监听线程**的空闲 tick 上，只有 `SupportsPassiveListen` 的插件才有那条线程；`NudgeHalfOpen` 由 **15 秒发现节拍**驱动，给没有被动流的纯查询型插件。两条共用 `LastBypassAt` 做节流——这是**故意的**：保证同一设备 30 秒内最多一帧，拆成两个时间戳会让两条通道各来一帧。

**闸门是 `HasHalfOpenProbe`（= 覆写了 `BreakerProbeInterval`），不是发现节拍那两个 flag**：`SupportsDiscoveryProbe` 表达的是"要不要 15 秒重探"，有被动监听的插件也可能为 true，但它的唤醒感知已由 CR-53 负责。把两者绑在一起会让"只覆写间隔、没开 flag"的插件静默空转（CR-108）。

**为什么默认是关闭**：这条通道只对"设备会频繁短睡、且没有被动监听"的插件有意义。
有被动监听的插件（雷柏/迈从/北通…）本来就能靠 CR-53 的 bypass 秒级感知，多一条只会抬高写入频率。
所以 `BreakerProbeInterval` 保持 `Zero` 默认，谁需要谁覆写一行——和 `OfflinePolicy` 一样的"每插件一行配置"。

### 23.1 哪些品牌该开、间隔定多少（适配者按实际设备判断，没有标准答案）

**各厂商对"睡着的设备被定期戳一帧"的容忍度不一样**，所以这里只给判断口径，不给批量结论。按四条过：

1. **有被动监听流吗**（`SupportsPassiveListen`）？有就**不开**。CR-53 的 bypass 已经在那条 ~500ms 空闲 tick 上做同一件事，再加一条只抬高写入频率。雷柏 / 迈从 / 北通 / HECATE 有线 / HyperX / 英菲克 / 德鲁 / 寸渊 / AulaG9 / DualSense 都属这一类。
2. **设备会频繁短睡吗**？常插着的键盘不会；2.4G 鼠标 / 耳机、BLE 省电外设会。不短睡的插件开了只是白花帧。
3. **戳了会不会出事**——这条只能实测，别靠推理：
   - 官方软件自己轮询吗？官方不轮询而我们轮询，风险更高；
   - 有会话占用史的协议（北通 dongle）、对"同一时刻第二帧不应答"的 dongle（雷蛇）先按"不开"处理；
   - 开了之后观察设备醒后有无异常：断连、重新枚举、驱动报错、官方软件掉线。
4. **间隔定多少**：**建议 30 秒起步**——正好是"每轮 60 秒主轮询之间最多一帧"。要更密先算清每小时帧数（30 秒 ≈ 120 帧/小时，且只落在熔断期），并按 `safety.md` §3 规则 3 ③ 跟用户确认写入预算。下限别低于 `ProbeCooldown`，否则探测本身被 cooldown 挡住、白跑。

**现状**：只有 ATK 开了（`SupportsDiscoveryProbe` + `ProbeCooldown` 10s + `BreakerProbeInterval` 30s）。其余**主动查询型、无被动监听**的插件（高斯 / 华硕 / 雷蛇 / 樱桃 / VGN / 凌豹 / 派世 / HECATE 无线 / 罗技 / 前行者）遇到同样的"睡醒卡住"仍只能干等退避到期，只是还没人报——要开就按上面四条逐个过，**别批量照抄 ATK 的 30 秒**。

**验证**（`BreakerProbeTests`，5 个用例）：探活失败档位不动 / 探活成功清零档位并回在线 /
按间隔节流 / 默认关闭时行为与旧版逐帧一致 / `NudgeHalfOpen` 不必等主轮询就能叫醒设备。

**教训**：**"别太频繁打扰设备"和"及时发现设备回来了"是两件事**，不能共用一条退避曲线。
退避该约束的是正式轮询；发现通道必须是独立的、失败不记账的。同理适用于任何"设备会主动睡"的协议
（2.4G 鼠标/耳机、BLE 省电外设）。

## 24. 「组合识别」的判据写了却没生效：数据源没接上（2026-10-26 实修，CR-112）

**症状**：同一只设备在列表里出现多行，名字还不一样（放电的一行、充电的一行）。

**根因**：1.3.0 引入了两套"同一台设备归一"的判据，**两套都没生效**：

| 判据 | 靠什么 | 实际状况 |
|---|---|---|
| `VgnDevicePairing`（插件层） | 序列号 SN | 逻辑在，但 `HidDeviceScanner` **从不调 `HidD_GetSerialNumberString`** → SN 恒空 → 配对恒不成立 |
| `DeviceGroupKey`（采集页） | 系统 ContainerId | 逻辑在，但**本机 HID 设备一条 ContainerId 都读不到** → 这条路在本机彻底不通 |

真机实测：F2 的 7 条接口 SN 全是 `541505796617`，**判据本来是好的，只是数据源没接上**；F108 的 9 条接口 SN 全空（设备不报）。

**规则（下次加新判据先照这个走）**：

1. **判据的数据源必须真的被读**。写完 `SameSerial` 之类，先确认 `HidDeviceInfo.SerialNumber` 有人赋值——"属性定义了"不等于"有值"。加一条源码级断言把这条链路钉住（`SerialNumberWiringTests`）。
2. **先用探针量一遍，再决定用哪个判据**。ContainerId 读不到、SN 全空，都是实测才知道的，别照文档猜。
3. **判据分两处用（黑名单键 vs 上报 Id）时必须同源**。`IdFor(路径)` 决定黑名单判定，`BuildDeviceId(信息)` 决定上报 Id；一个看路径一个看产品名，就会出现"永久移除这台设备"按 A 键写、按 B 键判，**删不掉**。
4. **设备不报 SN 时退到型号粒度，并把取舍写进文档**（同 `betop.md` §1.8.2 鲲鹏20）：同型号第二台会被并成一台。
5. **显示名带状态后缀会放大"多台设备"的错觉**：列表页名字会加 `" ⚡充电中"`，同一只鼠标在无线与有线两条接口下就显示成两个不同的名字——用户报的"多个名称"往往就是这个。


## 26. 隐藏到托盘后「内存」不回落：WinUI 3 只摘内容树，私有页仍驻留（2026-11-25 实修）

**症状**：主窗口关到托盘半小时，任务管理器「内存」仍显示 150MB 上下；要等系统内存紧张（本机可用
从 3.5GB 掉到 1.2GB）才自己掉到 30MB 左右。同一进程 09:26 与 10:18 两次采样：

| 口径 | 09:26（可用 3.5GB） | 10:18（可用 1.24GB） |
|---|---|---|
| 专用工作集（任务管理器「内存」列） | 148.1 MB | **28.9 MB** |
| 总工作集 | 311.6 MB | 117.3 MB |
| 提交（私有字节） | 183.8 MB | **187.8 MB** |

**根因**：`AppWindow.Hide()` 只让窗口不可见、把内容树 `Unloaded`，**不释放私有页**；Windows 只在
内存压力下才裁工作集。用户 2026-11-25 明确：非专业用户看的就是这一列，而且主窗口通常只开一次配置，
不该让 150MB 一直驻留。

**修法**：`MainWindow.HideToTray()` 在 `AppWindow.Hide()` 之后排一次 `WorkingSetTrim.Queue()`
（`Services/WorkingSetTrim.cs`），1.2 秒后调 `SetProcessWorkingSetSizeEx(GetCurrentProcess(), -1, -1, 0)`；
`TrayService.ShowMainWindow()` 先 `Cancel()`，避免刚裁完又整页缺页回来。

**规则**：

1. **这是"换出"不是"少占"。** 上表第三行是证据：工作集掉 119MB，提交一个字节没少（还多了 4MB）。
   报数时**必须同时给提交**，否则下一个人会把"数字变小"当成修好了。
2. **延迟 1.2 秒再裁。** `Hide()` 返回后还有一段异步尾部在释放内容树（同 §19 的 `Unloaded` 时机），
   裁早了那些页还没还回来。
3. **显示路径上必须先取消。** 裁完立刻显示等于让整棵内容树重新缺页，首帧明显变慢。
4. **净效果有限，别期待掉到个位数。** 任务栏贴片 1Hz 重绘会把它自己那部分页重新拉回；
   裁掉的只是 XAML 那半。
5. 想真正降占用只能降**提交**。但可选项比想象中少：**拆页面常驻是纯亏**（见 §27），
   真正有效的只有"删预热"这一条，且它只是把成本推迟到第一次切页。

## 27. 拆掉页面缓存反而更涨：重建出来的合成器资源不回收（2026-11-25 实测，**结论是别拆**）

**缘起**：用户问"7 个页面全常驻能不能优化"。逐页实测每页约 4–5MB 提交（设备页基线 127.7MB，
点完统计/历史/诊断/设置/关于/详情后 153.3MB），于是把 `设置`/`诊断`/`详情`/`关于` 的
`NavigationCacheMode.Required` 去掉、同时删掉 `PrewarmSettingsPage()`，重测。

**结果：不省，反而更贵。**

| | 启动基线 | 第一次切页后 | 第一轮点完 | 重复访问一轮 |
|---|---|---|---|---|
| 页面常驻 + 预热 | 127.7 | — | **153.3** | +0 |
| 页面不常驻 + 无预热 | **100.9** | 131.6（**+29.9**） | **153.6** | **+28** |

三件事：

1. **启动省下的 26.8MB 大部分只是推迟。** 第一次切页那一拍 `PRIVATE +29.6MB`、`MAPPED +100MB`、
   `IMAGE 区域 +120`——图形/文字那一套一次性加载。预热版在启动时就付掉了，所以它的 127.7 已含这笔钱。
   第一轮点完 153.6 vs 153.3，**两个版本完全一样**。
2. **重复访问开始累积。** 不缓存时每次进页面重建一整套 XAML 树 + 合成器资源，实测第二轮 +28MB 且不回收；
   缓存版第二轮是 0。
3. **手感差别很小**（用户实机判断"可以接受"），所以这不是拿手感换内存的取舍——是纯亏。

**规则**：

1. **页面常驻保留。** 它把重复访问的成本封顶，且不付出任何手感代价。别为了降基线去拆它。
2. **要降启动基线只能删预热**，而且要知道那是"把成本挪到第一次切页"：不点设置页就一直不付，
   点了就一次付清。真实收益只对"只开主界面看一眼就走"的用户成立。
3. 删预热后 `PrewarmSettingsPage` 的注释与设计意图一起失效，别只删调用留个空方法。
4. **页面在构造函数里订阅静态事件时，必须挪到 `Loaded`/`Unloaded` 并加 `_hooked` 守卫**（同 §19）。
   `AboutPage` 原先是构造期订阅、靠"页面永远不销毁"侥幸正确；这次顺手改成 §19 的形态，缓存与否都成立。
