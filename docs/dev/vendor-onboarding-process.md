# 新厂商接入流程

> 适用范围：新增品牌、给已有品牌接入新型号、把贡献者协议收进仓库。
> 本文规定**顺序与完成条件**；架构判断标准见 [厂商插件架构标准](../architecture/vendor-plugin-standard.md)。
> 基线：2026-11-18，`dev` 分支。流程里的“完成”指证据齐、行为可复现，不是“代码能编译”。

## 0. 总览

| 步骤 | 产出 | 通过后才能进入 |
|---|---|---|
| 1. 协议调研 | 协议证据包 + 硬件文档草稿 | 能说清帧、查询、充电、链路、离线信号 |
| 2. 现有能力复用分析 | 复用矩阵 + 架构选型 | 五个决策问题都有答案 |
| 3. 接入设计 | 接入设计说明 | 设计评审通过，无未决 Core/UI 改动 |
| 4. 实施 | 插件 + JSON + 单测 | 构建 0 警告 0 错误，目标测试绿 |
| 5. 验证 | 验证记录 + 能力状态 | 真机/证据覆盖声明，未验证项如实标注 |
| 6. 文档沉淀 | 品牌文档、索引、changelog、BACKLOG | 下一个人能按文档复现 |

整个流程遵守四条硬约束：

- **先被动、后查询、最后才写入验证**；任何写入必须有官方抓包或公开文档出处（[硬件安全规则](../hardware/safety.md) §3）。
- **不改变现有设备识别和遥测行为**；新品牌接入不得顺手改老插件的身份、离线或读数口径。
- **不把未验证能力标成 `supported`**；没有证据就写 `unverified`，确认不支持才写 `unsupported`。
- **发现问题先判断是否影响实际设备**：影响读数/离线/写入安全的先处理；纯代码整洁问题记 BACKLOG，不扩大本轮范围。

## 1. 协议调研

| 项 | 内容 |
|---|---|
| **输入** | 设备实物、VID/PID、接口列表、官方软件安装包/网页驱动、已有品牌文档、抓包工具、`docs/hardware/safety.md` |
| **工作** | 枚举接口；先被动监听；再抓官方软件的同款只读命令；记录帧、偏移、充电码、链路位、查询/应答、休眠/关机信号；判断是否有会话、校验和、分块、多帧状态 |
| **输出** | 协议证据包（抓包文件/日志/截图）+ `docs/hardware/brands/<品牌>.md` 或 `docs/hardware/devices/<型号>.md` 草稿 |
| **完成条件** | 能回答“电量从哪来、充电怎么判、链路怎么判、离线怎么判、哪些是未验证”；每条写入都有出处；没有把命令枚举/字节猜测留在正常路径 |

调研顺序：

1. **只读枚举**：`HidDeviceScanner` / 诊断采集拿到接口、usage、报告长度、产品串；不要先写帧。
2. **被动监听**：能靠 input report 拿到的，优先被动；记录原始 hex 与解析结果。
3. **官方软件抓包**：官方软件能读电量时，抓它的同款只读命令；只复刻读操作，不复刻配置写入。
4. **最小写入验证**：只有前两步拿不到，且帧有明确出处时，才在用户知情下验证；写入必须经过插件开关与熔断闸门。
5. **状态边界**：单独记录充电中、充满、放电、休眠、关机、断链、空槽；不要把“没读到”当成“离线”。

调研阶段就要判断架构，不要等写完代码再补：

- 固定帧、无会话 → 纯数据；
- 多套数据协议 + 少量先听后查/稳定窗口 → 多协议数据优先；
- 握手、ACK、密码门、分块、多代共存 → 有状态；
- 一个接收器多台逻辑设备 → 多设备接收器。

## 2. 现有能力复用分析

| 项 | 内容 |
|---|---|
| **输入** | 第 1 步的协议证据包；四个参考插件；`src/VigilWatt.Core/Plugins/Protocol/`；各品牌 JSON；`BatteryPluginBase` / `OfflinePolicy` / `DeviceClaimRegistry` |
| **工作** | 把需求逐项映射到“已有实现 / 扩展现有 JSON / 新插件代码 / 改 Core / 不做”；检查是否已有同构协议、`extends`、`override`、共享指纹分流、身份归一、离线策略 |
| **输出** | 复用矩阵（每项写结论与证据）+ 架构选型结论 |
| **完成条件** | 五个决策问题全部有答案；没有“先加个通用抽象再说”；Core 改动满足架构标准 §7 的八条准入 |

### 2.1 复用矩阵

每个需求一行，不允许只写“复用”两个字：

| 需求 | 现有实现 | 结论 | 证据/理由 |
|---|---|---|---|
| 读电量 | 某协议 / 某插件 | 复用 / 扩展 JSON / 新代码 | 帧差异、接口差异、真机证据 |
| 充电状态 | … | … | 充电码表是否有出处 |
| 链路/离线 | `OfflinePolicy` / 某插件 | … | 链路位、占位帧、沉默是否有信息 |
| 身份归一 | 路径哈希 / SN / group / 槽位 | … | 是否有稳定 ID 证据 |
| 能力声明 | `devices[].capabilities` | … | 哪些已真机验证 |
| 多设备/接收器 | 罗技会话模型 | … | 是否真是一个接收器多设备 |

### 2.2 五个决策问题

遇到任何“要加特殊逻辑”的念头，先按顺序回答：

1. **这是协议差异还是设备目录差异？**
   - 偏移/码表/查询帧/接口指纹 → 优先协议 JSON；
   - VID/PID/型号/角色/配对/group/能力 → 优先目录 JSON；
   - 状态机、特殊接口分类、会话分派等 JSON 无法合理表达的流程 → 留 C#，并写明理由。
2. **现有四个插件有没有成熟实现？**
   - 有 → 先读对应类与文档，不要凭印象重写。
3. **是否可以直接复用？**
   - 同构 → 复用；只差数据 → `extends` / `override`；只差目录 → 加 `devices[]`。
4. **是否确实需要修改 Core？**
   - 只有一个品牌 → 不改；两个以上同构且有真机证据 → 才进入架构标准 §7 的准入。
5. **是否有真机证据证明需要这项处理？**
   - 没有 → 标 `unverified` 或不做；不要把理论规格写成实现。

任何一项答不上来，停在第 2 步，不要进入设计。

## 3. 接入设计

| 项 | 内容 |
|---|---|
| **输入** | 复用矩阵、协议证据包、架构选型 |
| **工作** | 选定模板；列出目录条目、协议规格、插件方法、身份规则、离线参数、能力声明、写入闸门、默认开关、日志与测试计划 |
| **输出** | 接入设计说明（可放 `docs/reviews/` 或品牌文档的“接入设计”一节） |
| **完成条件** | 设计评审通过；没有未决的 Core 改动；没有未获用户确认的 UI 改版；每个特殊处理都有证据与移除条件 |

设计说明至少写清：

1. **范围**：接哪些 VID/PID、哪些型号、哪些通道；明确不接什么。
2. **架构**：纯数据 / 多协议 / 有状态 / 多设备接收器；选哪个参考实现。
3. **目录与协议**：新增/复用哪些 JSON 条目；是否用 `extends` / `override`；`implementation` 是 `data` 还是 `code`。
4. **身份**：默认路径哈希是否够用；是否需要 SN、group、槽位、自报身份；插线双连接怎么摘接口。
5. **离线**：用哪几条路径；`Silence` / `Confirm` / `MaxFailures` / `CountPollFailures` 的取值与真机依据。
6. **能力**：哪些 `supported`、哪些 `unsupported`、哪些保持 `unverified`；证据是什么。
7. **写入**：是否写帧；默认开关；`WritesEnabled` / `CanWrite` / 熔断怎么走；每轮最多几帧。
8. **日志**：哪些状态变化记 Info，哪些逐帧记 Debug；原始 hex 在哪里。
9. **测试**：纯逻辑单测、录制帧用例、真机验收项。
10. **不做**：明确不做的功能（配置写入、未验证能力、UI 改版等）。

## 4. 实施

| 项 | 内容 |
|---|---|
| **输入** | 通过评审的设计说明 |
| **工作** | 先 JSON 后代码；插件默认继承基类；实现候选/探测/轮询/被动解析；补身份、显示名、能力、开关、日志、单测 |
| **输出** | 插件文件、JSON、单测、必要的 Core 改动（仅限已批准项） |
| **完成条件** | 构建 0 警告 0 错误；目标测试绿；没有无关改动；注释配额与类头格式符合 `docs/dev/comment-style.md` |

推荐顺序：

1. **目录**：`devices[]` 加 VID/PID、型号、kind、protocol、配对/group；未验证型号不要占位。
2. **协议**：`protocols[]` 加接口指纹、passive/active、字段与码表；能 `extends` 就只写差异。
3. **插件骨架**：默认继承 `BatteryPluginBase`；实现 `Name` / `DisplayName` / `DisplayNameEn` / `Kind` / `IsCandidate` / `ProbeAsync` / `PollDevice`。`Probe` 是基类的同步入口，保留时只转调 `ProbeAsync`，探测逻辑不要写两份。只有确实存在基类无法承载的会话型设备，并且经过实际设计确认后，才考虑罗技 R2 类混合型实现；采用时必须明确基类生命周期方法与接口重新实现之间的调用关系（见 §7.3）。
4. **探测与轮询**：纯数据委托 `ProtocolEngine`；有状态按已有会话/分块/ACK 流程实现；先听后查的窗口写清。
5. **身份与显示名**：默认路径哈希；需要时覆写 `BuildDeviceId`；显示名先目录型号，再产品串，最后通用名。
6. **能力**：只从 `devices[].capabilities` 读；认领落地写进 `DeviceStatus.Capabilities`。
7. **开关与写入**：在 `AppSettings.PluginEnabled` 默认表加键；会写帧的默认 `false`；零写入插件显式 `WritesEnabled => false` + `ProbeWrites => false`。
8. **设置页**：品牌级一行，中文 `DisplayName` + 英文 `DisplayNameEn`；不带型号/品类/协议/通道。
9. **日志**：状态变化 Info，逐帧/探测明细 Debug；不要刷屏。
10. **单测**：帧解析、身份、离线、能力等纯逻辑优先；用录制帧钉住偏移。

实施红线：

- 能由现有 JSON 规格表达的设备身份、接口指纹、帧偏移、码表、协议名优先写进 JSON；C# 中保留品牌专用常量时必须有明确协议或实现理由。不得为了 JSON 化把状态机、会话分派等流程逻辑硬塞进 JSON，也不得把这条边界当成随意硬编码的许可；本应配置化的数据仍应进 JSON。
- 默认继承 `BatteryPluginBase`；Logitech 混合型不是新厂商默认模板。只有基类无法承载的会话型设备且设计确认后才采用；采用时必须明确 `new` 隐藏方法与接口重新实现的调用关系，避免以基类静态类型调用导致分支被跳过。
- 不为单个品牌新增通用接口；不实现 `codeFamily` 执行器；不统一目录加载器。
- 不改变现有插件的识别、离线或遥测行为；需要改就单独立项。
- 不引入设备配置写入；不把 `DpiWrite` / `RateWrite` 声明为 `supported`。

## 5. 验证

| 项 | 内容 |
|---|---|
| **输入** | 实现、单测、录制帧、真机 |
| **工作** | 机械层构建/测试；纯逻辑单测；录制帧回归；真机被动/查询/充电/离线/唤醒/双连接/多设备；老品牌回归 |
| **输出** | 验证记录（命令、测试类、日志、抓包、截图）+ 最终能力状态 |
| **完成条件** | 声明的能力都有证据；未验证项如实保留；没有误报离线/在线；老插件行为不变 |

### 5.1 机械层

```powershell
dotnet build VigilWatt.sln -c Debug
dotnet test src/tests/VigilWatt.Core.Tests --no-build --filter "FullyQualifiedName~<相关类名>"
```

- 构建必须 **0 警告 0 错误**。
- 测试规范要求：改了帧解析 / 读数过滤 / 历史库 / 离线判定，必须重跑对应测试类（R7）；合并/发布前应完成全量回归。
- 当前开发环境可能存在的执行限制：不带 `--filter` 的全量 `dotnet test` 在本机会卡住，这是本机环境问题，不是项目不要求全量测试。日常迭代用 `--filter` 跑目标测试类；需要全量时按 [build.md](build.md) §4.1 的绕法把测试产物复制到工作区外运行。

常用过滤：

| 改动 | 过滤 |
|---|---|
| 雷柏 JSON / 身份 | `FullyQualifiedName~Rapoo` |
| 北通目录 / 协议 | `FullyQualifiedName~Betop` |
| 迈从协议 / 遥测 | `FullyQualifiedName~Mchose` |
| 罗技 HID++ / 连接 | `FullyQualifiedName~Logitech` |
| 能力声明 | `FullyQualifiedName~DeviceCapability` |

### 5.2 证据层级

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 代码/静态检查 | 类型存在、分支可达、没有硬编码 | 真机行为 |
| 单测（合成帧） | 解析逻辑、边界、映射 | 固件真实输出 |
| 单测（录制帧） | 该固件版本的帧布局 | 其它型号/固件 |
| 真机被动监听 | 设备确实推这些帧 | 充电/满电/关机全状态 |
| 真机查询 + 官方对照 | 电量/充电口径 | 所有型号 |
| 多日/多状态样本 | 离线阈值、唤醒、插拔 | 未测型号 |

`supported` 的证据要求：真机读数，或被单测钉住的真实录制帧；只有官方规格或理论推算不算。

### 5.3 真机验收清单

- [ ] 冷启动/插拔后能被认领，显示名正确。
- [ ] 电量与官方软件或已知基准一致（至少一个稳定读数）。
- [ ] 充电中、充满、放电三态按协议能力正确；没有充电位就保持 `Unknown`。
- [ ] 设备休眠/关机后按设计离线；唤醒后能恢复，不永久停写。
- [ ] 插线 + 接收器同时在位时只有一条记录，优先保留可读本体。
- [ ] 多设备/多槽位接收器逐槽识别，空槽不误报设备。
- [ ] 插件开关关闭时零写入；打开后才发查询帧。
- [ ] 熔断/退避路径不产生额外命令，不绕过开关。
- [ ] 老品牌设备列表、电量、离线行为无回归。
- [ ] 日志有原始帧与状态变化，足以复盘。

## 7. 三种参考模板

### 7.1 纯数据协议：雷柏

**什么时候用：** 单设备、固定帧、纯被动或固定查询；没有会话、没有校验和、没有跨帧状态。

**照抄什么：**

- `RapooPlugin` 的骨架：`IsCandidate` 委托 `ProtocolEngine.Matches`，`ProbeAsync` 委托 `ProtocolEngine.ProbeAsync`，`PollDevice` 委托 `ProtocolEngine.Poll`，被动帧委托 `ProtocolEngine.Parse`。
- `src/VigilWatt.Core/Plugins/Rapoo/specs/rapoo.protocols.json` 的 `extends` 用法与 `src/VigilWatt.Core/Plugins/Rapoo/rapoo-catalog.json` 的目录结构。
- 零写入声明：`WritesEnabled => false`、`ProbeWrites => false`；只有确认纯被动时才用 `SupportsFastDiscovery => true`。
- 身份/配对：有 SN 才做 SN 归一；有线/无线两个 PID 用 `pairedPid` + `wired`，插线时 `SkipPathsForThisPass` 摘无线。

**不要照抄什么：**

- 雷柏的 `Confirm=6s` / `Silence=90s` / `[18].bit7` 是雷柏心跳实测结果，不是通用默认值。
- 不要假设所有设备都有 SN；没有就回落路径哈希。
- 不要把“纯被动”当成“所有协议都不用查询”；有 `active` 的协议仍要按开关与熔断发帧。

### 7.2 多协议及有状态协议：北通 / 迈从

**北通模板（数据优先）：** 适合同一品牌多套数据协议、以 JSON 为主，但需要少量传输编排。

- 照抄：`BetopPlugin` 的“目录认领 + 引擎探测 + 先听后查 + 稳定窗口 + 占位帧离线 + 显式 group 身份”。
- 适用：鲲鹏 20 的 `0x15` 广播/查询、宙斯被动流；新增型号优先加 `devices[]` 与 `extends`。
- 不要照抄：T9 的 500ms 稳定窗口不要套到 1Hz 广播协议；占位帧语义没有真机证据时不要用。

**迈从模板（有状态）：** 适合握手、会话、ACK、密码门、分块读、多代共存。

- 照抄：`MchosePlugin` 的接口分类、按路径记忆协议、`ReportPollFailure` / `ReportPollAnswered` 自己报账、被动监听与主动查询并存。
- 适用：`keyboard-v1` 的 `0x13` 会话、`mchose-0x4d` 的查询/事件、`cz-block` 分块读；新增型号先加目录/协议，只有流程差异才加代码分支。
- 不要照抄：`KnownProtocolByPath` 只适合“同路径永远同型号”的有状态设备；纯数据协议不需要这层缓存。
- `MchoseA5Plugin` 是“同品牌第二个插件类”的范例：共用设置键、用 `ClaimId` 保持认领互斥。

### 7.3 多设备接收器：罗技

**什么时候用：** 一个 HID 接口（接收器）下挂多台逻辑设备，按槽位/设备索引寻址；设备可能休眠、空槽、直连。

**照抄什么：**

- `ReceiverSession` 的“接收器 → 槽位 → 设备”结构；`SlotId` 的稳定身份。
- 槽位容量：接收器自报优先，目录 `maxSlots` 兜底；空槽负缓存与首次整轮无应答的句柄重建。
- `HidppNotificationQueue` 的“读报文只入队、派发在 I/O 锁外”；通知里未知槽位只登记，下一拍发现。
- 身份与链路分开：接收器体系是 `ReceiverIdentity`，链路是 `Connection`；推断只记 `Inferred`。
- 写入闸门：HID++ 的 `HidppIO.WritesAllowed`、Centurion 的 `WritesEnabled`、熔断与退避。

**不要照抄什么：**

- HID++ 的 feature ID、电压曲线、`0xB5` 寄存器细节是罗技协议事实，不要搬到别的品牌。
- 罗技的槽位模型不是通用接收器模型；别的品牌可能只是透明通道，先证明“一个接口多设备”再套。
- `LogitechPlugin` 的混合型 R2 例外不是默认模板，更不是所有新厂商的默认模板。默认优先继承 `BatteryPluginBase`；只有确实存在基类无法承载的会话型设备，并且经过实际设计确认后，才考虑采用。采用时必须逐条补齐基类能力，并明确基类生命周期方法与接口重新实现之间的调用关系：`LogitechPlugin` 对 `AttachAsync` / `Poll` / `ReconcileRemovals` 使用 `new` 隐藏并重新声明 `IBatteryPlugin`；不要以 `BatteryPluginBase` 静态类型持有它再调用，否则 HID++ 分支会被静默跳过（见架构标准 §2.3、CR-93）。

## 8. 统一决策规则

新增特殊逻辑前，必须留下这五个答案：

1. **协议差异还是目录差异？** → 能数据化的改 `protocols` 或 `devices`；状态机、特殊接口分类、会话分派等流程留 C# 并写明理由。
2. **现有四个插件有没有成熟实现？** → 有就复用，不重写。
3. **是否可以直接复用？** → 同构复用；只差数据用 `extends` / `override`；只差目录加条目。
4. **是否确实需要修改 Core？** → 只有一个品牌不改；两个以上同构且满足架构标准 §7 才改。
5. **是否有真机证据？** → 没有就标 `unverified` 或不做，不把理论写成实现。

如果现有能力足够，**不增加新机制**。如果五个问题里有任何一个答不上来，回到协议调研或复用分析，不进入实施。

## 9. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 把 `capabilities` 写到协议层 | 加载器报错，或声明丢失 | 只写 `devices[].capabilities` |
| 把未验证型号先塞进 `devices[]` 占位 | 目录优先，直接认领并顶掉 fallback 名 | 先放文档（该目录支持时放 `officialDevices[]`），验证后再进 `devices[]` |
| 按型号系列/PID 邻近合并设备 | 两台设备串台、历史混在一起 | 只用显式 `group` / SN / 槽位 |
| 把 `null` 一律当离线 | 零写入/熔断/纯推送设备永远离线或误报 | 区分“没发帧”和“发了没应答”；用 `ReportPollFailure` |
| 把 `SupportsPassiveListen` 和 `CountPollFailures` 合成一个布尔 | 关机后永远不离线 | 两个独立声明 |
| 为单个品牌加 Core 抽象 | Core 被品牌事实污染 | 留在插件；两个以上同构再评估 |
| 没有出处就写帧 | 可能把 dongle 会话搞死 | 官方抓包/公开文档 + 用户知情 + 开关/熔断 |
| 没有真机就把能力标 `supported` | 用户看到假能力 | `unverified`；有真机/录制帧再升级 |
| 缩短离线阈值求“快” | 误报离线 | 用真机噪音样本校准 |
| 改身份规则不评估历史 | 旧曲线对不上新 ID | 单独立项、写迁移说明 |
| 在 `devices[]` 重复登记同一 `VID:PID` | 后写条目覆盖前写条目，前一条静默失效 | 人工检查唯一性；当前加载器不会拒绝重复项 |
| 设置页写型号/品类 | 违反品牌级开关规则 | 只写中文名 + 英文名 |

## 10. 完成检查清单

- [ ] 协议证据包完整：帧、查询、充电、链路、离线、未验证项。
- [ ] 复用矩阵逐项有结论，五个决策问题有答案。
- [ ] 设计说明写清范围、架构、目录/协议、身份、离线、能力、写入、测试、不做项。
- [ ] 插件默认继承 `BatteryPluginBase`；只有基类无法承载的会话型设备且设计确认后才用 R2 例外混合型，并有类头理由与生命周期调用说明。
- [ ] 新型号优先 JSON；新增 C# 代码里没有本应配置化的设备身份、接口指纹、帧偏移、码表、协议名；保留品牌常量时有明确理由。
- [ ] 新增/修改 `devices[]` 时没有重复 `VID:PID`（当前加载器不会拒绝重复项）。
- [ ] 会写帧的插件默认关闭；`WritesEnabled` / `CanWrite` / 熔断路径完整。
- [ ] 能力只在 `devices[].capabilities`；`supported` 有真机或录制帧证据。
- [ ] 身份归一有规则；插线双连接只留一条。
- [ ] 离线路径与协议事实匹配；没有把触发器当证据。
- [ ] 构建 0 警告 0 错误；目标测试绿；老品牌无回归。
- [ ] 品牌文档、协议索引、changelog、BACKLOG/handoff 已按职责更新。
- [ ] 没有新增抽象接口、没有 `codeFamily` 执行器、没有统一目录加载器、没有配置写入。
