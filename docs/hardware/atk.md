# ATK / VXE 2.4G 电量（接收器 VID_373B）

鼠标走 16 字节 op 帧，键盘走 VIA，同一个 VID 下按 usage page 分流。鼠标部分：协议出处是公开逆向项目 [0x44oge-ATK](https://github.com/ReformedDoge/0x44oge-ATK)，本项目在其基础上做了真机复核与补强。

- **设备**：ATK 烈空 F1 Pro Max、F1 V3 ULTIMATE+、A9 Air 大师版+ 等同协议系列
- **VID**：`0x373B`（十进制 14139）。⚠ **不是**容易误抄的 `0x375B`
- **PID**：
  - 接收器：8K `0x101B`（产品名 `ATK Mouse 8K Dongle`）、1K `0x101A`、`0x1303`（产品名 `Wireless mouse 8k dongle-M`）、
    GEM 8K `0x1278`（产品名 `Wireless mouse 8k dongle-L`）
  - **鼠标本体（插充电线时枚举）**：**因型号而异**——F1 Pro Max = `0x1015`、F1 V3 ULTIMATE+ = `0x12A9`、A9 Air 大师版+ = `0x1293`
    （本体上报的产品名即机型，如 `ATK F1 V3 ULTIMATE+`、`ATK A9 Air+`）。**因此本体不能靠 PID 白名单穷举**，
    插件改用"没有任何接收器在位时，剩下的就是本体"来判定，新型号自动支持。
- **本机验证（上游维护者机器）**：F1 Pro Max 与 F1 V3 ULTIMATE+ 两台真机（电量 95% / 75%），与官方 ATK HUB 3.2.28 **共存实测无冲突**
- **A9 Air 大师版+（本 PR 作者机器，2026-10-26，单台）**：无线 70% / 80% 放电、插线 85% / 95% 充电均全应答，
  读数与官方 HUB 一致。其余两组（`promax` / `v3` / `f1ult`）的配对行沿用上游与既有记录，**本次未复测**

## 1. 接口地图

| 接口 | 用途 |
|---|---|
| `MI_01&COL05`（usagePage `0xFF02` / usage `0x0002`，17B in-out） | **电量通道** |
| `MI_01&COL01`（`0xFF05`）、`COL03`（`0xFF03`）、`COL04`（`0xFF04`）、`COL06`（`0xFF06`） | 其它功能，非电量 |

认领条件：`VID == 0x373B` 且 **`UsagePage == 0xFF02`**（精确匹配电量口）。
⚠ 不能放宽成 `>= 0xFF00`：同一设备还有 FF03/FF04/FF05/FF06 等厂商口，放宽后基类会对每个口各跑一次探测，每个口都白白发一帧查询——违反 `safety.md` §3 规则 4 的限频要求。

### 1.1 长度判据

除usage page 外还要求**接口能收发 17 字节帧**（`in == 17 && out == 17`，对齐 PR #28 的 `IsSupportedInterface`）：

| 设备 | `in` | `out` | 来源 |
|---|---|---|---|
| F1 Pro Max 8K 接收器 `0x101B` | 17 | 17 | 本机实测 |
| F1 Pro Max 1K 接收器 `0x101A` | 17 | 17 | 本机实测 |
| F1 V3 ULTIMATE+ 8K-M 接收器 `0x1303` | 17 | 17 | 本机实测 |
| F1 Ultimate 2.0 接收器 `0x11D9` / `0x11E4` | 17 | 17 | 本机实测 |
| A9 Air 大师版+ GEM 8K 接收器 `0x1278` | 17 | 17 | 本机实测（2026-10-26） |
| A9 Air+ 本体 `0x1293`（插线） | 17 | 17 | 本机实测（2026-10-26） |

- **接收器**用严格判据 `in == 17 && out == 17`（四个 PID 实测一致）。
- **有线本体**（插充电线时才枚举出来，PID 随型号变）只要求"容得下"（`in >= 17 && out >= 17`）——
  A9 Air+ 实测同样是 17 / 17，但其余型号的本体尚未逐个实测，写死 `== 17` 会在实测出别的长度时把本体误杀。

⚠ **长度判据放松就会被回显帧骗到**：同一接收器上 `0xFF60`（VIA）等其它通道会把请求原样回显，
回显帧的校验和是旧值——只有"帧长判据 + 校验和"同时成立才挡得住（PR #28 的实测结论）。

## 2. 帧格式（17 字节，report ID `0x08`）

请求：

```
08 04 00×14 49
```

校验算法（0x44oge 的 `calculateAtkChecksum`）：`尾字节 = (0x55 − 前 16 字节之和) & 0xFF`，本例即 `0x49`。
（"前 16 字节" = report ID + op 帧的前 15 字节；op 帧口径写法见下方说明。）
帧构造见 `AtkCodec.BuildQuery`。

> **帧长两种记法，同一协议**：上面写的是"线上 17 字节（含 report ID）"。
> 另一种记法是"op 帧 16 字节（不含 report ID）"，校验写成 `chk = (0x4D − op 帧前 15 字节之和) & 0xFF`。
> 两式**完全等价**（`0x4D = 0x55 − 0x08`）：已对本机抓到的 20 帧逐帧验算，两种口径全部通过。
> PR #28 用的是 op 帧记法，本 PR 用的是含 report ID 的线上记法——合并时按任一种统一即可，
> **不要留两套帧长判据**。

响应：

```
08 04 <b2> <b3> <b4> <b5> <电量%> <充电> <电压mV大端16位> … <校验>
```

| 偏移 | 含义 | 实测样本 |
|---|---|---|
| `[6]` | 电量百分比 | `0x5F` = 95%、`0x64` = 100% |
| `[7]` | 充电 / 有线标志 | **`0x00` = 放电（无线）；`0x01` = 充电（有线）** |
| `[8..9]` | 电池电压（大端 16 位） | `0x0FFC` ≈ 4092 mV、`0x1061` ≈ 4193 mV |

实测原始帧（**均为本机抓包**，见 §3.1）：

```
无线·放电 95%   08 04 00 00 00 02 5F 00 10 01 00 00 00 00 00 00 D7
无线·放电 95%   08 04 00 00 00 02 5F 00 0F FC 00 00 00 00 00 00 DD
有线·充电 95%   08 04 00 00 00 02 5F 01 10 61 00 00 00 00 00 00 76
有线·充电 95%   08 04 00 00 00 02 5F 01 10 5D 00 00 00 00 00 00 7A
无线·放电 100%  08 04 00 00 00 02 64 00 10 1E 00 00 00 00 00 00 B5
```

几点值得注意：

- **校验算法得到独立验证**：上列 5 帧的尾字节全部符合 `(0x55 − 前 16 字节之和) & 0xFF`。
  ⚠ 早期文档写作"前 15 字节"，漏算了 `[15]` 那一字节；本批样本的 `[15]` 恰好恒为 `0x00`，
  所以两种写法在本批抓包上结果一致——但口径必须写准，合并成一份 codec 时才对得上。
- **响应帧必须过校验和才采信**（`AtkCodec.ChecksumValid`）：固件会在同一设备上混发普通鼠标报文与
  厂商私有集合帧，只看"命令字 + 电量范围"会把非电量帧读成假读数；校验和是当前唯一能挡住这类帧的判据。
- **设备会把请求原样回显**：回显帧的校验和是**对的**、但电量位是 `0`，靠电量下界（`≤1` 视为休眠占位）挡住。
- **同一设备上确实混发非电量帧**（2026-10-24 实机复验时抓到）：
  `08 03 00 00 00 01 01 CB B3 8D 00 00 00 00 00 00 3D` —— 命令字是 `0x03`（不是 `0x04`），
  （A9 Air 的 GEM 接收器 `0x1278` 上又抓到一条同类帧：`08 03 00 00 00 01 00 8C 99 01 00 00 00 00 00 00 23`，
  纯被动监听所得、未发任何字节——说明这类 `0x03` 帧是固件自己推的，与查询无关）
  在同一次读的队列里紧跟着电量帧出现。这条帧命令字判据能挡住，但**校验和是独立于命令字的第二道防线**：
  凡是"命令字合法 + 电量位落在 2–100、但校验和对不上"的帧，旧实现会直接读成假读数，新实现一律拒绝。
- **`[8..9]` 是实时电压，不是常量**：同一状态下会在几 mV 内抖动（4092↔4097、4126↔4130）。
- **充电时电压高于放电时**：充电 4189~4193 mV vs 放电 4092~4097 mV，符合物理。
- **`[7]` 是可靠的充电判据**：`0x00` / `0x01` 在各自状态下连采多条均稳定，未见抖动。
- **读数与官方 HUB 交叉验证一致（A9 Air 大师版+）**：同一时刻本探针读到 `[6]=0x5F`（95%）、`[7]=0x01`，
  ATK HUB 界面同时显示 95% 充电中——两路独立取值一致，`[6]` 是电量位得到官方软件侧的确认。
- **充电读数虚高约 15 个百分点（A9 Air 大师版+ 实测，同一台鼠标相邻两分钟）**：

  | 状态 | `[6]` 电量 | `[8..9]` 电压 | `[7]` |
  |---|---|---|---|
  | 有线·充电 | **95%**（`0x5F`） | 4276 mV | `0x01` |
  | 拔线·放电 | **80%**（`0x50`） | 4213 mV | `0x00` |

  电压只差 63 mV，电量差 15 pp → 真实容量贴近 80%，充电时的高读数是**充电端电压抬升**让电压法电量计虚高。
  连带解释两条易被误判为"解析错了"的现象：①充电中读数涨得飞快（70% → 85% → 95% 约 25 分钟，
  实际只充进去约 10%）；②**插拔线瞬间读数会跳变**（95% ↔ 80%）。
  两者都是固件行为，插件与官方 HUB 读数一致，**codec 不做任何修正**——修正会掩盖设备真实的电压状态。

## 2.1 三种接收器的对照测试

ATK 同族鼠标标配多个接收器（一只鼠标可切 1K / 8K 无线模式）。**三个接收器都认同一条查询帧
`08 04 00×14 49`，响应结构完全一致**：

| | 8K `0x101B` | 1K `0x101A` | 8K `0x1303` |
|---|---|---|---|
| HID 产品名 | `ATK Mouse 8K Dongle` | （1K dongle） | `Wireless mouse 8k dongle-M` |
| 电量接口 | `MI_01&COL05` / `0xFF02` | **相同** | **相同** |
| 输出 / 输入报告长度 | 17 / 17 | **17 / 17** | **17 / 17** |
| Feature 报告长度 | 0 | **0** | **0** |
| 查询帧 | `08 04 …49` | **同一条** | **同一条** |
| 响应字节数 | 17 | **17** | **17** |
| `[6]`电量 / `[7]`充电位 / `[8..9]`电压 / `[16]`校验 | ✅ | **完全一致** | **完全一致** |
| `MI_00` | HID-compliant mouse | HID Keyboard Device | HID-compliant mouse |
| `MI_02` | USB Keyboard Device | HID-compliant mouse | HID Keyboard Device |
| 接口总数 | 10（含 `MI_01&COL08`） | 9 | 13（`MI_01` 多 COL07/COL08） |

`0x1303` 实测响应（连采 5 条全部应答、校验全部通过，电量 75%）：

```
08 04 00 00 00 02 4B 00 10 3A 00 00 00 00 00 00 B2    ← 第 1~3 条
08 04 00 00 00 02 4B 00 10 35 00 00 00 00 00 00 B7    ← 第 4~5 条
```

1K 实测响应（连采 5 条全部应答、校验全部通过，电量 100%）：

```
08 04 00 00 00 02 64 00 10 22 00 00 00 00 00 00 B1    ← 第 1~4 条
08 04 00 00 00 02 64 00 10 1E 00 00 00 00 00 00 B5    ← 第 5 条
```

差别只在**接口角色**上（枚举顺序不同，内容一一对应）：`101A` 的 `MI_00` 是键盘口、`MI_02` 是鼠标口，
**与 8K 正好互换**；`101B` 多一个 `MI_01&COL08`。

⚠ **踩过的坑**：前两次测 `0x101A` / `0x1303` 时鼠标电源是关的，5 次全部无应答，差点误判成
"这些接收器不支持这条帧"。**排查顺序应是：先确认鼠标已上电并与当前接收器配对，再谈协议差异**——
休眠/关机的表现同样是"不回帧"（见 §3）。

## 2.2 A9 Air 大师版+ 与 GEM 8K 接收器（`0x1278`，2026-10-26 本机实测）

A9 Air 大师版+ 是新一代机型（Nordic 54L15 主控、8T8R、标配半透明 GEM 8K 接收器），
接收器 PID 与前三代 8K 都不同：`0x1278`，产品名 `Wireless mouse 8k dongle-L`。
**协议与老机型完全一致**——同一条 `08 04 00×14 49` 查询帧、17 字节应答、同样的字节位：

| 形态 | PID | 产品名 | 接口形状 | 实测应答 |
|---|---|---|---|---|
| 2.4G（GEM 8K 接收器） | `0x1278` | `Wireless mouse 8k dongle-L` | `MI_01&COL05` / `0xFF02`，17 / 17 | 3/3 全部应答 |
| USB-C 有线（本体） | `0x1293` | `ATK A9 Air+` | `MI_01&COL05` / `0xFF02`，17 / 17 | 3/3 全部应答 |

接口地图与老机型逐项对应：`COL01 FF05` / `COL02 FF03` / `COL03 000C` / `COL04 0001` /
`COL05 FF02`（电量）/ `COL06 FF04`（8 字节 feature）/ `COL07 FF06`（49 字节）/ `COL08 0001`，
接口总数 10，`MI_00` = 鼠标、`MI_02` = 键盘。**没有新增接口，也没有改长度**，所以插件零改动即可
用同一条帧读数。

实测响应（本机抓取，校验和逐帧核对通过）：

```
2.4G · 放电 65%   08 04 00 00 00 02 41 00 0F CD 00 00 00 00 00 00 2A    4045 mV
有线 · 充电 80%   08 04 00 00 00 02 50 01 10 5E 00 00 00 00 00 00 88    4190 mV
```

- `[7]` 充电位表现与老机型一致：无线 `0x00`、插线 `0x01`（各连采 3 条，无抖动）。
- `[8..9]` 电压同量级（4045 mV 放电 / 4190 mV 充电），符合物理。
- ⚠ **第一次探测必须确认鼠标醒着**：本机第一次连发 3 条全部无响应，晃动鼠标后立刻 3/3 应答——
  与 §3 记录的休眠行为完全一致，**不要把它误判成"新机型协议不同"**。

**配对线索（未用于代码）**：GEM 接收器与本体在 USB 层的序列号相同（本机均为 `541505796617`），
这是 `atk.md` §4 里前三代机型所没有的自动配对标识。但插件侧的扫描器（`HidDeviceScanner`）不采集
序列号，故仍按 §4 的实测配对表归一；将来若扫描器补上序列号，可改用序列号自动配对并删掉配对表。



**实测结论（2026-10-23 本机抓包，两轮独立复核）**：鼠标闲置后，dongle 对电量查询帧**完全不回应**——
不是回 0、不是回旧值，而是**没有任何 `08 04` 帧返回**（每种状态连采 3 次，每次等 1.2s 均无响应）。
**关闭鼠标电源开关后同样不回**。

```
[第1轮] 闲置 20 分钟后 · 3 次查询 → 全部无响应（1.2s 内没读到 08 04 帧）
[第2轮] 闲置 10 分钟后 · 3 次查询 → 全部无响应
[第1轮] 关闭电源开关后 · 3 次查询 → 全部无响应
[第2轮] 关闭电源开关后 · 3 次查询 → 全部无响应
```

注意：dongle 本身**始终在位**——`MI_01&COL05` / usagePage `0xFF02` 接口照常被 Windows 枚举出来，
只是不会替一只睡着的（或断电的）鼠标回帧。**休眠与关机的表现完全一致**，无法区分这两者。

**查询本身唤不醒设备**（2026-10-26 拔线后实测）：拔掉数据线回到无线、鼠标静止后，
前 3 次查询 0/3 无应答；此后按 1.2 秒间隔连发，**前 18 次仍全无应答**，直到用户晃动鼠标后
第 19 次（约 23 秒）才开始应答，随即 14/14 全部成功（80% 放电 / 4213 mV，帧内容完全一致）。
→ 唤醒只能靠物理动作（移动/按键），空发查询不会把设备叫醒，所以插件的"熔断停写 + 递增退避"
正好符合这个行为：睡着的设备不该被高频空查询吵。

这一点对实现的影响：

- 读不到帧 → 插件按"查询失败"记账 → 连续 3 次触发**熔断停写 + 递增退避**（基类机制）。
  日志里可见完整循环：`连续 3 次查询失败，熔断停写` → `停写退避期满（30 秒），恢复查询` → 再失败 → 退避 60 秒…
- 退避是**必需**的：鼠标休眠是常态，固定的长退避会把"唤醒后恢复读取"一起挡死
  （`docs/hardware/safety.md` §3 规则 3 的由来，正是同类教训）。
- 唤醒后第一次查询成功即清零失败计数、解除熔断。

⚠ **但"唤醒后第一次查询"以前要等很久**（2026-10-27 修）：递增退避的档位只在读到应答时清零，
鼠标每睡一次就失败 3 轮、顶高一档，一天下来轻松爬到第 4 档（240 秒）。用户动鼠标唤醒后仍被退避挡着，
实机日志里出现过 **4 分 29 秒没有一次读数**，看起来就是"电量卡死、得手动刷新"。

修法是给纯查询型插件补一条独立的**半开探活**通道（`BreakerProbeInterval`，本插件 30 秒）：
熔断期内按间隔发一帧核实，**失败不记账、不升档**，成功即解除熔断；同时本插件接入 15 秒发现节拍，
把"睡醒被认领"的延迟从最坏 60 秒压到 15 秒。本机实测：启动时鼠标在睡、一直未认领，
19:07:51 鼠标被唤醒后**落在 15 秒节拍上**立刻认领并读到 85%。
细节与其它插件的影响面见 `docs/dev/runtime-pitfalls.md` §23。

因此**不需要**为休眠态专门解析什么——插件读不到帧就不更新读数，界面保持"最后已知读数 + 离线标记"。

⚠ 此前曾按参考实现的推断写成"休眠时仍会回应一帧、电量字节为 0"，**已被实测证伪**：本机休眠时是**完全不回**。
代码里"拒绝电量 ≤ 1"的防护仍保留（防止其它场景读到 0%），但它不是针对本机休眠行为的。

### 3.1 原始帧样本

**原始帧样本**（两轮独立采集，2026-10-23；第 2 轮为复核，结论与第 1 轮完全一致）：

| 轮次 | 场景 | 原始 17 字节 hex | `[7]` | 电压 |
|---|---|---|---|---|
| 1 | 无线 · 放电 | `08 04 00 00 00 02 5F 00 10 01 00 00 00 00 00 00 D7` | `0x00` | 4097 mV |
| 1 | 无线 · 放电 | `08 04 00 00 00 02 5F 00 0F FC 00 00 00 00 00 00 DD` | `0x00` | 4092 mV |
| 1 | 有线 · 充电 | `08 04 00 00 00 02 5F 01 10 61 00 00 00 00 00 00 76` | `0x01` | 4193 mV |
| 1 | 有线 · 充电 | `08 04 00 00 00 02 5F 01 10 5D 00 00 00 00 00 00 7A` | `0x01` | 4189 mV |
| 1 | 放电 · 满电 | `08 04 00 00 00 02 64 00 10 1E 00 00 00 00 00 00 B5` | `0x00` | 4126 mV |
| 1 | 休眠（闲置 20 分钟） | **无响应** ×3 | — | — |

几点值得注意：

- **两轮独立复核结论一致**：`[7]` 跨轮次、跨状态恒为 `0x00`（放电）/ `0x01`（充电）；
  充电态连采 5 条全为 `0x01`，未见抖动。
- **满电时 `[7]` 仍是 `0x00`**——它表达的是"**正在充电**"，不是"**插着线**"
  （满电那会儿鼠标插的是接收器，无线）。
- **`[6]` 与 `[7]` 相互独立**：满电 100% 配 `0x00`、充电 95% 配 `0x01`，两个字段各管各的。
- **校验字节全部符合** `(0x55 − 前 15 字节之和) & 0xFF`（两轮共 11 帧逐帧核对）。
- **`[8..9]` 是实时电压**：同一状态下有几 mV 抖动（放电 4092~4138、充电 4189~4197）。

回归单测 `AtkCodecTests.A3` / `A4` 用的是**按协议构造**的边界样本（用于锁住"不校验电量下界就会读出 0%"
这一行为），不代表抓包证据。

### 3.2 有线模式的枚举行为

**Windows 会把插线充电时的鼠标本体枚举成另一台设备实例**（PID 与接收器不同），
且**本体 PID 因型号而异**：

| | 接收器 | 插线时的本体（F1 Pro Max） | 插线时的本体（F1 V3 ULTIMATE+） |
|---|---|---|---|
| PID | `0x101B`（8K）/ `0x101A`（1K）/ `0x1303`（8K） | `0x1015` | **`0x12A9`** |
| HID 产品名 | `ATK Mouse 8K Dongle` / `Wireless mouse 8k dongle-M` | `ATK F1 PRO MAX` | **`ATK F1 V3 ULTIMATE+`** |
| 电量接口 | `MI_01&COL05`，usagePage `0xFF02`，17B in-out | **同样是 `MI_01&COL05` / `0xFF02`** | **同样是 `MI_01&COL05` / `0xFF02`** |
| 电量接口路径实例号 | `8&A2C29E2&0&0004` | `8&2B7F60F&0&0004` | `8&1D6F4258&0&0004` |
| 键盘口实例号 | `MI_02` `8&3296D7AB` | `MI_02` `8&97FFED` | `MI_02` `8&A3F261A` |
| 接口总数 | 10（多一个 `MI_01&COL08` / `0x0001`） | 9 | 10 |

接口结构一一对应：本体与接收器的 **COL01~COL07 完全对应**（`FF05` / `FF03` /
`000C` / `0001` / `FF04` / `FF06`），只有接收器多一个 `COL08`。

两端读到的**电量一致**（同为 95%），差别只在 `[7]` 充电标志（本体 `0x01`，
接收器 `0x00`）——因为插线时接收器已经不在位，读到的是鼠标本体自己的电池状态。

F1 V3 ULTIMATE+ 插线时的实测响应（`[7]`=`0x01`，与 F1 Pro Max 一致）：

```
08 04 00 00 00 02 5F 01 10 E2 00 00 00 00 00 00 F5    电量95%  充电位 0x01  4322mV  校验OK
```

⚠ **本体 PID 不可穷举**（`0x1015` / `0x12A9` / `0x1293` … 随型号变），所以插件**不靠 PID 白名单认本体**：
已登记分组的本体一律可认领，重复的那条接收器交给 §4 的配对摘掉；只有**未登记分组**的新型号才退回
"没有任何接收器在位时，剩下的 0xFF02 接口就是本体"的保守判法。

插件据此把两个接口归一到同一条设备记录（见 §4）。

### 3.3 双连接：接收器没拔就插了数据线（2026-10-26 本机实测）

A9 Air 大师版+ 在**接收器仍插着**的情况下接上 USB-C 数据线，设备树里两条链路同时在场：

| 形态 | PID | HID 产品名 | 电量查询帧应答 |
|---|---|---|---|
| 接收器 | `0x1278` | `Wireless mouse 8k dongle-L` | **0 次**（沉默） |
| 本体 | `0x1293` | `ATK A9 Air+` | **3/3 应答**：85%、充电位 `0x01` |

结论：**鼠标固件一旦切到有线，无线电就停了**，接收器那条链路变成死口。
所以"接收器在位 → 本体不是本体"这个判法是错的——恰恰相反，双连接时**只有本体能给读数**。

这也解释了为什么不能靠接收器拿整机状态：它报的是插线**之前**的旧快照，
且产品名是通用串（`Wireless mouse 8k dongle-L`），拿不到机型。

（同一次双连接期间还出现过光标可移动、点击无响应的现象，原因未定论，不作协议结论记录。）

插件侧验证（同一台机、同一套接口，2026-10-26 22:21）：

```
认领ATK设备: ATK A9 Air+ [VID_373B&PID_1293] usage=0xFF02/0x0002 in=17 out=17
             outId=0x08 proto=atk-v1 电量=85 充电=Charging
托盘提示已更新: VigilWatt · ATK A9 Air+ 85%
```

- 两条链路同时在场时**只出一条记录**：两条接口同属 `a9air` 组、共用同一个设备 ID，
  基类 `ExistingPathOfSameDevice` 保留先探测成功的那条、释放另一条（实测只有本体应答）。
- 去掉数据线、只剩接收器时（22:01 同机）：`VID_373B&PID_1278` → 70% 放电，显示名回落为接收器通用名
  `Wireless mouse 8k dongle-L`——这是 §4.1 已记录的行为（机型名只有本体上报才有）。



## 4. 设备 ID 归一：按「配对组」，一只鼠标一条

同一台鼠标的**接收器**与**插充电线时枚举出的本体**是同一台设备（充电时通常要拔掉接收器腾 USB 口，
两个接口会先后出现）。若按接口路径生成 ID，UI 上就会多出一台"设备"，且拔线后那条记录残留。

但**不能**简单地按「厂商 + VID」归一——那样同机接两台 ATK 鼠标（F1 Pro Max 与 F1 V3 ULTIMATE+）
会共用一条记录、读数串台。

该鼠标的 HID 描述符**序列号为空**，容器 ID 也不同，**硬件层没有可自动配对的标识**，
只能按真机实测出的配对表归组：

| 组 | 接收器 PID | 本体 PID（有线模式） | 机型 |
|---|---|---|---|
| `promax` | `0x101B`（8K）、`0x101A`（1K） | `0x1015` | ATK 烈空 F1 Pro Max |
| `v3` | `0x1303`（8K-M） | `0x12A9` | ATK F1 V3 ULTIMATE+ |
| `f1ult` | `0x11D9` | `0x11E4` | ATK F1 Ultimate 2.0 |
| `a9air` | `0x1278`（GEM 8K） | `0x1293` | ATK A9 Air 大师版+ |

⚠ 同一只鼠标可配**多个接收器**（F1 Pro Max 标配 1K 与 8K 两套），它们属于**同一组**——
同机插两个接收器也只显示一条设备记录。

- 插件覆盖基类的 `IdFor`，按组生成 `atk-promax` / `atk-v3` / `atk-a9air`：**同组共用一个 ID，不同鼠标各自一条**。
- **未登记的 PID 交回基类默认（路径哈希）**，即等同上游行为——宁可充电时多一条，
  也不能把两台不同的鼠标并成一条。
- 认领时**已登记分组一律可认领**，不再互相否决：接收器与本体同时在场时两条都进候选，
  同组共用一个设备 ID，基类 `ExistingPathOfSameDevice` 保留先探测成功的那条。
  实测依据见 §3.3：双连接切到有线后接收器已沉默、只有本体应答，所以实际留下的是本体。
  ⚠ 这一条必须是"**一律可认领**"而不是"按组让位"：同机接两台 ATK 鼠标时，
  另一台的接收器不能把本台的本体挤掉（2026-10-23 实机复现：F1 V3 插线后本体不认领）。
- 序列号只在**两边都有值**时作为否决条件（SN 不同 = 两只不同鼠标，不合并）；
  但 `HidDeviceScanner` 目前**不填 `SerialNumber`**（只填 Product / Manufacturer），
  实际运行拿到的是空串，所以配对**主要靠型号组**。SN 一旦补上会自动变严，无需改这段逻辑。


⚠ 配对表是实测结论，新增型号需要补一行；补之前该型号会退化为上游默认行为（可显示，但充电时多一条）。

### 4.2 换插充电线时另一台设备短暂离线（已修）

Windows 在 USB 重新枚举 HID 设备时，旧句柄会失效、读帧失败。若把这种句柄失效当成设备故障
计入失败计数，会连续触发熔断，让**另一台**鼠标假离线 30~60 秒（退避恢复）。

插件据此区分两类失败：**写帧失败 = 句柄已失效**（设备被拔出或重枚举，不计失败，基类下一轮
扫描会移除旧记录并重新认领）；**读帧失败 = 设备在位但不回帧**（鼠标休眠，该熔断）。

### 4.1 显示名从哪来

| 场景 | 显示名 | 来源 |
|---|---|---|
| 无线（接收器在位） | `Wireless mouse 8k dongle-M`（或 `ATK Mouse 8K Dongle` / `Wireless mouse 8k dongle-L`） | 接收器上报的 HID 产品字符串 |
| 插线充电（本体在位） | `ATK F1 V3 ULTIMATE+` / `ATK A9 Air+` | 本体上报的 HID 产品字符串（即机型） |

**接收器上报的是通用名，不含机型**（GEM 8K 接收器跨多个系列通用，`0x1278` 更不能当机型判据）；
其余厂商口（FF03/FF04/FF05/FF06）被动读 1.5 秒**零帧**，
只在被查询时应答——所以**型号信息只有插线时本体枚举出来才能拿到**。

插件的处理：本体被枚举过一次后，把它的产品名**按归一组**记住（进程内缓存），之后显示名就用它。
多只鼠标各记各的，不会互相覆盖。进程重启后需要再插一次线才能恢复；也可以在设置页用
**设备自定义**功能固定改名。

⚠ **手动改名对"无线/有线"两种形态同时生效**，不需要任何额外机制：`IdFor` 已把接收器与本体归到
同一个设备 ID（如 `atk:atk-a9air`），而改名是按设备 ID 匹配的（`DeviceCustomizationResolver.ApplyName`），
所以给这只鼠标改一次名，插不插线都显示这个名字。这也是目前**唯一**能跨进程固定的办法——
项目里没有"插件自动学习并持久化显示名"的先例（`DeviceCustomizations` 是用户手动设置），
按现状不为此新增持久化机制。

### 4.3 本体必须能**独立认领**（2026-10-27 修，两个型号各一条路）

配对表前几行都遵循"同组接收器在位 → 本体让位"。**本体在插线时必须能自己认领**，否则会出现
"dongle 认不上、本体又不许认"——整只鼠标从列表里消失。两个型号的实测成因不同，修法也不同：

**F1 Ultimate 2.0（`0x11E4`）：本体留在 `IsReceiverPid` 里**

它的本体 PID 也留在 `IsReceiverPid` 白名单里，两条接口各自独立认领，靠 ID 归一去重。
原因是实测出来的：**鼠标插着充电线时，dongle 读不到电量**。此时鼠标走有线链路，
dongle 收不到无线包，`Probe` 无应答 → dongle 不被认领。如果沿用"接收器在位就否决本体"，
就会变成"dongle 认不上、本体又不许认"——**整只鼠标从列表里消失**（2026-10-27 19:23 实测复现）。

**A9 Air 大师版+（`0x1293`）：本体不进白名单，靠"已登记分组一律可认领"**

本体 0x1293 **故意不**列入 `IsReceiverPid`——它的产品名 `ATK A9 Air+` 是唯一准确的机型来源，
留在外面才能被 `BuildDisplayName` 学到（§4.1）。它走 `IsCandidate` 里"已登记分组"那条分支直接认领，
不查本组接收器在不在位（§3.3 实测：插线后接收器连发 3 次 0 应答，只有本体回 85%/充电中）。

两条都能认领之后：

| 场景 | 谁被认领 | 结果 |
|---|---|---|
| 无线使用（没插线） | dongle | 一条，同组 ID |
| 插线充电（dongle 读不到） | 本体 | 一条，同一个 ID |
| 两者都能读（罕见） | 先探测成功的 | `ExistingPathOfSameDevice` 释放另一条，仍是一条 |

产品名可用来区分形态：dongle 是 `Wireless mouse 8k dongle-L`，本体是 `ATK F1 ULTIMATE 2.0` / `ATK A9 Air+`。

⚠ **踩过的坑**：曾把 `0x11E4` 当作"同型号另一只鼠标"登记进接收器白名单（§8 的修法），
结果插着充电线时 dongle 与本体各认领一条、ID 又不同 → 设备页出现 `ATK F1 Ultimate 2.0`
和 `ATK F1 Ultimate 2.0 (#2)` 两个条目。**PID 不同不等于设备不同**，判断形态要看产品名与
"充电时 dongle 是否还能应答"。

## 5. 写入边界

- 只会写**一条**固定查询帧 `08 04 …49`，不发任何其它命令
- 该设备独占 `WriteFile` 不可用（0x44oge 源码注释 "Only one that works"），故 `WriteOutput` 失败时回落
  `HidD_SetOutputReport`（非独占、经 HID 类驱动路由，可与 ATK HUB 的 WebHID 驱动同开）
- **会写帧 → 插件默认关闭**（`docs/hardware/safety.md` R1），用户在设置页自行开启
- 连续 3 次查询失败 → 熔断停写 + 递增退避（基类机制），鼠标休眠时的常见表现
- **熔断期开半开探活**（`BreakerProbeInterval` 30 秒，本仓库唯一开启的品牌）：鼠标一天睡几十次，
  只靠递增退避会让用户唤醒后干等 4~5 分钟。间隔是按本机的实测行为定的，别的品牌要开需按
  `dev/runtime-pitfalls.md` §23.1 逐个评估，别照抄这个数字

## 6. 蓝牙模式（备选，零逆向）

同系列鼠标支持蓝牙；切蓝牙连接后电量走标准 BLE GATT 电池服务 `0x180F` / `0x2A19`，
由本应用的 BLE 模块读取，不经本插件。

## 7. 键盘：VIA 读键盘值（page `0xFF60`）

ATK 键盘（A98 Pro，`373B:1152`）走标准 VIA 之上加的一层 `customId` 扩展：

```
[0] 0x00（前导）  [1] 0x02（id_get_keyboard_value）  [2] 0x96（customId）  [3] 0x24（battery）
```

响应实测 `00 02 96 24 64 01 …`：

| 偏移 | 含义 |
|---|---|
| `[0]` | 前导 `0x00`（不是 report ID，解析时跳过） |
| `[1]` | `0x02` 命令回显 |
| `[2]` | `0x96` customId |
| `[3]` | `0x24` 电量键 |
| `[4]` | **电量百分比**（样本 `0x64` = 100） |
| `[5]` | 充电标志：非 0 = 充电中 |

- 解析要求 `[1..3]` 三个命令字节全部对上，带/不带前导 `0x00` 两种偏移都试（`AtkViaCodec.TryParse`）。
- 接口判据：同 VID、`usagePage 0xFF60`、进出等长且 ≥5 字节、report ID 为 `0x00` 或缺省。
- **不要用 op 帧读键盘**：`0xFF60` 接口对 op 帧只回显请求，`data[0]` 恒为 `0x29`、校验和不重算，读出来必然是 41%——本项目踩过的坑。
- 官方客户端在充电时不显示百分比（`power = 0 === batteryCharge ? batteryLevel : undefined`）；本插件照读数显示并标"充电中"。

**型号表**（只按 PID 查，产品串不能当判据：`11E4` 的产品串是 `ATK F1 ULTIMATE 2.0`，不含 "mouse"）：

| PID | 型号 | 链路 |
|---|---|---|
| `0x1152` | ATK A98 Pro | VIA 键盘 |
| `0x11D9` / `0x11E4` | ATK F1 Ultimate 2.0 | op 帧鼠标 |
| `0x1278` / `0x1293` | ATK A9 Air 大师版+ | op 帧鼠标（GEM 接收器 / 有线本体） |

其余 ATK PID 默认按鼠标算，型号名退回产品串。键盘与鼠标共用一个 `Atk` 开关（品牌级），设置页一行。

## 8. 认领判据的坑：接收器白名单漏登记（1.3.0 实机复现）

**现象**：ATK F1 Ultimate 2.0（`373B:11D9`）在设备列表里完全不出现，**日志里连一条失败记录都没有**——
不是"读了读不到"，是 `IsCandidate` 直接返回 false，插件压根没打开过这个接口。同机键盘正常。

**成因**：`0x11D9` / `0x11E4` 没登记进 `IsReceiverPid`，于是掉进「其余 PID 视为有线本体」那条分支：

1. 长度判据 `in >= 17 && out >= 17` 通过（实测就是 17/17），继续往下；
2. `ReceiverOfSameGroupInPlace(0x11D9)` 查不到配对组，走兜底 `return _receiversInPlace.Count > 0`；
3. 而 `_receiversInPlace` 是按「同 VID + `0xFF02`」扫出来的，**接收器自己就在这个集合里**；
4. 兜底返回 true → `!true` → 不认领。**接收器把自己判成了"已被接收器顶替的本体"。**

**修法**：

- 把 `0x11D9` / `0x11E4` 登记为接收器（它们确实回应同一条 17 字节查询帧）；
- 兜底改成排除自身：`_receiversInPlace.Any(pid => pid != bodyPid)`，避免以后再出现"未登记 PID 自我否决"。

| 代码 | `0x11D9` 的 10 个接口中被认领的 |
|---|---|
| 1.3.0 原始 | **0**（鼠标消失） |
| 打补丁后 | **1**（`0xFF02` / 17B in-out，`proto=atk-v1`，读数 80%） |
