# HECATE 漫步者电竞（接收器 35BB:D00B）

> 从 [protocols.md](../protocols.md) 拆出（2026-10-21）。结论均来自真机验证或官方软件抓包；改协议代码前先读本文。

## 1. HECATE 漫步者电竞（接收器 VID_35BB&PID_D00B）—— 贡献者真机声明，本机未复测

### 1.1 实测身份

`HECATE G5M Pro` 走 2.4G 接收器，Windows 枚举出 5 个 HID collection，其中只有厂商自定义集合可用：

| collection | usage | 长度 | 说明 |
|---|---|---|---|
| 键盘 | `0x0001/0x0006` | 21 进 / 2 出 | 系统保护，`CreateFile` 返回 `err=5` |
| 消费者控制 | `0x000C/0x0001` | 3 进 | 打不开 |
| 系统控制 | `0x0001/0x0080` | 2 进 | 打不开 |
| **厂商自定义** | **`0xFF1C/0x0092`** | **64 进 / 64 出，feature = 0** | **电量来源** |

注意 usage_page 不是常见的 `0xFF00`：按 `0xFF00` 过滤会一个接一个地漏掉本设备。

### 1.2 状态帧（report `0x04`，64 字节）

同一集合上每 1~3 秒推两类报文，二者都以 `0x04` 开头：

```
04 AA 00 AA 00 00 00 00 FF 00 …     心跳，不含电量
04 00 00 1A 00 00 00 00 XX YY 00 …  状态帧
```

状态帧字段：`[3] = 0x1A` 是帧标志，`[8] = 电量百分比`，`[9] = 充电标志`。

真机对照（2026-10-18，插 USB 线充电、官方 HECATE Connect 1.1.0.26 显示 22%）：
10 分钟内 `[8]` 由 `0x14` → `0x15` → `0x16`（20 → 21 → 22），单调上升，与官方读数一致。
充电时 `[9]` 恒为 `0x01`；同一只鼠标、同一电量 31% 时拔掉充电线，`[9]` 立刻变成 `0x00`；
2026-10-18 19:14 充满后（`[8]=0x64=100%`），`[9]` 稳定为 `0x02`（20 秒窗口内所有状态帧一致）。
**`[9]` 三态定稿：`0x00`=放电、`0x01`=充电中、`0x02`=满电**（此品牌与英菲克 `0x01=放电` 相反，不可照抄），其余取值一律 `Unknown`。

### 1.3 安全边界

插件 `HecatePlugin` 会向设备写一条 `0x04` 查询帧（`WritesEnabled = true`、`ProbeWrites = true`），
品牌开关 `AppSettings.PluginEnabled["Hecate"]` **默认关闭**，用户在设置页手动开启后才查询；
会写帧故不参与 15 秒快发现，走 ≤60 秒常规节拍。查询帧、实测与离线判定见 §3。
认领同时要求 VID `0x35BB`、PID `0xD00B` 和 usage `0xFF1C/0x0092`。探测 6 秒内没有任何报文则不认领；
只有心跳时认领为休眠，等状态帧再填电量。迈从插件按 VID 排除该接收器，避免把 64 字节厂商接口当成迈从通道。
以上帧样本来自贡献者对 G5M Pro 的抓包，本仓库维护者没有在这台机器上复测。

## 2. HECATE Wireless Receiver（VID_35BB&PID_D3FB）—— 本机实测（2026-10-23）

### 2.1 接口与来源

官方 HECATE Connect 1.0.0.43 的 `Config.ini`（base64 解码）：接收器 `D3FB`、有线鼠标 `D3FD` / `D3FA` / `D3FC`，共 3 个鼠标槽位（MID 3/4/5），配置里有 21 档电池电压表（3050~4110 mV）。接收器产品串 `HECATE Wireless Receiver`，固件版本 `0x0102`。

| collection | usage | 长度 | 说明 |
|---|---|---|---|
| `MI_01&Col05` | `0xFF02/0x0002` | 17 进 / 17 出 | **电量通道**，与派世同款 |
| `MI_01&Col06` | `0xFF04/0x0002` | feature 8 | 未使用 |
| `MI_01&Col02` | `0xFF03/0x0000` | 8 进 | 被动监听 60 秒无报文 |

被动监听 20~120 秒基本收不到报文（仅一次 `08 08 …`，出现在官方软件运行时，含义未知）；关掉所有查询方后再监听 10 分钟，四个可读接口 0 帧，接收器不主动推送，必须查询。

### 2.2 帧（report `0x08`，17 字节，校验同 `PulsarCodec`）

只发这两条，出处是 `pulsar.md` §1 的同族帧；Linux 内核 `hid-kysona`（Kysona M600，6.13 合入）用同样的 `08 03 … 4a` / `08 04 … 49`，每 5 秒轮询。本机 2026-10-23 经用户授权各发一次：

```
STATUS 请求  08 03 00 … 00 4a
STATUS 应答  08 03 00 00 00 01 01 31 af f9 00 00 00 00 00 00 6f   ← [6]=1 鼠标在线
POWER  请求  08 04 00 … 00 49
POWER  应答  08 04 00 00 00 02 32 00 0f 08 00 00 00 00 00 00 fe   ← 0x32=50%、[7]=0、0x0F08=3848 mV
```

3848 mV 落在官方电压表 3840 mV（50%）一档，与 `[6]=50` 自洽。

同日从 Debug 版应用实跑（开 `HecateWireless`）：启动后约 0.4 秒握手成功并认领，设备列表与托盘显示 50%（3853 mV）、放电。

### 2.3 未解决

- **鼠标型号**：协议里没找到型号字段，官方软件也只有 3 个槽位图，没有型号名。本机鼠标是 **G3M Pro 升级版**（用户 2026-10-23 提供的产品图确认），插件名称据此写死为「HECATE G3M Pro 升级版」；接收器 D3FB 是否还对应其它型号未知，要区分需抓官方软件启动握手（本机 USBPcap 未装）。
- **充电位**：`[7]` 是否等于充电中未验证（读数时为 0 = 未充电）；插线充电后看日志 `充电位` 再下结论。
- STATUS `[7..9]` = `31 af f9` 含义未知。

### 2.4 安全边界

插件 `HecateWirelessPlugin`（`PluginEnabled["HecateWireless"]`，默认关）只发上面两条只读查询，走 15 秒发现节拍与 `BatteryPluginBase` 的熔断退避。认领要求 VID `0x35BB`、PID `0xD3FB`、usage page `0xFF02` 和 17 字节双向。迈从插件已按 VID 排除 `0x35BB`。

## 3. 主动查询（2026-10-21 实测定稿）

**命令发现**：Connect 主程序（HECATE Connect.exe，4.3MB）二进制含命令表
`04 00 00 {1A, 18, 19, 17, 16, 0B}`（出现 21 处），`0x1A` 即状态/电量命令。
其余 `16/17/18/19/0B` 语义未查——合规路径是 USBPcap 观察官方软件真实流量，不做盲写
（仓库 safety 记录：2026-10-04 盲扫 255 命令导致键盘与 dongle 断连零收获）。

**查询**：向厂商集合（usage `0xFF1C/0x0092`）写 0x04 输出报告 64 字节
（`04 00 00 1A` + 零填充）；设备即时回 0x04 状态帧（格式同 §1.2）。

**实测**（1.2.2/1.2.3，**Connect 完全关闭**）：5/5 成功、延迟 <1ms，
电量/充电标志与官方 Connect 显示一致；同一时刻官方 Connect 弹"未侦测到设备"也不影响应答。

**意义**：电量读取不再依赖 HECATE Connect。被动模式的离线判定被接收器会话心跳污染
（心跳只证明 Connect 进程活着，与鼠标是否在线无关，见 §1.2 心跳样例），
主动查询的"无应答"才是真实的离线信号。

**插件 v2（HecatePlugin 主动查询模式）**：`WritesEnabled = true`、`ProbeWrites = true`、
`SupportsFastDiscovery = false`（会写帧不进 15 秒档，走 ≤60 秒常规节拍）；
`PollDevice` 每主轮询周期（约 1 分钟）查询一次；Probe 先写查询再听 6 秒。
品牌开关 `AppSettings.PluginEnabled["Hecate"]`
**默认关闭**（会写帧的插件按贡献指南默认关闭），用户在设置页手动开启后生效。

**固有取舍（2026-10-24 明确写出，供使用者预期管理）**：查询节拍跟随主轮询
（约 60 秒一次，与仓库其他查询型插件一致），由此产生两处可感知的延迟，属设计取舍而非缺陷：

1. **切换通道后的显示延迟**：从蓝牙切到 2.4G 后，鼠标输入（光标）秒级恢复，但电量显示
   最长需等约 1 个轮询周期（≤60 秒）——链路本身是秒级就绪的（HID 输入可证），延迟来自
   我们刻意压低查询频率（1 次/分钟 ≈ HECATE Connect 强度的 1/20，对设备更克制）；
2. **关机后的离线延迟**：从 2.4G 关机若有"告别通知帧"则秒级标记离线；从蓝牙关机或
   深度休眠时无该帧，需连续 3 次查询失败（约 3 个轮询周期 ≈ 3 分钟）才标记离线。

如将来需要"拨到哪儿显示哪儿"的即时跟随，可在 BLE 断开事件处触发一次即时查询
（`RequestPollAsync`）解决第 1 条，本插件暂不提高常态轮询频率。

**离线判定（2026-10-23 定稿，GANSS 同款）**：`Offline = { CountPollFailures = false }`（Silence = Zero）。
查询帧本身就是存活探针，不再用沉默判定——Connect 关闭时查询周期 60s ≈ 沉默阈值会造成
在线/离线横跳；Connect 开启时心跳又会污染沉默判定。离线 = 连续 3 次查询无应答
（`MaxFailures = 3`，约 3 个主轮询周期 ≈ 3 分钟），行为确定、零横跳，且与 Connect 开关无关
（心跳刷存活骗不过失败计数）。深度休眠的鼠标也会在约 3 分钟后显示离线，动一下即恢复。
