# HyperX Cloud Flight 2 飓风炫彩版（dongle VID_03F0&PID_0AC1）

2.4G 无线耳机电量接入。**纯被动、零写入**：该 dongle 固件不接受任何输出帧，电量与充电状态都由耳机侧主动推送。

- **设备**：HyperX Cloud Flight 2（国行名"飓风炫彩版"）
- **VID**：`0x03F0`（HP 收购 HyperX 后的 ID）。⚠ **不是**初代 Cloud Flight 的 Kingston `0x0951`
- **PID**：`0x0AC1`（音频端点 `2753` 即此值）；`DeviceModel` 为 `CloudFlight2PCPS`
- **本机验证**：真机验证（放电 40%、充电 94→96% 全程），与官方 NGENUITY 3.1.0 **共存实测无冲突**

## 1. 接口地图

| 接口 | 用途 |
|---|---|
| `MI_03&COL04`（usagePage `0xFF90` / usage `0xFF00`，64B in-out） | **状态流，协议全部在这里** |
| `MI_03&COL01`（`0xFF13` 62B）、`COL02`（`0x000C:0x0001` consumer）、`COL03`（`0x000B:0x0005` headset 按键） | 实测 600 秒零数据，非电量通道 |

认领条件：`VID == 0x03F0 && PID == 0x0AC1 && UsagePage == 0xFF90`——少滤会碰到音频与按键接口。

## 2. 🚧 无法主动查询（已证伪的通道）

- `HidD_SetOutputReport` 在 `FF90` / `FF13` 两个 vendor 接口上均返回 `ERROR_INVALID_FUNCTION`
- `WriteFile` 同步写会阻塞
- 根因：固件**只实现 interrupt OUT 端点**（NGENUITY 的服务正因如此内嵌 libusb 走 interrupt OUT）

hub 的 ZeroMQ 广播（`127.0.0.1:7890` / `6890`）实测收不到数据，**不要再试**。

因此本插件走"被动监听"路线：认领后起后台只读线程，只解析耳机自己推上来的帧。

## 3. 帧结构

| 帧 | 含义 |
|---|---|
| `45 02 …` | 常驻心跳（~71 帧/秒），无电量信息 |
| `FF 01 00×12 <CMD@14> <01 请求 \| 02 确认>` | 官方软件的通信往返帧，同样无电量信息 |
| **`FB 13 00 <pct> <stage>`** | **电量帧**：耳机每变化 1% 推一帧，`[3]` = 百分比 |
| **`FB 09 01` / `FB 09 00`** | **充电状态事件**：插线 / 拔线——充电判定的唯一依据 |
| `FB 0A 00` / `FB 0A 01` | 耳机离线 / 在线 |
| `FB 0B 01` | 电量变化的伴随事件（充放电时都出现，**非充电专属**） |
| `51 02 <pct> 00 1A 00 <mV 大端>` | 开机/重连时的完整状态（44% ↔ 3776 mV） |
| `55 02 B0 04` / `61 02 49 01` | RGB 亮度（1200）/ 设备信息，不采信 |

本机实测样本：

```
放电 40%   fb 13 00 28 5f …      ← [3]=0x28=40
充电 94%   fb 13 00 5e 00 …
充电 95%   fb 13 00 5f 04 …
充电 96%   fb 13 00 60 03 …
插线瞬间   fb 09 01 …
拔线瞬间   fb 09 00 …
```

## 4. ⚠ `FB 13` 的 `[4]` 不是充电标志（已被实测证伪两次）

`[4]` 是**充电阶段编号**，会随充电进程变化：放电 40% 时 `0x5F`、充电 94%/95%/96% 分别是
`0x00` / `0x04` / `0x03`。曾两次误判——先按"`0x00` = 充电"、再按"非 `0x5F` 即充电"，
**都被实机截图推翻**（放电 94% 时 `[4]` 同样 ≠ `0x5F`，界面误显示充电中）。

**正确做法**：

- 电量帧**只更新百分比**，不碰充电状态
- 充电状态**仅认 `FB 09` 事件帧**，插线 / 拔线之后保持不变

官方 NGENUITY 也是这个判定逻辑。回归单测见 `Cf2CodecTests.B2`~`B4`。

## 5. 稀疏推送带来的两个设计约束

1. **认领时通常拿不到读数**：电量每变化 1% 才推一帧，认领窗口内未必有。
   因此认领条件放宽为"见到任何报文即认领"（心跳常驻在跑），读数由后续推送帧补上。
2. **在线状态要靠心跳翻正**：基类只在收到非 null 的被动帧时才把 `IsOnline` 置 true，
   而电量帧可能很久不来。插件在"还没拿到过电量"时用心跳帧回一个"保持原值 + 在线"的信号；
   已经有读数后心跳不再打扰（否则每秒 71 次心跳会刷新 `LastUpdated`，UI 上的"最后更新时间"
   会变成心跳时间，让人误以为电量是刚读到的）。

## 6. 写入边界

**零写入**：`WritesEnabled => false`、`ProbeWrites => false`，只读 `FF90` 口上耳机自己推的帧。
默认开启（纯被动插件不受"会写帧默认关"的约束）。

## 7. 蓝牙模式（备选，零逆向）

CF2 支持蓝牙 5.3，切蓝牙连接后电量走标准 BLE GATT 电池服务 `0x180F` / `0x2A19`，
由本应用的 BLE 模块读取，不经本插件。
