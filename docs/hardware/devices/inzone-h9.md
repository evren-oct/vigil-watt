# 索尼 INZONE H9 II（WH-G900N2，`054C:0FA8`）—— ✅ 插件已落地（会写帧，默认关闭）

> 2026-10-24 真机打通：USBPcap 抓客户端写帧 → 复现查询 → 关掉客户端仍能读（78%、音量 40 对得上）。
> 改协议代码前先读本文；写入边界见 [safety.md](../safety.md)。

## 1. 接口形态（接收器插上时）

| 接口 | usage | 报告 | 用途 |
|---|---|---|---|
| `MI_00` / `MI_03` | USB Audio | — | 索尼驱动 `INZONEHS` 接管，Chat / Game 两个音频端点 |
| `MI_05` COL01 | `0xFF13/0x01` | in `0x07` / out `0x06`，各 61B | 厂商通道，**客户端完全不用**（监听 5 分钟零帧） |
| `MI_05` COL03 | `0xFF04/0x01` | in/out **同为 report ID `0x02`**，各 64B | **电量查询走这条** |
| `MI_05` COL02/04 | `0x0C` / `0x0B` | 2B | 按键/电话语义 |

## 2. 传输方式（这条决定了成败）

必须走**控制传输 SET_REPORT**（`HidD_SetOutputReport`）。

> ⚠️ 用中断 OUT 端点（`WriteFile` / hidapi 的 `write`）写同样的 64 字节，设备会**原样回显**：
> 把电量字节改成 `0x10`，回来的就是 `0x10`。看上去像"有应答"，实际是假阳性。
> 这个坑让第一轮排查全部作废——**认设备行为之前，先确认走的是哪条传输**。

## 3. 请求帧（64 字节）

```
02 0C 01 00 FC 08 96 C3 | cls | id | 01 01 00 | chk | 00 ×50
```

| 字段 | 说明 |
|---|---|
| `02` | report ID（in/out 共用） |
| `0C 01 00 FC 08 96 C3` | 固定头 |
| `cls` | `0x41` → 响应 class `0x14`；`0x21` → 响应 class `0x12` |
| `id` | 命令号 |
| `01 01 00` | 固定 |
| `chk` | `(cls==0x41 ? 0x9C : 0x7C) + id`（真机反推，样本有限，只用于固定命令） |
| 其余 | 全 0 |

已确认的命令：

| 请求 | 响应 | 内容 |
|---|---|---|
| `41 04` | `14 04` | **电量**：payload `00 <charging> <level> <chk>`，level 在 **`frame[14]`**，充电标志 `frame[13]` |
| `41 06` | `14 06` | 状态：`00 05 00 <level> 00 1E FF <vol> 00 FF …`，电量 `[15]`、**音量 `[19]`** |
| `41 02` | `14 02` | 设备信息（序列号 ASCII `2001258`） |
| `41 03` | `14 03` | 未知，含 `0x85` |
| `21 01` | `12 01` | 状态总览，含 `0x7E` |

注意：**电量偏移随命令不同**（`14/04` 在 `[14]`，`14/06` 在 `[15]`），别写成一个通用偏移。

## 4. 响应帧

```
02 0E 04 FF 0B 00 96 C3 | 14 | 04 | 10 01 | 00 00 4E D0 | … | 55 5D 20 14
                         cls   id   src      payload
```

- `frame[10]`：`0x10` = 查询应答，`0xA0` = 设备通知，`0x20` = 设置下发。
- 尾部 4 字节按 class 固定（`0x14` → `55 5D 20 14`，`0x12` → `09 A6 11 08`），**不是逐帧校验**。

## 6. 写入安全

- 插件会写帧 → 默认关闭：`AppSettings.PluginEnabled["SonyInzone"] = false`，用户开开关 = 授权。
- 只发 `41 04` 一条查询帧，每轮 1 帧、失败重试由基类冷却兜住（8 秒）。
- **不要盲写 `0xFF04`**：`0x20` 类是设置下发（音量/EQ），写错会改真实设置。
