# GANSS GS3104T-Pro 2.4G 电量

> 接收器 `VID_05AC&PID_024F`。帧样本来自贡献者 luze258 的抓包（PR #15），**本仓库维护者没有这台设备，未复测**。
> 索引与其它设备见 [protocols.md](protocols.md) §11。

## 1. 实测身份

接收器枚举出多个 HID collection，电量只在厂商自定义集合上，且该集合**不是** `mi_00`。认领必须同时满足下表全部条件（`GanssCodec.IsSupportedInterface`）：

| 判据 | 取值 |
|---|---|
| VID / PID | `0x05AC` / `0x024F` |
| **接口路径段 或 产品名** | 路径含 `&mi_03#`（大小写不敏感，`&mi_030#` 不命中）**或** 产品名含 `GANSS` / `GS3104` |
| usage page / usage | `0xFF60` / `0x0061` |
| 输入 / 输出报告长度 | 33 / 33 |
| 输出报告 ID | `0`（枚举不到时为 `null`，同样不认领） |

前四条里只有"接口路径段"是枚举顺序的偶然产物，所以它和产品名做成**二选一**：产品名是设备自己声明的身份，接口编号漂移时靠它兜底。其余三条（usage、长度、reportId）**不参与兜底**，产品名再像也不能绕过——这条边界由 `ProductNameDoesNotOverrideUsageLengthOrReportId` 守着。

同一接收器上 `&mi_00#` / `&mi_04#` 都拿不到电量，所以不能放宽成"任意 mi_ 号"；放宽的只能是"有产品名做第二证据"这一种情形。整条判据仍比其它品牌都窄，是贡献者在本机逐集合试出来的结果。

**产品名兜底的前提是设备真的报了名字。** 如果接收器自报的是 `2.4G Wireless Receiver` 这类通用串，这条分支永远不会命中，行为与没有它完全一致。实际报什么尚未确认，见 §6.1 第 1 条。

判据越窄，静默失败越难诊断。因此 VID/PID 命中但其余判据不符时，插件会打一条 10 分钟节流的 Info（带实际 usage、报告长度、`outId` 和接口路径），用来回答"为什么我的键盘没出现"。

## 2. 查询帧（33 字节）

```
00 20 01 00 00 … 00 21
```

`[0]` 是 HID report ID（恒 0），`[1]=0x20`、`[2]=0x01` 是命令，`[32]` 是校验和。**校验和 = 前 32 字节求和取低字节**，所以固定查询帧的校验和恒为 `0x21`（`0x20 + 0x01`）。

这是**写帧**：不主动发这一帧，接收器不会推电量。发送后 750 毫秒窗口内读响应，窗口内解析不出有效帧就判本轮失败。

## 3. 响应解析

```
20 01 00 61 00 … 00 82
```

- `[0]=0x20`、`[1]=0x01`、`[2]=0x00` 是响应头，三者不符即丢弃。
- **`[3]` 就是电量百分比**。贡献者样本 `[3]=0x61` 即 97%。
- 校验和 = **该帧除末字节外所有字节求和取低字节**（33 字节帧即前 32 字节；剥掉 report ID 后的 32 字节 payload 即前 31 字节），不符即丢弃。
- 长度接受 32（纯 payload）与 33（带 report ID 前缀且前缀为 0）两种；33 字节时先剥掉首字节。
- **`0` 在协议层就判无效**：键盘休眠/关机时接收器会回 0，与"真的 0%"无法区分，一律丢弃。
- **`1` 仍按公共下界判无效**：插件不覆写 `BatteryReadingFilter.MinValidPercent`（默认 2），与其它品牌一致。本插件没有任何证据证明设备会把 `1` 当作真实电量报出来，宁可不显示也不采信疑似占位值。

## 4. 安全边界

- **会写帧**，因此 `AppSettings.PluginEnabled["Ganss"]` 默认 `false`。开插件即授权写帧，没有第二个写入许可（[safety.md](safety.md) §3）。
- 写点有纵深防御：`QueryAsync` 发帧前再次校验插件开关**和**完整接口判据（`WritesEnabled && IsCandidate(handle.Info)`），避免同 VID/PID 的其它集合被当成厂商通道。
- 不进 15 秒发现节拍（未覆盖 `SupportsFastDiscovery` / `SupportsDiscoveryProbe`）：未认领时不会把查询帧抬到约每 15 秒一次，打开后只跟 60 秒主轮询。
- 熔断与退避沿用基类：连续 3 次无应答 → 停写 + 标离线，退避 30 秒起、封顶 5 分钟。
- `Offline.CountPollFailures = false`：轮询失败不计入基类的自动记账，改由插件在"确实发过帧且没解析出读数"时调 `ReportPollFailure` 自己报账——`null` 在未开写入/熔断中时也会出现，插件比基类更清楚这一轮到底发没发帧。
- 充电状态恒为 `ChargingState.Unknown`：协议里没有充电语义，不猜。

## 5. 未验证项

- **只验证过 2.4G 接收器**。蓝牙通道走通用 GATT 电量服务，与本协议无关，本仓库没有单独验证。
- **充电状态未知**：抓到的报文里没有可解释为充电标志的字节，界面只会显示电量。
- **`1%` 的语义未验证**：设备在低电量段是否会报 `1`、以及它是否只是休眠占位，都没有样本。当前按公共下界当作无效值丢弃。
- **`0x05AC` 是 USB-IF 分配给 Apple 的厂商号**，出现在 GANSS 键盘上属于接收器固件沿用的现成 VID，不表示任何 Apple 关联。贡献者样本只有一台设备，无法确认 GS3104T-Pro 的其它批次/固件是否同号。同 VID/PID 的外设目前只有接口判据这一道屏障，误认领的可能与后果见 §6。
- **`&mi_03#` 已降级为二选一**：与产品名含 `GANSS` / `GS3104` 互为替代。枚举顺序漂移时，设备只要自报品牌名就仍能认领；产品名是通用串时退回硬绑，仍会认领失败。见 §6.1。
- 帧样本与校验和规则均来自贡献者抓包，本仓库维护者**没有**这台设备，未复测。

## 6. 认领判据的风险与待验证（CR-66）

贡献者只在一台机器上抓过包。五条判据里**四条描述的是"任何一台 VIA 风格键盘"，唯一能区分 GANSS 的那条是枚举顺序**——这是本插件最大的不确定来源。

| 判据 | 实际证明什么 | 唯一性 |
|---|---|---|
| `05AC:024F` | 借用 Apple 号段的 VID/PID（`0x024F` 落在 Apple 内置键盘号段内） | 不唯一，廉价接收器沿用方案商默认描述符很常见 |
| `0xFF60 / 0x0061` | QMK/VIA raw HID 的标准 usage 对 | 标准值，不唯一 |
| 33 字节 / reportId 0 | VIA 标准的 32 字节 payload + 0 号报文 | 标准值，不唯一 |
| `&mi_03#` | 该机器上第 4 个接口 | 枚举顺序产物，**最不稳** |
| 产品名含 `GANSS` / `GS3104` | 设备自己声明的品牌 | 设备真报名字时才成立，**未确认** |

两个方向的风险不对称：

- **假阴性（概率高、危害低）**：换固件、换批次、换 USB 口导致 `mi` 号变化 → 认领不上，用户只看到键盘不显示。已有两条缓冲：10 分钟节流的诊断日志（`GANSS 接口判据不符，未认领`），以及**产品名兜底**（`&mi_03#` 与产品名二选一）。兜底只在设备确实自报品牌名时生效。
- **假阳性（概率低、危害高）**：另一台抄了 `05AC:024F` 的 VIA 键盘，满足 usage + 长度 + `mi_03`，或产品名里恰好含 `GANSS` → 被认领并**写入**查询帧。默认关闭与熔断只能限制写入频率，不能消除这一次写入。产品名兜底会让"mi 号不同"的这类设备也有机会被认领，收益是救回固件漂移的自家键盘，代价是假阳性面略微变大——这是当前明确的取舍。

### 6.1 验证清单（需要有设备的人执行）

1. **确认设备自报的产品名与厂商名**。日志开 Debug 档启动一次，看 `HID 扫描完成` 前后的元数据；或跑 `scripts/probe-hid-caps.py`。代码里已经有产品名兜底（`LooksLikeGanss` 匹配 `GANSS` / `GS3104`），但**是否命中取决于真实字符串**：若报的是 `2.4G Wireless Receiver` 这类通用串，这条分支等于不存在，需要把匹配词换成实际值。
2. **抓 GANSS 官方配置软件的 HID 通信**（手法见 [debugging.md](debugging.md) §1）。重点回答两件事：
   - 官方软件**用什么定位接口**。它绝不会用 `mi_03`，大概率是按 usage + 长度遍历，或按产品名匹配。
   - 有没有**取设备信息的命令**。响应帧 `20 01 00 xx` 是"命令 + 子命令 + 状态 + 值"的结构，说明这是一族命令而不是孤零零一条；`0x02` / `0x03` 很可能是型号 / 固件版本。取得到型号，身份问题就当场解决。
3. **换 USB 口、换机器、升级固件后复测 `mi` 号是否仍为 03**。这一条直接决定假阴性概率。
4. 若确认是 QMK/VIA 系固件，可试 VIA 标准命令 `0x01`（取协议版本）/ `0x02`（取键盘 ID）。**注意**：贡献者的帧用的是 `0x20`，在 VIA 命令范围之外，不能先假设标准命令可用。

验证结论回填本文与 BACKLOG **CR-66**，不要只写在 PR 评论里。

## 7. 同一协议的第二个品牌：狼蛛 F108 Pro（2026-10-21 真机验证）

接收器自报 `F108Pro Dongle`（厂商串为空），五条判据与 GS3104T-Pro **逐条一致**：
`05AC:024F` / `&mi_03#` / `0xFF60:0x0061` / 33-33 / reportId 0。所以 HID 层无法区分品牌，
唯一可用的区分证据是**产品名**：含 `F108` → 设备行显示 `狼蛛 F108 Pro`，否则 `GANSS GS3104T-Pro`。
不新开插件（两个插件抢同一接口只会打架），开关仍是 `Ganss`。

```
查询 00 20 01 00 … 21   →  应答 00 20 01 00 64 … 85   （[3]=0x64=100%）
```

实测：同一台机器先后读到 `100%` 与 `99%`（间隔十几分钟，说明是实时值）。
**空闲时可能连续多次零应答**（键盘休眠），09:24–09:29 四次失败后 09:30:11 一次成功；
不要用单次超时判断协议不对。
