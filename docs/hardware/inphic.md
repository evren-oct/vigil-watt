# 英菲克（ZHEN 1D57:FA65 / IN9 248A:5B2F）

> 从 [protocols.md](protocols.md) 拆出（2026-10-21）。结论均来自真机验证或官方软件抓包；改协议代码前先读本文。
> 两台的号段与机制都不一样，**不能互相复用**：ZHEN 是零写入被动帧，IN9 要先写一条刷新请求才拿得到新值。

## 1. 英菲克 ZHEN（接收器 VID_1D57&PID_FA65）—— ✅ 被动电量帧已确认

### 1.1 实测身份与状态帧

英菲克官方 ZHEN 网页驱动在 2.4G 模式下通过 WebHID 连接。设备名为 `Inphic KP 8K`，VID/PID 为 `1D57:FA65`。Windows 将它枚举成多个 HID collection：系统控制 `0x0001/0x0080`（输入长度 2）、consumer `0x000C/0x0001`（长度 3）、电量输入 `0xFF00/0x0001`（输入长度 5，Report ID `0x03`）和厂商输出接口 `0xFF01/0x0002`（双向长度 64，Report ID `0x04`）。电量插件必须匹配 `0xFF00/0x0001` 的输入 collection；不能按网页显示的系统控制 collection 来筛选。

report ID `0x03` 的输入数据为 4 字节：

```
76 41 <状态> <电量百分比>
```

真机样本 `76 41 01 55` 与官方驱动显示的 **85% 放电**一致，因此 `[3]` 是百分比，`[2]=0x01` 表示放电。第二轮充电实测期间，状态变为 `0x03`（例如 `76 41 03 54`，84%），因此 `0x03` 表示充电；接线测试之后又观察到 `76 41 01 57`（87%），表明已回到放电状态。代码将 `0x01` 解析为放电、`0x03` 解析为充电，其余标志仍保留为 `Unknown`。

### 1.2 安全边界

插件只被动读取 report `0x03`，不发送官方网页驱动中的 report `0x04` 命令。样本中 report `0x03` 约每 2 秒到达；无报告时以 90 秒静默作为离线兜底。迈从插件也必须按 VID 排除该接收器，避免把其 64 字节输出 collection 当成迈从接口。充电状态已通过接线实测确认；暂未采集满电状态编码。

## 2. 英菲克 IN9（接收器 VID_248A&PID_5B2F）—— feature `0x0C` 快照 + 刷新请求

> 来源：[issue #40](https://github.com/evren-oct/vigil-watt/issues/40)（@YyingnLL）的 USBPcap 抓包与真机验证；2026-10-31 维护者真机补抓 `in9.pcapng` 与 `in9多次重启软件保持报文正常.pcapng`，复测刷新序列。

### 2.1 设备与接口

电量只在 `MI_01 Col04`（usage `0xFF00/0x0001`，**仅 feature 33 字节**）；`MI_02`（`0xFFEF`，64/64/64）是主厂商管道、本协议未用，`MI_01 Col06`（输入 33）实测静音。`248A` 是 Telink 通用号段，判据须带 usage 与 feature 长度（见 [protocols.md](protocols.md) §2）。插充电线后鼠标切换成独立设备 **`248A:5B2E`**。

### 2.2 `0x0C` 报文与刷新机制

`HidD_GetFeature(0x0C)` 返回 33 字节，首字节回显 report ID：

| 偏移 | 值 | 含义 |
|---|---|---|
| 0 | `0x0C` | report ID |
| 8–12 | `4D 39 30 39 34` | 型号串 `M9094` |
| 18 | 百分比 | 电量百分比；`0` 是还没回填的占位值，必须当无效重读。样本见过 `0x51`（81%）、`0x57`（87%）、`0x5A`（90%）、`0x5B`（91%）；插充电器后固定 `0x64`（100%），不可信 |
| 19 | `0x00` / `0x01` | 充电位：`0x01` = 插着充电器（2026-10-31 充电抓包确认），此时电量不上报 |
| 21 | 状态 | 链路状态：`0x01` 放电 / `0x03` 充电 / `0x00` 未知；充电时仍可能保持 `0x01`，不能单独判充电 |

真机样本（连续 6 次读取完全一致）：

```
0C 01 20 00 01 01 10 00 4D 39 30 39 34 01 00 25 14 FF 51 00 FF 01 00 00 B7 B7 62 38 FF C7 67 09 6D
```

`[15..16]`（`0x25 0x14`）疑似 DPI 档位或回报率，未证实，不参与解析。

**这是「先写请求、再读结果」——刷新帧是硬前置，不发就是全 0。** 只读轮询时电量长期不变（实测 16 小时停在 79%），新品接收器则直接回全 0；只有官方驱动 `Inphic IN9 GM.exe` 发出刷新帧后才跳到真实值。抓到的控制传输是 `SET_REPORT wValue=0x030C wLength=33`，数据 `0C 01 20 00 <序号>` + 28 个 0（样本里序号为 `02`）；读回的响应由接收器回填型号与电量。

**`[4]` 是递增序号，不是固定命令字**（真机 2026-10-30 抓包更正早期结论）：官方驱动每发一条就 +1（`01`→`02`→`03`…），像个时间戳；设备只在它**变化**时才做一次查询，重复发同一个值会被当成重复请求丢掉，并把寄存器打成全 0。早期实现的固定 `02` 在设备记住的上一条也是 `02` 时第一条就失败，之后每轮全 0——这才是"刷新不出来"的真正原因。写入的是同一个寄存器，读回时 `[4]` 显示的就是刚写进去的值，别当成回显。

**官方驱动每次启动都从 `01` 重来，不持久化序号**（2026-10-31 抓包，三次重启样本）：它同样会遇到"上一条正好是 01"的情况，此时 `01` 立刻回全 0，官方驱动约 15 ms 后就改发 `02` 并拿到真实帧。所以重启后仍能正常的关键不是记住序号，而是**读到全 0 就换下一个序号重发**。插件据此实现：序号 1..255 循环跳过 0（首值 1），首次写后等 30 ms 读；无效就隔 500 ms 换号重写一次（单轮最多 2 条，符合 [safety.md](safety.md) §3 规则 4），仍无效再纯重读 80/160 ms 等回填。**只重读不换号永远等不到回填**——重复值被设备直接丢掉。

写完到寄存器成形之间有空档（真机 2026-10-29：刷新后 4 ms 就读，`[18]` 还是 `0`，被当成 0% 进了列表并触发低电量提醒）。**探测阶段同样先刷新**，否则空寄存器会让设备永远认领不到。

2026-10-31 的 `in9.pcapng` 是旧构建（固定 `02`）的现场：0–68 s 每轮发 `02` 都读到全 0；72 s 打开官方驱动后 `01→02→03→04→05` 把寄存器填成 91%，应用随后读到快照；102.9 s 应用再发一次 `02`，寄存器又被清回全 0。同一晚 `in9多次重启软件保持报文正常.pcapng` 里，官方三次重启均从 `01` 起，失败即换 `02`。

2026-10-31 的 `in9后面插上充电器显示100%了.pcapng`（88 帧）里，87% 时 `[19]=0x00`；插充电器后 `[18]` 跳到 `0x64`（100%）、`[19]=0x01`，`[21]` 仍是 `0x01`，全程也没枚举 `5B2E`（尾部充电口不走数据）。所以充电判据只能用 `[19]`，且充电期间不显示电量。

> ⚠️ **写错会清空寄存器**：一次 `SetFeature(0x0C, 全 0)` 就让 `GetFeature` 返回全 0，靠打开官方驱动或拔插恢复。插件只发这条抓包帧，全 0 响应一律判无效。

### 2.3 充电与离线

- **充电**：插线后 `5B2F` **仍然在位、PID 不变**，判据看报文 `[19]`（`0x01` = 插着充电器，2026-10-31 充电抓包确认）；`[21]` 在充电时仍报 `0x01`，不能用来判。`5B2E`（有线本体）只在不同批次确实枚举出本体时兜底，别指望它一定出现。
  **充电期间只报充电状态、不报电量**：此时的百分比是缓存/换算值，不可信，当成真实电量展示会误导（低电量提醒也会跟着误报）。
- **离线不可靠**：关机后接收器仍用缓存值应答，只能靠接口消失判定，故插件不按轮询空读记账。

### 2.4 实现

`InphicIn9Plugin` 与 ZHEN 共用 `PluginEnabled["Inphic"]` 一行开关（`Name` 相同，设置页按 `Name` 去重），但必须独立成类：IN9 会写帧，ZHEN 零写入且要进 15 秒发现节拍。认领 `248A:5B2F` + `0xFF00/0x0001` + `FeatureReportLength == 33`；每轮 `CanWrite` 为真时发刷新帧（序号 1..255、首值 1，全 0 就换号重写一次）再 `GetFeature`，取 `[18]`/`[19]`/`[21]`，全 0 / 越界 / 截断一律丢弃；`[19]=0x01` 时只报充电中、不上报百分比；不参与 15 秒节拍，熔断走基类。开关**默认关闭**（共用行里有会写帧的设备，见 [safety.md](safety.md) §3.1 硬约束 2）。
