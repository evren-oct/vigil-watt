# MCHOSE V9 Pro 耳机 2.4G 电量

> 接收器 `VID_291D&PID_385D`。帧样本来自贡献者 luze258 在官方 MCHOSE HUB 显示 100% 时的 USB 抓包（PR #15），**本仓库维护者没有这台设备，未复测**。
> 索引与其它设备见 [protocols.md](protocols.md)；同品牌的键盘/鼠标链路见 [mchose.md](mchose.md) §1、§1.6。

## 1. 实测身份

同一接收器枚举出多个 HID collection，电量只在 `mi_00` 的第 5 个 collection 上。认领必须同时满足下表全部条件（`MchoseV9ProCodec.IsSupportedInterface`）：

| 判据 | 取值 |
|---|---|
| VID / PID | `0x291D` / `0x385D` |
| 接口路径段 | 含 `&mi_00&col05#`（大小写不敏感；`&col050#` 不命中） |
| usage page / usage | `0xFF90` / `0x0001` |
| 输入 / 输出报告长度 | 64 / 64（**已含 report ID，不加前置零**） |
| feature 报告长度 | `0`（有 feature 通道说明是另一个集合） |
| 输出报告 ID | `0x55`（枚举不到时为 `null`，同样不认领） |

与 GANSS（[ganss.md](ganss.md) §1）不同，这里**没有**"接口编号可能漂移"的兜底：贡献者只在一台机器上抓到过 `col05`，既没有产品名证据也没有第二条样本，所以按硬判据收窄——认不到就认不到，不拿"放宽"去换假阳性。

接口去向由 `MchoseInterfaceClassifier.Classify` 统一判定（键盘 V1 / 鼠标 V2 / 耳机 / 不是迈从），**耳机必须排在最前**：它也是 64 字节输出，落到鼠标分支会收到 `0x11/0x06` 触发帧。

## 2. 查询帧（64 字节）

```
55 65 01 00 00 … 00
```

`[0]=0x55` 是 HID report ID，`[1]=0x65`、`[2]=0x01` 是命令，其余 61 字节为 0。响应约 27 毫秒后到达。

**这是写帧**：不主动发这一帧，接收器不会推电量。发完 750 毫秒窗口内读响应，窗口内解析不出有效帧即判本轮失败。

## 3. 响应解析

```
55 65 64 02 00 … 00
```

- `[0]=0x55`、`[1]=0x65` 是响应头，不符即丢弃；**`[2]` 就是电量百分比**（样本 `0x64` = 100%）。
- `[2]` 为 `0` 或 `> 100` 在协议层就判无效：耳机休眠/关机时接收器会回 0，与"真的 0%"无法区分。
- `[3]` 样本为 `0x02`，含义未校准，**不解释为充电**，充电状态恒为 `Unknown`。
- 长度必须是 64。带前置零的 65 字节报文（GANSS 那种布局）不接受。
- **回显保护**：有的接收器会把主机写入回显到输入队列，而查询帧 `55 65 01 …` 本身能解析成 1%。整帧等于查询帧时丢弃。代价是"真 1% 且 `[3]` 恰为 0"的响应也会被丢，见 §5。
- **`1` 仍按公共下界判无效**：插件不覆写 `BatteryReadingFilter.MinValidPercent`（默认 2）。理由与 GANSS 一致——没有任何证据证明设备会把 `1` 当真实电量报出来，宁可不显示。

## 4. 安全边界

- **会写帧**，因此走 `AppSettings.PluginEnabled["Mchose"]`，默认 `false`。**没有单独的 `MchoseV9Pro` 开关**：设置页是品牌级开关（`AGENTS.md` §9），一个品牌一行，型号差异在插件内部消化；开「迈从」即授权向键盘、鼠标、耳机三类设备发送各自工作所需的帧。
- 实现位置：帧与偏移在 `Plugins/Mchose/specs/mchose.protocols.json` 的 `headset-v9`（解释器执行，`MchoseV9ProCodec` 只是薄壳、保留接口判据与既有断言），接口分流在 `MchoseInterfaceClassifier`，I/O 由 `Plugins/Protocol/` 的 `QueryRunner` 负责，协议名 `headset-v9`，图标由 `ResolveKind` 给 `Headset`。
- 参与 15 秒发现节拍（`SupportsDiscoveryProbe` 是插件级属性，无法按协议分档）：未认领时每拍最多 1 条查询帧，比键盘链路（1 条会话帧 + 最多 2 条查询）更省。耳机不在位时该接口仍然存在（接收器插着），会按拍重探。
- 熔断与退避沿用基类：连续 3 次无应答 → 停写 + 标离线，退避 30 秒起、封顶 5 分钟。`Offline.CountPollFailures = false`，由 `PollDevice` 在确实发过帧的分支自己报账。
- 无应答只在状态变化时记一条 Debug（`Log.Once` + 成功即复位），不逐次记 WARN。

## 5. 未验证项

- **只在一个电量点验证过（100%）**：非满电时 `[2]` 是否线性变化、低电量段会不会出现占位值，都没有样本。
- **充电状态未知**：`[3]` 的 `0x02` 未校准，界面只显示电量，不显示充电中/已充满。
- **`1%` 不显示**：协议层接受 1，公共下界（2）会把它判为无效值。与 GANSS 同一口径。
- **回显保护有代价**：若设备真的回 `55 65 01 00 …`（1% 且 `[3]=0`），会被当成回显丢弃。
- **型号名写死**：`291D:385D` 只对应已验证的 V9 Pro，显示名固定为「迈从 V9 Pro」；V9、Pro2、Turbo 等型号是否兼容**不做推断**。
- **蓝牙通道**：贡献者用经典蓝牙 HFP 系统属性读到过 100%，属通用路径，不新增私有插件，本仓库未验证。
- 帧样本来自贡献者抓包，本仓库维护者**没有**这台设备，未复测。
