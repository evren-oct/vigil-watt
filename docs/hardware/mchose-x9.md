# MCHOSE X9 耳机 2.4G 电量

> 接收器 `VID_3837&PID_6045`。**帧结构与 V9 Pro 完全相同，但 VID 与迈从键鼠同号段**——分类器必须把它排在鼠标分支之前。
> 协议由贡献者 Gpan666 从官方 M HUB 前端（公开 CDN 上未混淆的 Vue bundle）解出，并在本机 Python 探针与 VigilWatt 1.2.1 本地构建上实测；本仓库代码由 AI 辅助编写，只做到编译 + 单测通过，维护者未复测。
> 索引与其它设备见 [protocols.md](protocols.md) §14；同品牌键鼠链路见 §1、§1.6，V9 Pro 见 [mchose-v9-pro.md](mchose-v9-pro.md)。

## 1. 实测身份

同一个接收器枚举出 6 个 HID collection，电量只在 `mi_00` 的第 5 个 collection 上。认领必须同时满足下表全部条件（`MchoseX9Codec.IsSupportedInterface`）：

| 判据 | 取值 |
|---|---|
| VID / PID | `0x3837` / `0x6045` |
| 接口路径段 | 含 `&mi_00&col05#`（大小写不敏感；`&col050#` 不命中） |
| usage page / usage | `0xFF90` / `0x0001` |
| 输入 / 输出报告长度 | 64 / 64（**已含 report ID，不加前置零**） |
| feature 报告长度 | `0` |
| 输出报告 ID | `0x55`（枚举不到时为 `null`，不认领） |

同接收器上的其它集合全部不认：

| 路径段 | usage page | 长度 | 用途 |
|---|---|---|---|
| `&mi_00&col01#` | `0xFF21` | in 2 / out 16 / feat 16 | 控制通道 |
| `&mi_00&col02#` | `0xFF22` | feat 64 | 固件版本（`AA 01` 查询） |
| `&mi_00&col03#` | `0x000C` | in 3 | consumer |
| `&mi_00&col04#` | `0x000B` | 3 / 3 | 其它 |
| `&mi_00&col06#` | `0xFF82` | 64 / 64 | 另一条 64 字节厂商通道（report `0x41`） |

**分流顺序是硬约束**：X9 的 VID 是 `0x3837`，和 G87 V2 / A7 V2 Pro 接收器同一号段，而它的输出也是 64 字节。`MchoseInterfaceClassifier.Classify` 必须把 X9 判定插在「≥60 字节只走鼠标」之前，否则会往耳机发 `0x11/0x06` 触发帧。

## 2. 查询帧（64 字节）

```
55 65 01 00 00 … 00
```

`[0]=0x55` 是 HID report ID，`[1]=0x65`、`[2]=0x01` 是命令，其余 61 字节为 0。官方是 WebHID 的 `sendReport(0x55, [0x65, 0x01, 0×61])`，线上首字节才是 `0x55`。

**这是写帧**：不主动发这一帧，接收器不会推电量。发完 750 毫秒窗口内读响应，窗口内解析不出有效帧即判本轮失败。

## 3. 响应解析

实测样本（90% 放电）：

```
55 65 5A 02 00 … 00
```

| 偏移 | 含义 |
|---|---|
| `[0]` | `0x55` 响应头 |
| `[1]` | `0x65` 命令回显 |
| `[2]` | **电量百分比**（样本 `0x5A` = 90） |
| `[3]` | 状态字节，见下表 |

| 状态字节 | 含义 | 映射 |
|---|---|---|
| `0x02` | 放电 | `Discharging` |
| `0x03` | 充电中 | `Charging` |
| `0x04` | 已充满 | `Full` |
| `0x1A` | 休眠 | `Discharging` |
| 其它 | 未收录 | `Unknown` |

- `[2]` 为 `0` 或 `> 100` 在协议层判无效：耳机休眠/关机时接收器会回 0，与"真的 0%"无法区分。
- 长度必须是 64。带前置零的 65 字节报文（GANSS 那种布局）不接受。
- **回显保护**：有的接收器会把主机写入回显到输入队列，而查询帧 `55 65 01 …` 本身能解析成 1%。整帧等于查询帧时丢弃。
- **官方精度是 10% 一档**：M HUB 的 store 里记 `batteryPrecision: 10`，所以读数会是 90、80 这类整十值，不是逐点百分比。

## 4. 安全边界

- **会写帧**，因此走 `AppSettings.PluginEnabled["Mchose"]`，默认 `false`。**没有单独的 `MchoseX9` 开关**：设置页是品牌级开关（`AGENTS.md` §9），开「迈从」即授权向键盘、鼠标、V9 Pro、X9 发送各自工作所需的帧。
- 实现位置：帧结构在 `MchoseX9Codec`（纯函数，有单测），接口分流在 `MchoseInterfaceClassifier`，I/O 在 `MchosePlugin`（`TryHeadsetX9` / `PollHeadsetX9` / `QueryHeadsetX9`），协议名 `headset-x9`，图标由 `ResolveKind` 给 `Headset`。
- 参与 15 秒发现节拍（`SupportsDiscoveryProbe` 是插件级属性）：未认领时每拍最多 1 条查询帧。耳机不在位时该接口仍然存在（接收器插着），会按拍重探。
- 熔断与退避沿用基类：连续 3 次无应答 → 停写 + 标离线，退避 30 秒起、封顶 5 分钟。`Offline.CountPollFailures = false`，由 `PollDevice` 在确实发过帧的分支自己报账。
- 无应答只在状态变化时记一条 Debug（`Log.Once` + 成功即复位），不逐次记 WARN。

## 5. 未验证项

- **状态字节只实测过 `0x02`（放电）**：`0x03` / `0x04` / `0x1A` 的语义来自官方前端代码，本机未逐一接线验证。
- **`0x1A`（休眠）映射为放电**：这是"不在充电"的保守解释，不是实测结论。
- **只验证过 80% / 90% 两个点**：低电量段会不会出现占位值没有样本；官方 10% 一档的精度意味着读数不会连续变化。
- **型号名写死**：`3837:6045` 只对应已验证的 X9，显示名固定为「迈从 X9」；X9 Pro、其它配色是否同 PID **不做推断**。
- 本仓库代码由 AI 辅助编写，只做到编译 + 单测通过；协议依据是贡献者本机实测与官方前端代码，维护者未复测。
