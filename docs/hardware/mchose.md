# 迈从 MCHOSE（G87 键盘 / 0x4D 鼠标通道 / Gmouse G3 V2 / 耳机）

> 从 [protocols.md](protocols.md) 拆出（2026-10-21）。结论均来自真机验证或官方软件抓包；改协议代码前先读本文。
> **设备清单、协议族判定、鼠标 DPI/回报率取数口径**见 [mchose-catalog.md](mchose-catalog.md)（2026-11-01 逆向，静态分析）。

## 1. 迈从键盘 G87（dongle VID_41E4&PID_2001）—— ✅ 已打通，应用在用

> `41E4:2001` 是这颗键盘的**接收器**，已在 `mchose-catalog.json` 的 `transports` 里登记为 `dongle-wireless`。
> 认领到它就把链路推断为 2.4G（`Inferred`，不是设备上报）：主机读的是接收器通道，有线数据不经过 dongle。
> 键盘本体 PID 未登记，插线时保持"未知"——不拿接收器在位去猜本体链路。

### 1.1 接口地图

| 接口 | 用途 |
|---|---|
| MI_00 | 标准键盘（系统保护，打不开，按键走这里） |
| MI_01&Col01（usagePage 0xFF02，in/out=20 字节） | **配置/电量通道**，report ID 0x13 |
| MI_01&Col02/Col03/Col05 | consumer / system / mouse，无输出通道，别碰 |
| MI_01&Col06（usagePage 0xFF04，feature=8） | "邮箱"，**不是电量**（不是电量通道，别拿它当电池） |

### 1.2 帧格式（20 字节 output report，report ID 0x13）

```
[0]=0x13  [1]=命令  [2]=参数  [3..18]=0x00  [19]=sum(前19字节) & 0xFF
```

校验就是前 19 字节简单求和截断。

### 1.3 会话时序（关键！）

1. **开会话**：`13 05 01 00×16 19`
   ACK：`13 05 01 00 0A 03 00 00 00 02 1C 01 … 45`，随后常跟一条自发推送。
   **不开会话，dongle 对一切查询静音。** 实测 dongle 会记住会话状态，重启后（或句柄重开）重发一次也无妨。
2. **电量查询**：`13 4A 01 00×16 5E`
   响应：`13 4A 01 00 02 <电量%> <充电标志> 00×12 84`
   - `[5]` = 电量百分比（实测 35% 时 = 0x23，与键盘指示一致）
   - `[6]` = 充电标志：`0x10` 位 = 充电中（确定）；实测 35% 放电时 = 0x01。已充满/其餘位语义**待插充电线校准**（看日志 `状态字节`）
   - **`≤1` 一律视为无效读数**（真实电量到不了 1：低电量阈值是 20%，早该提醒过了，拒绝它不会漏告警）
3. **自发推送（report 0x13，`[1]=0x0A`）**：`13 0A 01 00 04 <类型位> <载荷> … sum`
   **实时更新**：认领后基类后台被动听 0A/CZ 推送，`StatusPushed` 即时 Upsert；主动 `4A` 查询仍每分钟兜底（dongle 缓存冻结见 §1.3.1）。
   **`[5]` 是消息类型位，必须先认它，再决定 `[6]` 怎么解释**：

   | 类型位 `[5]` | 含义 | `[6]` 是什么 |
   |---|---|---|
   | `0x05` | 电量推送 | **电量百分比**（实测 66% = `0x42`），`[7]` = 充电标志 |
   | `0x02` | 设备状态通知（语义未明，见下方 2026-10-06 晚复测） | **payload，不是电量**（实测 `0x00`/`0x01` 交替出现） |
   | 其他 | 未知类型 | 忽略 |

   > **血泪教训（2026-10-06 挖到真凶）**：旧代码不看类型位、直接读 `[6]` 当电量，于是把状态通知帧
   > `13 0A 01 00 04 **02** 01 …` 的 payload `0x01` 显示成 1%，触发误报低电量。识别到 `0x02`
   > 后曾把它当"设备已休眠"信号**立即标离线**（`BatteryPluginBase.RequestOffline`），比等 3 次
   > 通信失败（约 3 分钟）快得多。原始帧两边校验和都自洽，可自证。
   > 解析代码：`MchoseV1Codec.ParsePush`（`V1PushKind`），真机帧回归用例在 `src/tests/VigilWatt.Core.Tests/`。
   >
   > **复测推翻"0x02 = 休眠"（2026-10-06 晚，全天日志）**：payload `0x00`/`0x01` 全天交替出现
   > （19:36–19:46 每 4~5 分钟一对，20:12、21:39 各一次），且**每次通知后 1 分钟内设备都能正常
   > 应答电量查询**（日志里紧跟着"设备重新上线"）——设备根本没睡，按休眠标离线只造成在线↔离线
   > 闪烁和脏历史。现降级为**仅记录**，不发离线。
   > `payload 0x00/0x01` 的真实语义待下次插拔充电线时对照日志确认（怀疑与充电状态变化有关）。
   >
   > **2026-10-08 追补：`payload=0x00` 当"触发器"用**（`MchosePlugin` 的被动解析 → `RequestConfirm`）。
   > 语义既然未定论，就**不能当离线证据**；但它可以触发一次**立刻核实**——基类在被动监听的空闲 tick
   > 上跑一次与轮询同款的 `13 4A 01` 查询：有应答就什么都不会发生，没应答就当场判离线。
   > 这把"键盘真关机"的发现从"60 秒轮询攒 3 次失败 ≈ 2~3 分钟"压到秒级。
   > 注意这条**不是**离线判据，只是把核实时机提前——真正的定性仍由查询结果决定。
   > 另外：**迈从协议里没有"连接状态"字段**（不像雷柏有 `[18].bit7`、北通有占位帧），
   > 所以主动查询失败是它唯一能判离线的物理依据；也因此 `0x00/0x01` 的语义将来即使搞清楚了，
   > 也只影响触发时机，不会变成新判据。
   >
   > **2026-10-08 22:13 真机样本（第一次支持"0x00=链路断"这个假设）**：键盘**关机**那一刻来的
   > 正是 `payload=0x00`（触发核实 → 1.75 秒后判离线）；键盘**开机**那一刻来的正是 `payload=0x01`
   > （0.34 秒后"设备重新上线"）。两者与电源状态严格对应。
   > 与 2026-10-06 那次"全天交替"并不矛盾——**如果**那次交替其实是**键盘空闲休眠/唤醒**
   > （无线键盘空闲会自己睡），一切自洽：休眠也算"链路断"，但 dongle 仍能应答缓存帧，所以
   > "每次通知后设备都能正常应答查询"。
   > **待验**：让键盘自然休眠（**不关电源**），看是否发 `0x00`、以及那时 `4A` 查询是否仍能应答。
   > 即便成立，`0x00` 也**仍然不该直接判离线**（休眠会闪）——现在"触发器 + 核实"的用法正好绕开了这个坑。

### 1.3.1 ⚠ 充电状态可能长时间冻结（dongle 缓存，固件行为）

**现象**（2026-10-06 晚，用户复报"已断开充电仍显示充电中"）：键盘空闲（无人打字）时，dongle 对
`4A` 电量查询返回**逐字节完全相同的缓存帧**——当晚 19:47–21:52 连续 2 小时每分钟都返回
`13 4A 01 00 02 63 10 … D3`（99% + 充电标志），而设备实际状态早已变化；21:53 前后键盘被唤醒
（按键）后才恢复真实读数（`62 01` = 98% 放电）。

**机理**：dongle 的 4A 响应 = 键盘最后一次上报的快照；键盘深度空闲时不与 dongle 通信，主机侧
无论怎么查都只能拿到旧快照。**拔充电线不会触发 dongle 缓存刷新**，这是固件行为，主机无法提前
感知。自发推送（0x05）与会话重建（05 01 开会话）后 dongle 会立即推一条状态——但它同样是缓存值
（21:21 会话推送仍是"充电中"），只是键盘唤醒后它会变成新值。

**应用侧对策**（已实现）：
- `DeviceManager.Upsert` 的变化判定**包含充电标志**——设备一旦改口（充电中↔放电），即使电量数字
  没变也立即刷新 UI/托盘/小组件并写历史（旧版漏判，界面要等下次电量跳动才自愈，正是本次 bug）；
- `0x02` 状态通知不再标离线（见 §1.3 复测）；
- 拔线后显示滞后到"键盘下次醒来"为止属预期，无法更快——可敲任意键让键盘唤醒，1 分钟内读数即刷新。

轮询实现：`MchosePlugin.PollKeyboardV1`（每分钟 1 条 4A 查询 + 顺带解析 0A 推送）；探测实现：`TryKeyboardV1`（05 01 开会话 → 4A 01）。

### 1.4 已证伪的通道（别再试）

- **feat8（Col06，feature 0x06）**：`06 <命令回显> <连接模式 01=有线/02=2.4G> 64 64 64 B5 6A`。[3..5] 恒为 0x64（=100），**不随电量变化**——旧版读出 100% 的错误来源。SetFeature 只是回显写入字节。
- **经典鼠标协议（feature 0x11）/ Rapou7 V2（64 字节 output 0x4D）**：此 dongle 物理上不支持——feature 通道数量为 0（HidD 返回 err=1）、输出只有 20 字节。Rapou7/offline-mchose 项目只覆盖迈丛**鼠标**（A7/L7/M7/AX5/A5/K7），不含键盘，不要再看它。（`0x3837` 世代接收器另当别论，见 §1.6。）
- **0x4D 报文**：WriteFile 报"参数错误"，此 dongle 不认（见 §2，那是新一代 dongle 的协议）。

### 1.5 会话排他（运维注意）

dongle 的配置会话一次只服务一个客户端。崩溃进程不关会话 → dongle 假死，**官方软件也连不上**；kill 持有进程或重新插拔恢复（详见 safety.md §2 事故二与 §4 应急恢复）。本应用与官方 M HUB 不要同时连。

### 1.6 鼠标 V2 世代（接收器 3837:100A / 3837:201B）—— 贡献者真机验证，本机未复测

`0x3837` 世代接收器在厂商接口上给 65 字节（64 数据 + 1 report ID），与老 G87 的 20 字节 0x13 通道不是一回事：**在这条通道上发键盘 `0x13` 帧没有意义**，只能走鼠标 V2 的 E2 状态帧。

**E2 状态帧（被动）**：Windows `ReadInput` 缓冲 `[0]` 是 report ID 前缀（`0x13`），**不参与取反**；其后 payload 逐字节 `^0xFF` 后：

| 取反后下标 | 含义 |
|---|---|
| `[0]` | 恒为 `0xE2`（帧识别位） |
| `[3]` | 充电位：`1` = 充电中 |
| `[4]` | 电量百分比 |

真机样本（A7 V2 Pro 接收器，68% 未充电）：
`13 1D FE FE FF BB FD FD F9 D6 BE C8 DF A9 CD DF AF 8D 90 FF FF 00 00 00`
→ 去前缀取反 = `E2 01 01 00 44 …`，`[3]=0x00` 未充电、`[4]=0x44`=68%。

**触发帧（写）**：接收器约 10 秒自推一次 E2；等不到时发一次 `0x11/0x06` 唤醒上报。

```
[0]=0x11（report ID，原样）  [1]=0xF9（=0x06^0xFF）  [2..]=0xFF（=0x00^0xFF）  补零到接口输出长度
```

官方 MOUSE_LEGACY 的 WebHID 写法是 `sendFeatureReport(0x11, "06 00×19" ^ 0xFF)`——**`data` 不含 rid**。Windows `WriteOutput` 要求 `buffer[0]` 就是 report ID 且**不取反**，照抄网页版把 rid 一起取反必写失败。

**型号识别**：官方 M HUB WEB 前端 `battery-monitor` 的 `getPassWord` / `KB_PW2MODEL` 把"接收器密码"映射到型号名；密码就是 V1 会话 ACK（`13 05 01 …`，布局见 §1.3）payload 的前 6 字节，即真机 ACK 的 **`[5..10]`**（`13 05 01 00 0A 03 …` 里 `03` 在第 5 字节；早期合成样本多一个字节、密码在 `[6..11]`，`ModelFromSessionAck` 两种偏移都试）。已收录 18 个键（G87 / G87 V2 / K99 / K99 V2 / G98 / G98 Pro / X75 / X75 V2 / G75 Pro / G75 V2 / G98 V2 / UT98 / Z75 / Z75S / KX75 / GX87 / GX87 V2 / K87），全表在 `MchoseMouseCodec.ModelFromPassword`。产品名是泛化的「MCHOSE 2.4G Wireless」时用型号替换，显示成「迈从 xxx」。

**本机边界**：本机只有 G87 V1（`41E4:2001`），没有 A7 V2 Pro / G87 V2，鼠标链路只有单测与代码审查。贡献者（zi-ha）在 A7 V2 Pro 接收器（`3837:100A`）上抓到了 E2 帧与触发帧；G87 V2 接收器（`3837:201B`）在贡献者机器上走**键盘 V1 会话**（抓到 4A 应答 69%），但会话 ACK 的密码段是全 0，型号表匹配不到，显示名退回产品名。

**未知项**（别按猜测补）：E2 帧其余字节语义未定；充电位只区分"充电中/未充电"，没有"已充满"；型号表外的设备一律退回产品名。

耳机 V9 Pro 用的是另一个 VID（`291D:385D`），不在这条链路上，见 [mchose-v9-pro.md](mchose-v9-pro.md)。

## 2. 0x4D 协议（新一代 dongle，M HUB WEB 前端逆向）—— 鼠标主力通道；键盘走 §2.4 的 CZ 分块读

来源：官方 www.mchose.com.cn 的 M HUB WEB 运行时 JS（当前是 `main-CRYCuU75.js`，2026-11-07 抓取；
旧版文件名是 `purify.es-*.js`，现在的 `purify.es-*` 只剩 DOMPurify）。VigilWatt 侧只有一个执行器
`Mchose0x4DCodec`——原 `qhw` 与 `mouse-k7` 两套实现已于 M2-2 合并，运行时协议名统一 `mchose-0x4d`。

**⚠ 0x3033 这颗 dongle 实际上不认 0x4D**：本机 2026-11-04 实测，`0x4D` 写入在三条 65 字节通道上
全部静默；官方 web 驱动与 VigilWatt 都走下面 §2.4 的 CZ 分块读。
（旧文档记的 `0x0904` 查询同样无效——该命令在当前官方代码里已不存在，见 §2.2。）

### 2.1 帧格式（report ID 0x4D，请求与应答同布局）

```
[0]=0x4D [1]=ver=1 [2]=flags=1 [3]=payload长度 [4]=cmdLo [5]=cmdHi [6]=bizCode=0 [7]=seq=0 [8…]=payload [8+len]=XOR([2]..[7+len])
```

- **flags 恒 1**：官方 `getCommandBuffer` 只在 `flags === 1` 时写校验字节。
- **seq 恒 0**：不要自增（自增会让设备的应答匹配错位）。
- **校验是异或，范围从 `[2]`（flags）起**，不含 version 与 report ID。
- 帧长固定 64 字节（官方 `length: 64`），不足补零。

WebHID 侧 reportId 自动加首字节；Windows WriteFile 时 [0] 就是要写的 report ID。
`ReadInput` 缓冲可能带 report ID 前缀，解析时偏移 0 / 1 都试（`Mchose0x4DCodec.TryLocate`）。

### 2.2 命令表（来自官方 JS；读与写是两套命令号）

| 命令 | 含义 | 响应 payload | 方向 |
|---|---|---|---|
| `0x0900` | getBaseInfo（连接后第一条，**电量也在这条**） | `[0..1]`=配对本体 VID le、`[2..3]`=PID le、`[4]`=maxProfile、`[10]`=连接(1有线/2无线)、`[11]`=充电(0未充/1充电/2充满)、`[12]`=电量%、`[13]`=gameSafeMode | 只读 |
| `0x0901` | getFwVersion（参数 `[0]`=主固件 / `[1]`=RF 固件） | parseFwVersion | 只读 |
| `0x0905` | 板名分块读（`[board, offset, size]`，每块 23 B，累计 60 B） | UTF-8 文本 | 只读 |
| `0x0002` / `0x0003` / `0x0009` / `0x000a` | 基础配置 / DPI / LOD / 回报模式 | 见 [mchose-catalog.md](mchose-catalog.md) §2 | 只读（VigilWatt 未实现） |
| `0x0102` / `0x0103` / `0x0109` / `0x010a` 等 | 上表同项的**写**方向（读命令 + 0x0100） | — | **禁止** |
| `0x0906` / `0x090D` / `0x0918` / `0x0921` / `0x0924` | 灯效 / 配置 / 宏 / 心跳 | 见 JS | **禁止** |

**`0x0904` 不存在**：当前官方 `readMap` 里没有这条命令，电量由 `0x0900` 的 `payload[12]` 给出。
VigilWatt 旧实现曾按 `0x0904` 发送（且 flags / 校验范围也不对），M2-2 已改正。

**握手帧**：官方只在 `newMouseWCH` 四款（V7 / V7 Pro / G3 V3 / G3 S）上发
`AA 55 AA 55 AA 55`（63 字节裸 report，无 0x4D 头），**不是通用步骤**；VigilWatt 未实现，
这些型号是否必须握手**尚未真机验证**。

### 2.3 CZ 通道（同代键盘的批量配置协议）

帧：flag=0x55 / 响应 expect=0xAA，`[55, cmd, 0, chk, size, offsetLo, offsetHi, 0, payload…]`（chk 逻辑见 JS）。批量灯效/配置走这条。电量推送：dongle 自发 `[FA, FB, 07, 电量%, 充电标志]`。

### 2.4 CZ 分块读：这颗 dongle 真正认的电量通道 —— ✅ 本机真机验证

协议名 `cz-block`，帧与解析全在 `specs/mchose.protocols.json`（`implementation` 缺省 `data`），插件只负责分流。

接口地图（本机 `3837:3033`，G87 V2 2.4G）：

| 接口 | usagePage/usage | 长度 | 读电量的结果 |
|---|---|---|---|
| MI_01 | `0x0001/0x0000` | 65/65 | ✅ 有应答，但分类器按"非厂商页"排除，不走 |
| MI_02 | `0xFF31/0x0074` | 65/65 | ✅ **实现走这条**（官方 WebHID filters 也登记它） |
| MI_03 | `0xFF70/0x0071` | 65/65 | ❌ 任何写入都只回固定 `00 0F 01 FE 0E`（占位帧，不是 NAK） |

请求（65 字节，首字节是 report ID 槽，本机为 `0x00`）：

```
55 05 00 [off+size] size offLo offHi 00 …补零
```

`[3]` 是 **offset+size**，不是校验和（别和 §2.3 的 `chk` 混）。官方一次性读 `offset=0, size=0x38`，覆盖 `0x00..0x37`；电量在 `0x20`，所以**第二段 `0x38..0x3F` 不必读**。

应答：

```
AA 05 00 xx size offLo offHi 00 <data…>     data 从下标 9 起（含 report ID 槽）
```

`[5]=size`、`[6..7]=offset`、`[4]` 随包变化（不是长度）。数据段头两字节 `[2..3] == AA BB` 是"这是合法状态块"的判据。

状态块字段（本机实测）：

| 偏移 | 含义 |
|---|---|
| `[0]` | 恒为 `0x50`，**不是电量**（80%→100% 全程不变，另一个 64 字节块里也是 0x50） |
| `[2..3]` | `AA BB` 魔数 |
| **`[0x20]` bit7** | **充电中**（插线置位，拔线清零，实测 0xCE↔0x4E） |
| **`[0x20]` bit0..6** | **电量百分比**（实测 0x5A=90、0x62=98、0x64=100，与官方页面逐次一致） |
| `[0x20]` 以下/以上其余字节 | 语义未定，不参与判定 |

充满判据 = 未充电且电量 100，与官方前端 `resolveMCChargeStatus` 一致。JSON 里**不写 `fullAt`**——通用满电阈值会无条件覆盖设备报的充电态，改用插件层的 `MchoseSpecs.ResolveFull` 补判：100% 且 bit7=0 才判"已充满"，bit7=1 仍显示"充电中"。

**证据来源**：浏览器 hook `HIDDevice.sendReport`，在官方 www.mchose.com.cn 连上这颗 dongle 时抓到两条读帧 `55 05 00 38 38 00` / `55 05 00 40 08 38`；原样回放即有应答，随后按插拔对照锁定 `[0x20]` 的位含义。

**两条别再试的路**：

- **`0x4D` 帧**（§2.1/2.2）：这颗 dongle 全静默，写进去没有任何应答
- **官方 `audio.mc` 单帧电量命令**（`reportId 0x55`、帧头 `AA`、`subCmd 11`）：4 种摆放全失败，其中两条回错误帧 `00 AB AA 01 00 00 01 00 0A 63 73 65 72 72`（尾部 ASCII `cserr`）。CZ 通道的命令字在 `[2]`，把 MC 的帧头 `0xAA` 放进去会被当未知命令拒掉；`0xAB` 首字节 + 明文错误串才是真 NAK

**注意**：`[0x20]` 的低 7 位是电压估算，同簇内会有 ±2 抖动（90→89→90）。所以"充满"只能靠 `MchoseSpecs.ResolveFull` 补判，不是独立字段。

## 3. 0x4D 通道（`3837:0x1018` 等通用 dongle）—— 贡献者真机验证

协议名统一 `mchose-0x4d`，帧与解析全部在 `Mchose0x4DCodec`（纯函数，有单测）；原 `qhw` / `mouse-k7`
两套实现已于 M2-2 合并。**本节标题与历史记录里的 "K7" 是叫法问题，不是型号判定**：
`0x1018` 是通用 8K dongle（K7 V2 全系 / A7 V3 全系 / K5 Pro+Ultra / R7 Ultra 共用），
具体型号只能由 `0x0900` 自报的 VID/PID 决定（§3.3、§3.8）。

### 3.1 接口地图

这颗 dongle 有两条厂商接口，只有一条能用：

| 接口 | usagePage / usage | IN / OUT / FEAT | 结论 |
|---|---|---|---|
| `MI_02&Col02` | `0xFF01` / `0x0001` | 64 / 64 / 64 | ✅ 唯一可用的命令通道（report ID **`0x4D`**） |
| `MI_02&Col01` | `0xFF0B` / `0x00C4` | 61 / 61 / 61 | ❌ 实测 60 秒零报文 |

**这颗 dongle 的 feature 通道"写通读不通"**：`SetFeature(0x11 / 0x4D / 0x13)` 全部返回成功，
但 `GetFeature` 恒为 `ERROR_GEN_FAILURE`(31)。因此 A5 / A7 / gmouse / V2 世代那几族（靠 feature 读）
和 `0x11` 触发帧 + E2 状态帧那条被动路径，在这颗 dongle 上都不成立——这正是它原先完全读不到电量的原因。

### 3.2 帧格式（output report `0x4D`，补零到 64 字节）

```
偏移  0    1      2      3     4      5      6    7     8..7+len    8+len
    4D  01   flags  len  cmdLo  cmdHi  biz  seq   payload…      checksum
```

- **`checksum = XOR(frame[2 .. 7+len])`，且只有 `flags == 1` 时才写**
- ⚠ **是异或，不是求和**。早前用 `flags = 0x03` + 求和写过几十轮，设备一律把自己的写原样回显、
  什么都不做，于是被误判成"这颗 dongle 只会回显、没有查询通道"。读法是错的，不是设备没有通道。
- 设备也会**回显自己的 output 报告**为一条 input 帧，解析前必须整帧比对跳过。

### 3.3 命令 `0x0900`：读设备信息

请求 9 字节有效：`4D 01 01 00 00 09 00 00 08`。

应答 16 字节 payload，字段表照抄官方 `deviceInfoToObj`（旧文档称 `_K()`）：

| payload[0..1] | payload[2..3] | payload[4] | payload[10] | payload[11] | payload[12] | payload[13] |
|---|---|---|---|---|---|---|
| 配对**本体** VID（LE） | 配对**本体** PID（LE） | maxConfigNum | connectStatus | **chargeStatus** | **batteryLevel** | gameMode |

真机样本：`4D 01 01 10 00 09 00 00 | 37 38 26 40 04 00 00 00 00 10 02 00 64 00 08 E4 | EF`
→ 连接状态 2、充电状态 0、**电量 `0x64` = 100%**。

**字段 → 统一模型（M2-3 起接入）**：三项一次读出，映射只写在 `Mchose0x4DCodec` 里，插件不另写码表。

| 字段 | 取值 | 映射 | 证据 |
|---|---|---|---|
| `[10]` connectStatus | `1` | `ConnectionKind.Wired` | 官方枚举；**真机未留证**（样本全是 2.4G） |
| | `2` | `ConnectionKind.Wireless24G` | 官方枚举 + 真机（`0x1018` dongle） |
| | `0` / 其它 | `ConnectionKind.Unknown` | 官方没给这两个值的语义，**不猜** |
| `[11]` chargeStatus | `0` | 未充电（100% 时按"已充满"收尾） | 官方枚举 + 真机（`0x0900` 与 `0x0600` 都见过 0） |
| | `1` | `ChargingState.Charging` | 官方枚举 + 真机（`0x0600` 上底座那条） |
| | `2` | `ChargingState.Full` | 官方枚举；**真机未留证** |
| | 其它 | `Unknown` | **不默认成"未充电"** |
| `[12]` batteryLevel | 1..100 | `BatteryPercent` | 真机 100%；`0` 视为"还没算出来"，不报 0% |

连接方式**只刷徽标**：`Unknown` 不覆盖已知值、不参与在线判定、也不触发重新认领（认领只看 VID/PID 与接口描述符）。
`0x0600` 事件里没有连接字段，所以连接方式只能来自 `0x0900`。M4-3B-1 起 `DeviceStatus.Connection` 是
`TelemetryValue<ConnectionKind>`，这条帧记 `TelemetrySource.DeviceReported`（`0x0900` 是唯一来源）；
其它协议族（`keyboard-v1` / `cz-block` / `gmouse` / `mouse-v2` / `mouse-a5` / 耳机）没有该字段，保持"未知"
（见 `project/architecture.md` §6）。

**身份字段（M2-1 起解析，只用于显示名，不参与认领）**：样本前 4 字节解出 VID `0x3837` / PID `0x4026`，
按官方型号表 `0x4026` 是 **A5 V3 Ultra+**，不是 K7 V2 Ultra+（`0x4028`）——见 §3.8。

### 3.4 命令 `0x0600`：设备主动上报的电源事件

`payload[0]` / `payload[1]` 是**"本次带了哪些字段"的位图**（不是固定子类型）：

| 位置 | 掩码 | 字段 | 取值 |
|---|---|---|---|
| `payload[0]` | `0x02` | **电量** | `payload[3]` |
| `payload[0]` | `0x01` | DPI 档位 | `payload[2]` |
| `payload[0]` | `0x08` | 配置索引 | `payload[6]` |
| `payload[1]` | `0x02` | **充电状态** | `payload[12]` |

真机样本：

```
电量事件   4D 01 01 0D 00 06 00 00 | 02 00 00 64 00 … 00 | 6C
充电事件   4D 01 01 0D 00 06 00 00 | 00 02 00 00 00 … 01 | 09   (在底座上)
充电事件   4D 01 01 0D 00 06 00 00 | 00 02 00 00 00 … 00 | 08   (已离开)
```

事件**一次只带一个字段**，插件里缺的那项沿用上一次的值，不能冲成 `Unknown`。

**长度按实际带的字段判，不按最长那条**：纯档位事件只有 3 字节（`payload[0..2]`），
电源事件才到 `payload[12]`。M2-4B1 之前一律要求 ≥13 字节，纯档位事件会被整条丢掉。

**档位事件（bit0）**：`payload[2]` 是**活动档位索引（0 基）**，不是档位数、也不是 DPI 值。
VigilWatt 只把它落到 `PointerTelemetry.DpiLevel`（存协议原值，不 +1），且**不据此推算当前 DPI**——
`ActiveDpi = dpiX[usbDpiIndex]` 只有在"读的配置档确实是活动档"时才成立，而活动档来源仍未确认。
`payload[6]`（配置索引）仍**不采信**为 `profileIndex`（只有 B 级证据）。

### 3.4.1 命令 `0x0003`：读 DPI 配置（M2-4B1 起实现，未发布）

请求 `payload = [profileIndex, direction]`（0 = X / 1 = Y，读两轴要发两次）；
应答 `[2]=dpiSum、[3]=usbDpiIndex、[4]=dpiHasY、[5..16]=6 档小端 16 位`。

- 解析在 `Mchose0x4DCodec.TryParseDpi`，换算关系在 `TryGetActiveDpi`（profile 对不上就返回 false）。
- 插件**最多试 3 轮**（每轮主轮询一次），先读 X；只有 X 解析成功且 `dpiHasY==1` 才再读一条 Y，
  Y 失败只丢 Y、不影响 X。两项都成功即收工——睡着的设备不会因为第一次没应答就永远拿不到样本。
- **不写进 `DeviceStatus`**：没有可靠的活动档来源，读到的档位不能当"当前 DPI"。能力声明也没有因此改成 supported。
- 字段表、证据等级、官方代码定位与未确认项见 [mchose-dpi-report-rate-audit.md](mchose-dpi-report-rate-audit.md)。

### 3.4.2 命令 `0x0002`：读性能配置（M2-4B2 起接入回报率）

请求无参数；应答 `[0]=profileIndex`、`[1]` 高半字节 `usbRateIndex` / 低半字节 DPI 档位、
`[2]` 高半字节 `gRateIndex`。**协议只给 index，没有 Hz**，换算靠两张官方表：

| 表 | 档位 |
|---|---|
| `1k` | 125 / 500 / 1000 |
| `8k` | 125 / 500 / 1000 / 2000 / 4000 / 8000 |

选表（官方 `getReportRateList`）：先认型号，再按 **USB 枚举 PID** 在该型号的槽位里选表；本体直连用槽 0。
槽位在 `mchose-catalog.json` 的 `rateProfiles`（本体 PID → {USB PID → 表名}），表值在 `rateTables`。

- 线上 index 是"设置值 + 1"（写侧 `index>0 ? index+1 : index`），读侧 `v>1 ? v-1 : v`。
- **两个 index 不一致就不发布**：官方只在改档位时同步写两套，样本里不一致说明我们还不知道哪套在生效；
  这时保持 Unknown，**不拿另一个顶替**、也不清已有值（`MchoseRatePolicy` 是唯一判定点）。
- 发布 `ReportRateSettingHz`，来源 `Inferred`（表来自官方静态数据，本机未验证）。
- `ReportRateMeasuredHz` **永远不填**：协议里没有实测吞吐。
- 型号不明 / 槽位缺失 / index 越界 → 保持 Unknown，**不默认 125Hz**。
- `gRateIndex` 只记日志：官方改档时两个 index 一起写，全仓唯一的下标使用点是 `usbRateIndex`。

**取证日志**（默认 Info 级别就能看全）：认领后各一条 `迈从 0x4D 回报率:` / `DPI(X):` / `DPI(Y):`，
都带原始帧与解析值；读失败在**最后一轮**记 Info、中间轮记 Debug；`0x0600` 档位事件也记 Info 带原始帧。

### 3.5 ⚠ `0xFF` 是"鼠标在睡"，不是失败

真机常态应答是 `4D 01 01 01 00 09 00 00 FF`（payload 只有 1 字节）。官方 `hgt()` 遇它也是重试 + 容忍无读数。

**绝不能当查询失败记账**：按普通失败记的话，睡着的鼠标三轮就被判离线并熔断停写，醒了也不会再被问。
`Poll0x4D` 因此自己记账——收到任何 `0x4D` 帧就 `ReportPollAnswered`，只有一帧都没收到才算失败。

### 3.6 证据来源

官方 M HUB 是 Electron 套壳，`app.asar` 里一个协议字符串都没有，真实驱动是运行时从
`https://www.mchose.com.cn/assets/` 拉的打包 JS（2026-11-07 抓取时是 `main-CRYCuU75.js`，7.67 MB；
旧版文件名 `purify.es-*.js`，现在这个文件只剩 DOMPurify）。定位过程：

1. `--remote-debugging-port=9222` 启动 M HUB，CDP 连上内嵌 iframe
2. 在页面里 hook `HIDDevice.prototype.sendReport` 与 `inputreport`，拿到 WebHID 层原始报文
3. 在 JS 里按命令码**十进制值**定位：`2304`(0x0900) → `readDeviceInfo` / `deviceInfoToObj`；`1536`(0x0600) → `LA()`
4. 帧构造器 `getCommandBuffer` 就在相邻位置，一起读出来即得完整协议

**教训：能读到官方解析代码时，不要靠改字节暴力猜。** 本轮穷举猜了两个小时没结果，读到 `i1e()` 后十分钟闭环。

## 4. MCHOSE Gmouse 主动查询（G3 V2，接收器 VID_3837&PID_4245）—— 贡献者真机验证

并入迈从插件，协议名 `gmouse`，帧与解析全部在 `MchoseGmouseCodec`（纯函数，有单测）。

### 4.1 接口地图

G3 V2 的 2.4G 接收器（`3837:4245`）枚举出多个厂商接口，**命令通道只有一个**：

| 接口 | UsagePage/Usage | IN/OUT | 说明 |
|---|---|---|---|
| `mi_00&col04` | `0xFFA5/0x0088` | 2 / 0 | 厂商页，无输出通道 |
| `mi_01&col04` | `0xFF05/0x0002` | 64 / 0 | 厂商页，无输出通道 |
| `mi_01&col05` | `0xFF06/0x0002` | 64 / 64 | 厂商页，有进有出（非 Gmouse 命令通道） |
| **`mi_02`** | **`0xFF01/0x0010`** | **65 / 65** | ✅ Gmouse 命令通道（65 = 64 数据 + 1 report ID） |

与 K7 的 `0xFF01/0x0001` 不同，Gmouse 的命令通道 usage 是 `0x0010`——靠这组完整指纹（VID + PID + usagePage + usage + 双方向长度）与同厂的 K7、V2 被动 E2 链路区分。

### 4.2 帧格式（65 字节主动查询）

Gmouse 是**主动查询**协议：鼠标不会自发推送电量帧，必须由主机发查询帧。

**查询帧**（65 字节，`[0]` = report ID = 0）：

```
00 55 30 A5 0B 2E 01 01 01 00 … 00
```

**应答帧**（前缀 `AA 30`，可能带 report ID 前缀，偏移 0 或 1）：

```
AA 30 xx xx xx xx xx xx [电量] [充电] …
```

- 电量 = `[offset+8]`（1..100 合法；0 按"未就绪"占位拒掉，属推断，见 §4.5）
- 充电 = `[offset+9]`（0=未充电，非 0=充电中）

### 4.3 证据来源

- 社区项目 `aliezzzz/mchose-battery`（Rust 实现，`src/protocols/g3.rs` 的 `GmouseProtocol`；查询帧、偏移与充放电判据与本节逐字节一致）
- 迈从官方 M HUB 网页端 `/gmouse` 打包 JS
- 真机 G3 V2（3837:4245）验证读到电量（如 89% 未充电）

### 4.4 与 0x4D / V2 的差异（别搞混）

| | Gmouse（本节） | 0x4D（§3） | V2 被动 E2（§1.6） |
|---|---|---|---|
| 命令通道 usage | `0xFF01/0x0010` | `0xFF01/0x0001` | ≥60 字节厂商接口 |
| PID | `0x4245` | `0x1018` | `0x100A` 等 |
| 帧 | `00 55 30 A5…`（65B） | `4D 01…`（64B） | 被动 E2 推送 |
| 触发 | 主动查询 | 主动查询 + 被动事件 | 被动 + 0x11/0x06 触发 |
| 应答前缀 | `AA 30` | `4D 01` | E2 帧 |

### 4.5 未验证边界（别当成已知）

- **充电态**：`[off+9]` 非 0 判充电中只经合成用例，**未在真机充电时抓包**；是否存在"已充满"专用值未知。本实现只区分"充电中 / 未充电"，再由 `ChargingStateMap` 把"100% 且未充电"判成 `Full`。
- **断连 / 休眠**：鼠标关机时 dongle 零应答，插件按 3 轮失败判离线并熔断停写（退避 30 秒起、封顶 5 分钟）；未做长跑与唤醒验证。
- **只认一组 PID**：来源项目里 Gmouse 族还有 `0xA8A5` / `0xA8A4`（这两个是 **VID**，不是 PID）以及 `0x2255` / `0x4011~4013` / `0x4033` / `0x4042` / `0x418c` 等 PID；本实现只认 `0x3837:0x4245`，其它型号未验证。
- **`usage=0` 枚举变体**：来源项目对 `usage=0` 也放行，本实现要求 `usage=0x0010`；若某型号枚举成 0 则不会被认出（宁可漏认，不误认）。
- **`0 = 未就绪`**：来源实现只拒 `>100`、接受 0；本实现把 0 当占位拒掉属**推断**（避免把"没连上"报成 1%），未真机留证。
- **`mi_01&col05` 仍走 V2 兜底**：该接口（`0xFF06/0x0002`，64/64）不是命令通道，但按"≥60 字节只走鼠标"仍会被分类为 `MouseV2`，每 15 秒拍点收到一条 `0x11/0x06` 触发帧。本轮未改（非本 PR 引入），见 BACKLOG。

## 5. 迈从 G75（接收器 `3554:FA09`）—— 本机实测

### 5.1 与 AULA 共用指纹

接口与 G87 完全同型：`0xFF02/0x0002`、report `0x13`、进出各 20 字节、`0xFF04` feat8 那个"邮箱"也在。
同一个 VID/PID 还被 AULA F99 Pro 占用，**HID 层分不出品牌**，只能靠会话 ACK 里的型号码（§1.6 的密码表）分流：

- 会话 ACK 的密码落在迈从型号表 → 迈从插件认领，显示「迈从 G75 Pro」；
- 落不到（如 AULA 的 `030000000158`）→ 迈从放弃，接口留给 AULA 插件。

两端都实现了这条判据：`MchosePlugin.IsSharedWithAula` + `TryKeyboardV1(requireKnownModel: true)`，
AULA 侧 `Probe` 见到迈从型号直接返回 null。判据只放宽到这条精确指纹，不按 VID 泛化（protocols.md 的共用号段一节）。

### 5.2 会话 ACK 的字节偏移

与 G87 同一套：密码是 ACK 的 `[5..10]`（布局见 §1.3、密码表见 §1.6）。
`MchoseMouseCodec.ModelFromSessionAck` 依次试 `[5]`、`[6]`——`[6]` 只为兼容多一个填充字节的早期样本，命中即返回。

本机真机 ACK（G75 Pro，2026-10-24）：

```
13 05 01 00 0A 03 00 00 00 01 15 01 … 3D     # 密码 03 00 00 00 01 15 = G75 Pro
```

### 5.3 读数

同一套 V1 协议，开会话后 `13 4A 01` 查询：

```
发  13 4A 01 00 … 5E
收  13 4A 01 00 02 24 01 … 85        # [5]=0x24=36%，[6]=0x01 未充电
推  13 0A 01 00 04 05 24 01 …        # 类型位 0x05 = 电量推送
```

### 5.4 边界

- 型号名来自官方 `getPassWord` 表，本机这台是 **G75 Pro**（`030000000115`），不是无后缀的 G75；显示名按表走。
- 已知未收录的迈从新型号会被判给 AULA 插件（显示成 AULA F99 Pro）——遇到再补密码表。
- 用户自述为「迈从 G75 2.4G 键盘」，与 ACK 型号一致（官方把 G75 Pro 也归在 G75 系列）。

## 6. A5 V2 Ultra 鼠标（接收器 `3837:100C`）—— 贡献者声明，本机未复测

与同品牌 E2 状态帧、0x4D、gmouse 都是**不同链路**：A5 走厂商 Feature 通道（`0xFF01/0x0001`），
一条反码查询 + 一次读回。插件是独立的 `MchoseA5Plugin`，但 `Name` 同为 `Mchose`、共用品牌开关，
设置页按 Name 去重后只出一行（`AGENTS.md` §9）。

### 6.1 帧

查询：Feature report `0x11`，20 字节 payload **全 `0xFF`、首字节改 `0xF9`**，按 21 字节（含 report ID）发送。
同一 collection 里混着长短不同的 report，**必须按 21 字节发/读**，按最大长度 65 会错位。

通知：`13 ?? F9 …`（等它到达后再读，官方驱动也是这个顺序）。

回包（`0x11` + `0xF9` + 反码 VID/PID + …）：

| 偏移 | 含义 |
|---|---|
| `[2..3]` | 反码 VID，取反后须为 `0x41E4` |
| `[4..5]` | 反码 PID，取反后须为 `0x1101` / `0x1102`（**鼠标本体**的 ID，不是 dongle） |
| `[11]` | 反码电量，取反后 0~100 |
| `[12]` | 反码充电位：`0` 放电 / `1` 充电中 / `2` 已充满 |

反码是这个协议唯一的完整性手段（没有校验和），所以 VID/PID 两位必须逐字节对上才采信。

### 6.2 边界

- 电量下界放 0：协议会给出真实的 0%（反码 `0xFF`），不能按「0/1 是占位」拒掉。
- `ProbeCooldown = 60 秒`：不跟着键盘的 15 秒发现节拍增加写入。
- 本机无该设备，未复测；作者真机读数与官方一致。
