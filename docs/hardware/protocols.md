# 2.4G 协议手册

所有结论都是真机验证或官方软件分析所得，**改协议代码前先读本文，不要重新猜**。最后更新：2026-10-19。

## 1. 迈从键盘 G87（dongle VID_41E4&PID_2001）—— ✅ 已打通，应用在用

### 1.1 接口地图

| 接口 | 用途 |
|---|---|
| MI_00 | 标准键盘（系统保护，打不开，按键走这里） |
| MI_01&Col01（usagePage 0xFF02，in/out=20 字节） | **配置/电量通道**，report ID 0x13 |
| MI_01&Col02/Col03/Col05 | consumer / system / mouse，无输出通道，别碰 |
| MI_01&Col06（usagePage 0xFF04，feature=8） | "邮箱"，**不是电量**（见 §3） |

### 1.2 帧格式（20 字节 output report，report ID 0x13）

```
[0]=0x13  [1]=命令  [2]=参数  [3..18]=0x00  [19]=sum(前19字节) & 0xFF
```

校验就是前 19 字节简单求和截断。

### 1.3 会话时序（关键！）

1. **开会话**：`13 05 01 00×16 19`
   ACK：`13 05 01 00 0A 03 00 00 00 02 1C 01 … 45`，随后常跟一条自发推送。
   **不开会话，dongle 对一切查询静音。** 实测 dongle 会记住会话状态，重启后（或句柄重开）重发一次也无妨。
2. **电量查询**：`13 4A 01 00×16 5E`
   响应：`13 4A 01 00 02 <电量%> <充电标志> 00×12 84`
   - `[5]` = 电量百分比（实测 35% 时 = 0x23，与键盘指示一致）
   - `[6]` = 充电标志：`0x10` 位 = 充电中（确定）；实测 35% 放电时 = 0x01。已充满/其餘位语义**待插充电线校准**（看日志 `状态字节`）
   - **`≤1` 一律视为无效读数**（真实电量到不了 1：低电量阈值是 20%，早该提醒过了，拒绝它不会漏告警）
3. **自发推送（report 0x13，`[1]=0x0A`）**：`13 0A 01 00 04 <类型位> <载荷> … sum`
   **实时更新**：认领后基类后台被动听 0A/CZ 推送，`StatusPushed` 即时 Upsert；主动 `4A` 查询仍每分钟兜底（dongle 缓存冻结见 §1.3.1）。
   **`[5]` 是消息类型位，必须先认它，再决定 `[6]` 怎么解释**：

   | 类型位 `[5]` | 含义 | `[6]` 是什么 |
   |---|---|---|
   | `0x05` | 电量推送 | **电量百分比**（实测 66% = `0x42`），`[7]` = 充电标志 |
   | `0x02` | 设备状态通知（语义未明，见下方 2026-10-06 晚复测） | **payload，不是电量**（实测 `0x00`/`0x01` 交替出现） |
   | 其他 | 未知类型 | 忽略 |

   > **血泪教训（2026-10-06 挖到真凶）**：旧代码不看类型位、直接读 `[6]` 当电量，于是把状态通知帧
   > `13 0A 01 00 04 **02** 01 …` 的 payload `0x01` 显示成 1%，触发误报低电量。识别到 `0x02`
   > 后曾把它当"设备已休眠"信号**立即标离线**（`BatteryPluginBase.RequestOffline`），比等 3 次
   > 通信失败（约 3 分钟）快得多。原始帧两边校验和都自洽，可自证。
   > 解析代码：`MchoseV1Codec.ParsePush`（`V1PushKind`），真机帧回归用例在 `src/tests/VigilWatt.Core.Tests/`。
   >
   > **复测推翻"0x02 = 休眠"（2026-10-06 晚，全天日志）**：payload `0x00`/`0x01` 全天交替出现
   > （19:36–19:46 每 4~5 分钟一对，20:12、21:39 各一次），且**每次通知后 1 分钟内设备都能正常
   > 应答电量查询**（日志里紧跟着"设备重新上线"）——设备根本没睡，按休眠标离线只造成在线↔离线
   > 闪烁和脏历史。现降级为**仅记录**，不发离线。
   > `payload 0x00/0x01` 的真实语义待下次插拔充电线时对照日志确认（怀疑与充电状态变化有关）。
   >
   > **2026-10-08 追补：`payload=0x00` 当"触发器"用**（`MchosePlugin` 的被动解析 → `RequestConfirm`）。
   > 语义既然未定论，就**不能当离线证据**；但它可以触发一次**立刻核实**——基类在被动监听的空闲 tick
   > 上跑一次与轮询同款的 `13 4A 01` 查询：有应答就什么都不会发生，没应答就当场判离线。
   > 这把"键盘真关机"的发现从"60 秒轮询攒 3 次失败 ≈ 2~3 分钟"压到秒级。
   > 注意这条**不是**离线判据，只是把核实时机提前——真正的定性仍由查询结果决定。
   > 另外：**迈从协议里没有"连接状态"字段**（不像雷柏有 `[18].bit7`、北通有占位帧），
   > 所以主动查询失败是它唯一能判离线的物理依据；也因此 `0x00/0x01` 的语义将来即使搞清楚了，
   > 也只影响触发时机，不会变成新判据。
   >
   > **2026-10-08 22:13 真机样本（第一次支持"0x00=链路断"这个假设）**：键盘**关机**那一刻来的
   > 正是 `payload=0x00`（触发核实 → 1.75 秒后判离线）；键盘**开机**那一刻来的正是 `payload=0x01`
   > （0.34 秒后"设备重新上线"）。两者与电源状态严格对应。
   > 与 2026-10-06 那次"全天交替"并不矛盾——**如果**那次交替其实是**键盘空闲休眠/唤醒**
   > （无线键盘空闲会自己睡），一切自洽：休眠也算"链路断"，但 dongle 仍能应答缓存帧，所以
   > "每次通知后设备都能正常应答查询"。
   > **待验**：让键盘自然休眠（**不关电源**），看是否发 `0x00`、以及那时 `4A` 查询是否仍能应答。
   > 即便成立，`0x00` 也**仍然不该直接判离线**（休眠会闪）——现在"触发器 + 核实"的用法正好绕开了这个坑。

### 1.3.1 ⚠ 充电状态可能长时间冻结（dongle 缓存，固件行为）

**现象**（2026-10-06 晚，用户复报"已断开充电仍显示充电中"）：键盘空闲（无人打字）时，dongle 对
`4A` 电量查询返回**逐字节完全相同的缓存帧**——当晚 19:47–21:52 连续 2 小时每分钟都返回
`13 4A 01 00 02 63 10 … D3`（99% + 充电标志），而设备实际状态早已变化；21:53 前后键盘被唤醒
（按键）后才恢复真实读数（`62 01` = 98% 放电）。

**机理**：dongle 的 4A 响应 = 键盘最后一次上报的快照；键盘深度空闲时不与 dongle 通信，主机侧
无论怎么查都只能拿到旧快照。**拔充电线不会触发 dongle 缓存刷新**，这是固件行为，主机无法提前
感知。自发推送（0x05）与会话重建（05 01 开会话）后 dongle 会立即推一条状态——但它同样是缓存值
（21:21 会话推送仍是"充电中"），只是键盘唤醒后它会变成新值。

**应用侧对策**（已实现）：
- `DeviceManager.Upsert` 的变化判定**包含充电标志**——设备一旦改口（充电中↔放电），即使电量数字
  没变也立即刷新 UI/托盘/小组件并写历史（旧版漏判，界面要等下次电量跳动才自愈，正是本次 bug）；
- `0x02` 状态通知不再标离线（见 §1.3 复测）；
- 拔线后显示滞后到"键盘下次醒来"为止属预期，无法更快——可敲任意键让键盘唤醒，1 分钟内读数即刷新。

轮询实现：`MchosePlugin.PollKeyboardV1`（每分钟 1 条 4A 查询 + 顺带解析 0A 推送）；探测实现：`TryKeyboardV1`（05 01 开会话 → 4A 01）。

### 1.4 已证伪的通道（别再试）

- **feat8（Col06，feature 0x06）**：`06 <命令回显> <连接模式 01=有线/02=2.4G> 64 64 64 B5 6A`。[3..5] 恒为 0x64（=100），**不随电量变化**——旧版读出 100% 的错误来源。SetFeature 只是回显写入字节。
- **经典鼠标协议（feature 0x11）/ Rapou7 V2（64 字节 output 0x4D）**：此 dongle 物理上不支持——feature 通道数量为 0（HidD 返回 err=1）、输出只有 20 字节。Rapou7/offline-mchose 项目只覆盖迈丛**鼠标**（A7/L7/M7/AX5/A5/K7），不含键盘，不要再看它。（`0x3837` 世代接收器另当别论，见 §1.6。）
- **QHW 0x4D 报文**：WriteFile 报"参数错误"，此 dongle 不认（见 §2，那是新一代 dongle 的协议）。

### 1.5 会话排他（运维注意）

dongle 的配置会话一次只服务一个客户端。崩溃进程不关会话 → dongle 假死，**官方软件也连不上**；kill 持有进程或重新插拔恢复（详见 safety.md §2 事故二与 §4 应急恢复）。本应用与官方 M HUB 不要同时连。

### 1.6 鼠标 V2 世代（接收器 3837:100A / 3837:201B）—— 贡献者真机验证，本机未复测

`0x3837` 世代接收器在厂商接口上给 65 字节（64 数据 + 1 report ID），与老 G87 的 20 字节 0x13 通道不是一回事：**在这条通道上发键盘 `0x13` 帧没有意义**，只能走鼠标 V2 的 E2 状态帧。

**E2 状态帧（被动）**：Windows `ReadInput` 缓冲 `[0]` 是 report ID 前缀（`0x13`），**不参与取反**；其后 payload 逐字节 `^0xFF` 后：

| 取反后下标 | 含义 |
|---|---|
| `[0]` | 恒为 `0xE2`（帧识别位） |
| `[3]` | 充电位：`1` = 充电中 |
| `[4]` | 电量百分比 |

真机样本（A7 V2 Pro 接收器，68% 未充电）：
`13 1D FE FE FF BB FD FD F9 D6 BE C8 DF A9 CD DF AF 8D 90 FF FF 00 00 00`
→ 去前缀取反 = `E2 01 01 00 44 …`，`[3]=0x00` 未充电、`[4]=0x44`=68%。

**触发帧（写）**：接收器约 10 秒自推一次 E2；等不到时发一次 `0x11/0x06` 唤醒上报。

```
[0]=0x11（report ID，原样）  [1]=0xF9（=0x06^0xFF）  [2..]=0xFF（=0x00^0xFF）  补零到接口输出长度
```

官方 MOUSE_LEGACY 的 WebHID 写法是 `sendFeatureReport(0x11, "06 00×19" ^ 0xFF)`——**`data` 不含 rid**。Windows `WriteOutput` 要求 `buffer[0]` 就是 report ID 且**不取反**，照抄网页版把 rid 一起取反必写失败。

**型号识别**：官方 M HUB WEB 前端 `battery-monitor` 的 `getPassWord` / `KB_PW2MODEL` 把"接收器密码"映射到型号名；密码就是 V1 会话 ACK（`13 05 01 …`，布局见 §1.3）payload 的前 6 字节，即 ACK 的 `[6..11]`。已收录 18 个键（G87 / G87 V2 / K99 / K99 V2 / G98 / G98 Pro / X75 / X75 V2 / G75 Pro / G75 V2 / G98 V2 / UT98 / Z75 / Z75S / KX75 / GX87 / GX87 V2 / K87），全表在 `MchoseMouseCodec.ModelFromPassword`。产品名是泛化的「MCHOSE 2.4G Wireless」时用型号替换，显示成「迈从 xxx」。

**本机边界**：本机只有 G87 V1（`41E4:2001`），没有 A7 V2 Pro / G87 V2，鼠标链路只有单测与代码审查。贡献者（zi-ha）在 A7 V2 Pro 接收器（`3837:100A`）上抓到了 E2 帧与触发帧；G87 V2 接收器（`3837:201B`）在贡献者机器上走**键盘 V1 会话**（抓到 4A 应答 69%），但会话 ACK 的密码段是全 0，型号表匹配不到，显示名退回产品名。

**未知项**（别按猜测补）：E2 帧其余字节语义未定；充电位只区分"充电中/未充电"，没有"已充满"；型号表外的设备一律退回产品名。

耳机 V9 Pro 用的是另一个 VID（`291D:385D`），不在这条链路上，见 §12。

## 2. QHW 协议（新一代 dongle，M HUB WEB 前端逆向）—— 已实现备用

来源：官方 www.mchose.com.cn 的 M HUB WEB 前端 JS（QhwCmdQueueItem 类），适用于 0x3837 世代 dongle（官方通用 2.4G dongle = VID 0x3837&PID 0x3033，G87 V2/G75 V2/K87S/K99 V3 共用）。用户现款 41E4:2001 不适用，代码已备好（TryQhw），遇到新 dongle 直接用。

### 2.1 帧格式（report ID 0x4D）

```
[0]=0x4D [1]=ver=1 [2]=flags=3 [3]=payload长度 [4]=cmdLo [5]=cmdHi [6]=bizCode=0 [7]=seq [8…]=payload [8+len]=XOR(从[1]起到最后一个payload字节)
```

WebHID 侧 reportId 自动加首字节；Windows WriteFile 时 [0] 就是要写的 report ID。

### 2.2 命令表（来自官方 JS）

| 命令 | 含义 | 响应 payload |
|---|---|---|
| 0x0900 (2304) | getBaseInfo（连接后第一条） | [0..1]=VID le, [2..3]=PID le, [4]=maxProfile, [10]=连接(1有线/2无线), [11]=充电(0未充/1充电/2充满), [12]=电量%, [13]=gameSafeMode |
| 0x0901 (2305) | getFwVersion（参数 [0]=主固件 / [1]=RF 固件） | parseFwVersion |
| **0x0904 (2308)** | **getBattery** | **[0]=充电状态(0/1/2), [1]=电量%** |
| 0x0906/0x090D/0x0918/0x0921/0x0924 等 | 灯效/配置/宏/心跳 | 见 JS |

连接握手：report 0x4D，数据 `AA 55 AA 55 AA 55`（无 QHW 头、无校验），连接时发一次。

### 2.3 CZ 通道（同代键盘的批量配置协议）

帧：flag=0x55 / 响应 expect=0xAA，`[55, cmd, 0, chk, size, offsetLo, offsetHi, 0, payload…]`（chk 逻辑见 JS）。批量灯效/配置走这条。电量推送：dongle 自发 `[FA, FB, 07, 电量%, 充电标志]`。

## 3. 罗技 / 雷柏现状

### 罗技 Logitech (VID_046D) —— ✅ Bolt 真机验证（2026-10-08）；协议驱动 + 嵌入目录

HID++ 1.0/2.0 协议发现（无型号白名单）。电量级联：
`0x1004` Unified Battery → `0x1000` Battery Status → `0x1001` Battery Voltage → `0x1F20` ADC Measurement → 1.0 寄存器 `0x07`/`0x0D`。

嵌入资源 [`logitech-hidpp.json`](../../src/VigilWatt.Core/Plugins/Logitech/logitech-hidpp.json) 提供接收器槽位/报文偏好与毫伏曲线；**目录是补充不是白名单**——未知 PID 仍打开 HID++ 接口（默认最多 6 槽、有长则跳短）。

| 新设备类型 | 怎么扩展 |
|---|---|
| 新的 HID++ 鼠标 / 键盘 / 演示器（已有特征） | **零代码**——ping + GetFeature 自动发现 |
| 新的接收器族（确认 PID / 槽位 / 长短偏好后） | 在 JSON `receivers` **加一行** |
| 某 WPID 电压曲线与默认锂电差很大 | JSON `wpidCurves` + `voltageCurves` |
| 全新电量特征 ID，或根本不是 HID++ | **改 C#**（耳机 / Centurion / 仅 G HUB 等） |

蓝牙罗技走标准 GATT `0x180F`（`BleBatteryWatcher`），不在此插件。

**本机 Logi Bolt 接收器 `046D:C548` + MX Master 3S（2026-10-08）：**
- 必须走 20 字节长接口（usage `FF00/0002`，report **0x11**）；旁边 7 字节短接口（`0x10`）对 Bolt 鼠标不应答，应跳过（目录 `reportPreference=long`）。
- Unifying（`C52B`/`C532`）常只在短接口应答 → 目录 `reportPreference=short`，有短同伴时跳过长接口。
- 把 `0x10` 补零写进长接口 → 驱动 `ERROR_INVALID_FUNCTION`（与北通硬编码错 report ID 同类）。
- `Request()` 返回缓冲从 feature 字节起，**参数在下标 2**：GetFeature 下标 / 电量% / 充电态分别是 `resp[2]` / `resp[2]` / `resp[4]`（旧代码读 `resp[0]` 会把 feature 下标当成电量）。
- 发现 ping 醒着约 1s 才回，超时宜 ≥1.5s；设备名走 `GetFeature(0x0005)` 再 GetCount/GetChar；设备类型优先读接收器配对寄存器 `0xB5`（Unifying `0x2N` / Bolt `0x5N`），读不到再 `DeviceKindGuesser`。
- Unified Battery `0x1004`：**func 1 = GetStatus**（电量% + 充电态），**func 0 = GetCapabilities**（不能当电量）。组装请求必须 `(feature<<8)|(func<<4)`，写成 `|func` 会被 SwId 补丁抹成 func 0（真机曾把 Capabilities 的 15 误当电量，充着电也读不到 charging）。
- **实时充电**：插拔电时设备会发 HID++ 自发通知（`sw` 低 4 位=0，payload 与 GetStatus 同布局）。插件后台 `PumpNotifications` 只读不写，经 `StatusPushed` 即时 Upsert——不必等 60 秒轮询（与 Logi Battery Dashboard 同源）。未知 `devIdx` 的通知会当场补 ping 发现。
- 每次 `Attach` 按目录槽位数补扫尚未发现的索引（接收器上第二台不必等重启）。

**HID++ 报文层（字节级；实现见 `Plugins/Logitech/HidppIO.cs` / `HidppCodec.cs`）：**

| 报文 | 布局 |
|---|---|
| 短（7 字节） | `[0x10, devIdx, feature, (func<<4)\|sw, p0, p1, p2]` |
| 长（20 字节） | `[0x11, devIdx, feature, (func<<4)\|sw, p0..p15]` |
| 错误响应 | `data[0]` = `0x8F`（1.0）/ `0xFF`（2.0）；`data[1..2]` 回显请求前两字节；`data[3]` = 错误码 |
| 设备自发通知 | `sw` 低 4 位 = 0（本应用请求应答用 SwId `0x0B`，据此区分） |

**各特征的电量 / 充电编码（实现见 `HidppCodec.cs`）：**

| 特征 | 编码 |
|---|---|
| Battery Voltage `0x1001` | 大端毫伏 + flags；`bit7`=充电中、低 3 位 `1`=充满、`bit5`=危急 |
| ADC Measurement `0x1F20` | 大端毫伏 + flags；`0x01`=放电 / `0x03`=充电 / `0x07`=充满 |
| 统一充电状态码（`0x1004` / `0x1000` 共用） | `1`/`2`/`4`=充电中、`3`=充满、其余=放电 |
| 配对信息 `0xB5` 字节布局 | Unifying `0x2N`：参数区 `[3..4]`=WPID、`[7]`=kind；Bolt `0x5N`：`[1]`=kind、`[2..3]`=WPID（小端，交换后成大端） |

### 雷柏 Rapoo (VID_24AE) —— V2 世代 status-report7 协议 —— ✅ 插件已落地（纯被动）

**协议出处**（公开逆向，MIT，真机验证过，符合 safety.md 出处要求）：
- [pedro3z0/rapoo-software-linux](https://github.com/pedro3z0/rapoo-software-linux)：逆向自官方驱动 **A HUB 1.0.19** + 官方 Web 驱动 **hub.rapoo.cn** 抓包，VT0 Air Max（dongle 24AE:14A1）实测；
- [D3m0nZOnFire/mousectl](https://github.com/D3m0nZOnFire/mousectl)：VT3 PRO 一代（dongle 24AE:1231）实测。
- 官方设备表（pedro3z0 DEVICES.md）：VT3 PRO V2=14A5、VT0=1410、VT3 MAX=1417、VT0/VT3 Air=14A1 等。**本机 1412 不在表内**，但 PID 区段/帧特征同代 = VT3 二代 dongle（实测本机）。

**旧观测复核**：24AE:1412 的 `GetFeature(0x08) → 02 00…` 正是该协议 feature 8 应答通道的 **ACK 0x02 = Device Busy**；HID++ ping 无响应是正常的——雷柏不是 HID++ 协议。

#### 1. 状态心跳（电量的唯一来源）

dongle 每 ~3 秒自发推送 **input report 0x07（19 字节，hidraw 含 ID 视角）**，2.4G 和有线都在推：

| 字节 | 含义 |
|---|---|
| [0] | 0x07 |
| [1] | 低4位=连接方式（0=2.4G，2=有线）；高4位=sensor 类 |
| [2] | DPI 档位 0..6 |
| [3..4]/[5..6] | DPI X/Y（u16 LE） |
| [7] | **充电标志（本机实测校准 2026-10-05）：0x01=放电、0x02=充电**；充满态的值待采样（100% 时一律判充满兜底）。pedro3z0 文档此字节记为"0=有效"，与本机观测不符，以实测为准。与 mousectl 在 VT3 PRO 一代记录的 1/2 编码同族 |
| [8] | **电量 0..100**（有线=最后已知值，重插后瞬间 ~1% 属正常） |
| [9] | 背光模式 |
| [10] | 键扫率索引 |
| [11] | 轮询率码 |
| [12] | profile 索引 |
| [13..14] | USB PID（u16 LE） |
| [15] | 键/滚轮类型 |
| [16] | RF 类型 |
| [17] | sensor 模式预设 |
| [18] | bit7=RF 已连接，bit0..6=RSSI |

**电量没有查询命令**——官方驱动也是被动听心跳。充电标志已实测校准（0x01=放电/0x02=充电，见上表 [7]）；充满态的原始值待下次充满时看日志 `充电标志` 补全。

**实时更新**：`BatteryPluginBase` 认领后后台只读心跳，经 `StatusPushed` 即时 Upsert，不必等 60 秒轮询。**存活判据是该接口有没有在说话**（收到任何报文即算在线），详见下节。

#### 2. 其余通道（仅备查，本应用不使用）

- EEPROM 读/写：output report 0x06，帧 `[conn, 0xA4读/0xA5写, len, addr u32 LE, payload…]`（conn：0xA5=无线/0xFF=有线），应答走 feature report 0x08（`[08, ACK, echo…, payload]`，ACK 0x01=OK/0x02=Busy）。**电量不在 EEPROM**。
- VT3 PRO 一代（1231/4431）电量查询：report 0xBA，`[conn, 0xAA, 0, addr=0]` → 应答 `[0xBA, 充电态(1放/2充), %]`。**本机 1412 实测 WriteFile 拒绝 0xBA（描述符无此 ID），二代不走这条**，勿再试。

#### 3. 关键行为：鼠标停手 = dongle 静音，但**静音 ≠ 离线**（2026-10-08 修正）

鼠标停手/睡着后 dongle 不推心跳、鼠标接口也停报文，被动监听空转是**预期行为**（不是协议错/会话占死）。移动鼠标即恢复推送。

**但静音不能当离线判据**：0x07 是**活动驱动**的心跳——动鼠标时稳定 3.04s 一帧，一停手就静音，正常空档里 13~39 秒的间隙很常见（2026-10-08 实测 4 分钟内出现 5 次 >10s：13.3 / 18.2 / 26.1 / 35.3 / 39.5 秒）。旧版按"沉默 >12s → 离线"判，于是用户"鼠标一直在用"却看到掉线——只是某次 60 秒轮询（或手动刷新/改设置触发的补跑）正好撞进了空档。

##### 离线判定的两条腿（现行，2026-10-08 定稿）

**① 设备自己说断链**（主判据，本次新增）

`[18].bit7` 就是"RF 已连接"。**鼠标断电瞬间 dongle 会主动吐一帧 `[18]=0x7F`**
（bit7=0 且 RSSI=127，即"断链且无信号"），随后静音 **27.9 秒**才恢复：

```
21:38:38.564  雷柏 状态帧: ... RF=0x7F(bit7连接=False RSSI=127) 原始=…7F
21:39:06.454  雷柏 状态帧: ... RF=0xD2(bit7连接=True  RSSI=82)  原始=…D2   ← 恢复
```

这条帧的价值：**设备自己告诉你断链了**，比"靠静音计时猜"精确得多。

但 `bit7` 描述的是 **2.4G 链路**，不是"设备在不在"——关机、移出范围、受干扰都会翻 0。
所以**不直接判离线**，而是走延迟确认（`RapooPlugin.Offline.Confirm = 6s`，
机制在 `BatteryPluginBase` + `OfflinePolicy`）：真关机 → 没有恢复帧 → 6 秒后翻离线；
抖动 → 3 秒后的下一帧 bit7=1 就把候选撤销了（宁可漏判不可误判）。

> 窗口 **12s → 6s** 是 2026-10-08 用户拍板的（依据：心跳间隔实测 3.04s，6s ≈ 2 个周期）。
> 真机实测的"断链帧 → 标记离线"延迟：12s 窗口下是 12.4 / 12.2 秒，6s 窗口预期 ≈ 6 秒。
> 用户提过 3 秒，被否：3s 只等于 1 个心跳周期，正常丢一帧就会误判；而且鼠标停手时 dongle
> 本来就会静音，"断链后一直没有新帧"与"停手静音"在被动路径上无法区分。

**② 接口彻底不说话**（兜底）

存活判据 = **该接口有没有在说话**：被动监听收到**任何**报文都刷新 `LastPassiveAt`
（不只 0x07；该 vendor 接口上还跑着大量 0x00/0x04/0x05 报文）。
`RapooPlugin.Offline.Silence = 90s` 是"鼠标真关机/没电"的兜底，不是主要判据。

两条判据**独立生效，谁先满足谁算**，参数都装在本插件的 `OfflinePolicy Offline` 里
（`CountPollFailures = false`——本插件零写入，轮询恒返回 null 是协议形态，不是失联）。
帧解析与链路位判定都在 `RapooCodec`（纯函数，有单测）。

> **实测（2026-10-08 21:37~21:39 会话，用户断电重连鼠标+键盘）**：雷柏 39 帧心跳、
> 最大空档 27.9s、出现 1 次 `bit7=False`，全程 `标记离线` / `重新上线` 各 **0 次**
> ——旧逻辑（12s 静音）下这两次空档必然误报。

**附带观测（未定论）**：断电重连时 `[7] 充电标志` 由 `0x01` 变成 `0x00`（电量同时 94%→95%）。
本机此前只校准过 `0x01=放电 / 0x02=充电`，`0x00` 的含义待确认——可能是"刚上电/未充电"，
也可能 [7] 根本不是纯充电标志。下次复现时留意。

#### 4. 已证伪/勿再试

- HID++ ping（短/长、带/不带 ID）：雷柏无响应（非 HID++ 协议）；
- report 0xBA 电量查询（一代协议）：1412 描述符不含此 ID，WriteFile 报参数错误；
- LogitechPlugin 认领雷柏接口：已移交 RapooPlugin（`WritesEnabled=false`，纯被动零写入）。

### 弱水时砂 ROSE FIRST ANGEL（2.4G dongle = 38FF:0001）—— ❌ 2.4G 无电量通道（2026-10-05 完整勘察）

**身份澄清（修正旧记录）**：`ROSE FIRST ANGEL (VID_38FF&PID_0001)` 就是**2.4G dongle 本体**（USB 声卡 + HID 复合设备，MI_00=MEDIA 音频、MI_03=HID），不是耳机或无关设备。旧记录里的 `04F3:026F`（义隆 Elan）是另一台设备，与此耳机无关。官方配套软件 RoseLink（Flutter + BLE 自定义协议）与官方升级助手 first_angel_upgrade.exe 均已逆向。

**结论：2.4G dongle 模式下主机侧不存在电量数据通道。** 逐路证伪：

| 通道 | 勘察结果 |
|---|---|
| dongle MI_03 HID（usage 0x0C/0x01，in=3B，out=0，feat=0） | 只有耳机按键透传（音量/播放）；被动监听多次零帧 |

| 官方 0xAB OTA 协议 | 仅在耳机**OTA 升级模式**（重新枚举出 usagePage 0xFFAB 接口）可用；正常模式无处发送；官方工具也只做 OTA 不查电量 |

**官方升级助手协议出土（OTA 模式专用，备查勿日常使用）**：report ID 0xAB（64B），查询帧 `[0x92, seq, TLV...]`，TLV=`[type, len, data]`，type 1=版本 / 3=TWS / 4=状态 / 6=通道；单查 `[0x91, 01, type]`；OTA 握手 `CC AA 55 EE 12 19 E4`；OTA 数据头 `[0xA0, seq, filesize u32...]`。设备响应 `[0x47 'G', 0x4D 'M', cmd, len, payload...]`，cmd 0x87=原始日志 / 0x88=版本(ASCII) / 0x89=OTA 数据 / 0x8A=GUID / 0x8B=GUID 回传。芯片平台 AB123A（Actions），USB 侧电量命令**不存在**。

**RoseLink 电量通道**：BLE 自定义服务 `0000AE00`（AE01=notify 设备→App，AE02=write App→设备），设备协议族 rs_common_v2（FirstAngel 专属 `first_angle_receive_handler.dart`）。不走标准 0x180F。**耳机在 2.4G 模式下不发 BLE 广播**（系统 AEP 枚举 0 台）。

**2.4G 模式电量唯一官方途径 = 耳机语音播报**（不经主机）。主机侧与官方 App 侧均已确认无通道，**此设备在本应用中不提供电量显示，勿再投入**。

### 2026-10-06 主机侧复检（只读实测，结论不变）

用户复报"2.4G 读不到电量"，对 `38FF:0001` 做了一轮独立真机复检，全部只读、零写入：

### 2026-10-18 复检：描述符级确认 + 耳机 USB-C 直连零枚举

`scripts/probe-hid-caps.py`（只读）重取 MI_03：

```
UsagePage=0x000C Usage=0x0001   IN=3B  OUT=0B  FEATURE=0B
ButtonCaps: IN=9  ValueCaps: 0
  [in] 0x000C: E2/B6/B5/40/CF/EA/E9/CD    [in] 0x000B: 21（Hook Switch）
```

- **`FEATURE=0B` 是描述符级事实**：`HidD_GetFeature` / `IOCTL_HID_GET_REPORT(Feature)` 在 Windows 侧就被拒，**不存在"发了没回显"**——"GET_REPORT 回显设备信息"这类现象在本机永远观察不到。

- 耳机 USB-C 直连（线已确认可传数据）：**零枚举**——无新节点、无未知设备、`LastArrivalDate` 仍是开机时刻 → **该口正常状态只充电**。

- 蓝牙节点里的 `OTA1` 属于 **EDIFIER W820NB（`0C:AE:BD:C6:CD:A7`）**，与炽天使无关，别误认。
- 对照 Feaulle SHINE（`0124:FB01`）：其 MI_03 有厂商页 0xFF01 + 63B 双向 IN/OUT——**那台有主机→设备通道，本机没有**，两台的结论不可互推。

### 2026-10-18 绕过 HID 驱动直读端点 —— ❌ 同样证伪

前面所有结论都建立在"Windows HID 栈"之上，唯一没验证的是：**端点上有没被 HID 栈丢掉的数据**。为此用 Zadig 把 `MI_03` 从 `HidUsb` 换成 WinUSB（`oem40.inf`，libwdi 生成），用 pyusb 直读。全部只读，零写入。

**配置描述符（首次直读）**：`bNumInterfaces=4`——if0 UAC 控制、if1/2 音频流、if3 HID；if3 有 **两个 64 字节中断端点**（`0x82` IN、`0x02` OUT，`bInterval=1`）。

**原始 HID 报告描述符（47 字节，标准 GET_DESCRIPTOR，只读）**：

```
05 0C 09 01 A1 01 85 01 15 00 25 01 09 CD 09 E9 09 EA 09 CF 09 40 09 B5 09 B6 09 E2
95 08 75 01 81 02 05 0B 95 01 09 21 81 02 95 07 81 05 C0
```

8 个 consumer 位（Play/Pause、Vol±、Play、Menu、Next、Prev、Mute）+ 1 个 telephony Hook Switch + 7 位填充 = 2 字节载荷 + report ID = 3 字节。**描述符完整闭合：只有 Input，没有 Output / Feature / 厂商页。**

**直读 `0x82` 结果**：按键时只有 3 字节帧，与 HID 层完全一致（`01 01 00` / `01 00 00` / `01 40 00` / `01 20 00`）；**耳机断电再上电、重连 2.4G 期间零帧**——连"耳机是否连上"都不上报主机。

判据：`0x02` 这个 64 字节 OUT 端点物理存在，但描述符里没有任何输出报告，固件也没有向主机推状态帧的迹象 ⇒ **"绕过 HID 栈拿隐藏数据"这条路同样走不通**。加上 `FEATURE=0`，`38FF:0001` 的 HID 接口已无剩余可挖空间。

回滚：`pnputil /delete-driver oem40.inf /uninstall /force`（管理员）→ `pnputil /scan-devices`，Windows 自动装回 `HidUsb`。

（Windows 11 + 2.4G 接收器，2026-09-29，电量与充电状态均与官方客户端一致）。

### 4.1 接口地图

接收器是复合设备，4 个 HID 接口靠 usage 区分：

| 接口 | usage_page / usage | 用途 |
|---|---|---|
| **厂商** | `0xFF00` / `0x0003` | ⭐ **电量通道**（本插件只碰这个） |
| 鼠标 | `0x0001` / `0x0002` | 鼠标模拟 |
| 键盘 | `0x0001` / `0x0006` | 键盘模拟 |
| 手柄 | `0x0001` / `0x0005` | 手柄本体（XInput 呈现） |

### 4.2 帧格式

收发同构：`[report_id, header, payload…]`，header 一个字节拆两个 4 位字段：

```
bit: 7 6 5 4 | 3 2 1 0
     └ subcmd ┘└── cmd ─┘     header = (subcmd << 4) | cmd
```

命令表（官方客户端内置多型号脚本 `kp20d/kp40b/kp70/t9` 等共用同一族帧结构）：

| cmd | subcmd | header | 含义 | 方向 |
|---|---|---|---|---|
| `0x5` | `0x1` | **`0x15`** | **状态报告（含电量、充电状态）** | 请求 / 上报 |
| `0x5` | `0x2` | `0x25` | 按键/摇杆报告 | 持续上报 |
| `0x5` | `0x5` | `0x55` | 固件版本信息 | 请求 / 上报 |
| `0x2` | `0x1` | `0x12` | 读配置 | 请求 / 上报 |
| `0x2` | `0x2` | `0x22` | 写配置 | 请求 |

> ⚠️ 本插件**只发读类命令 `cmd=0x5`**（即 `02 15` 状态查询），**不碰写配置（`cmd=0x2`）**、不刷固件、不改灯效。

### 4.3 电量查询时序

1. **查询**：帧 `[report_id, 0x15, 0…]`，其余补零到接口输出长度（HID 驱动要求写满声明长度）。
   - ⚠️ **report_id 必须从接口的 HID caps 读**（`HidP_GetButtonCaps` / `HidP_GetValueCaps` → `HIDP_*_CAPS.ReportID`，
     见 `Hid/NativeHid.cs` 的 `ReadReportId`），**不能硬编码**：它是设备/型号自己的描述符决定的
     （鲲鹏20 厂商集合 = `0x02`，T9 = `0x01`/`0x04`/`0x05`）。
     写一个该接口没有的 report ID，HID 驱动直接返回 `ERROR_INVALID_FUNCTION`（"函数不正确"）——这正是"设备列表里不出现北通"的根因。
   - ⚠️ **用户态拿不到原始报告描述符**：`hid.dll` **不导出** `HidP_GetReportDescriptor`（实测 `AttributeError`；
     写成 P/Invoke 会抛 `EntryPointNotFoundException`，被 catch 吞掉后表现为"读不到描述符"）。
     hidapi 的 `get_report_descriptor()` 其实是拿 preparsed data **自己重建**描述符，不是 IOCTL。
     所以这里走 caps 的 `ReportID` 字段——它是 HID 规范里 report ID 的唯一权威来源。
     真机实测 T9 三接口 = `0x01`/`0x04`/`0x05`，与 hidapi 重建结果一致。
   - **写入长度**直接用 `HIDP_CAPS.OutputReportByteLength`，它**已含 report ID 那一字节**
     （T9 Col04 实测 16 = 15 数据 + 1 ID），不需要再 +1。
   - **report ID 取值约定**（`HidDeviceInfo.OutputReportId`）：`null` = 读不到；`0` = 该接口**不使用** report ID（报文首字节即数据、无 ID 前缀）；`>0` = 就是它。HID++ 长接口应为 `0x11`、短接口 `0x10`。
2. **响应**：`02 15 <电量%> <保留> <充电标志> …`
   - 整帧 `[2]` = 电量百分比（0~100 十进制；`0` 视为未就绪/占位，不接受）
   - 整帧 `[4]` **低 4 位** = 充电标志，非 0 = 充电中（高 4 位是保留位，勿误判）
   - 实测：`02 15 64 00 51 …` = 100% 充电中；`02 15 5D 00 50 …` = 93% 用电池

解析实现：`Plugins/Betop/BetopCodec.cs`（纯函数，单测 `BetopCodecTests.cs`）；轮询/探测：`Plugins/Betop/BetopPlugin.cs`。

### 4.4 T9 变体（`USB\VID_20BC&PID_5073`）—— 不响应查询，走被动状态流

真机（2026-10-06，Windows 11）实测：T9 的厂商接口（Col01/Col04/Col05，report ID `0x01`/`0x04`/`0x05`）
**对 `02 15` 查询全程无响应**（含"写一个接口、读全部三个"的路由测试），也不出现任何 `0x15` 帧。
取而代之：**dongle 在 Col04 上持续推**一帧固定结构的状态流，电量直接就在里面。
**实时更新**：基类被动听该流，电量/未连接占位帧经 `StatusPushed` 即时 Upsert（鲲鹏等仍靠轮询写 0x15）。

帧特征（识别用）：

```
04 0C 80 80 80 80 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 58
│  │                                                        └ byte23 = 电量
│  └ 整帧[1] = 可变状态位（**不是帧头**！实测见过 0x02 / 0x04 / 0x0C，无规律）
└ report ID（唯一稳定的识别特征：0x04 = Col04；Col05 摇杆流是 0x05、Col01 配置流是 0x01）
```

**电量编码（4-bit 等级 × 8，满值 120）**：byte23 只出现 8 的倍数，即"电量等级(0~15) × 8"。
换算：`percent = round(raw × 100 / 120)`。

| byte23 | raw | 换算 | 现场含义 |
|---|---|---|---|
| `0x78` | 120 | **100%** | 充满（北通助手显示**满格绿色**；充电后稳定在此值） |
| `0x58` | 88 | 73% | 手柄开机（实测 2 小时稳定在此值） |
| `0x50` | 80 | —— | ⚠ **不是电量**：dongle 在"手柄没连上（关机/休眠）"时推的**占位值**，见 §4.4.1 |

- 该字节 **不是** 直接的百分比（`0x78` = 120 > 100 已排除），也**不是** `raw & 0xF7`（曾一度以为 bit3 是充电标志，被"充电/断电后数值不变"推翻）。
- T9 状态流里**未观察到充电标志字节**，故 T9 一律按"用电池"返回；`percent >= 100` 由插件判为"已充满"。
- 其它 T9 旁路设备 `PID_5075`（"T9 For Wireless"）无 report ID、64 字节全 0、无响应 —— 与本通道无关，已排除。

#### 4.4.1 ⚠ `0x50` = "手柄未连接"占位帧（2026-10-06 晚实测，用户复报）

**现象**：用户报「我设备已经关闭了 只有连接器还在电脑上」，但列表里「北通 T9」仍显示 **67% 在线**。

**根因**：**手柄关机后 dongle 不会停止推流**，而是继续每轮推同一帧、只把电量字节换成固定的 `0x50`。
旧实现照单全收 → 手柄明明关了还报 67%。

**真机对照**（同一天同一台 T9，翻 app.log 全部 Col04 帧，一次例外都没有）：

| 时刻 | 帧 | byte[1] | byte[23] | 现场 |
|---|---|---|---|---|
| 15:13 ~ 15:18 | `04 02 80 80 80 80 … 58` | `0x02` | `0x58` | 手柄开机 |
| 15:19 ~ 15:30 | `04 02 80 80 80 80 … 50` | `0x02` | `0x50` | 手柄休眠 |
| 15:31 ~ 17:02 | `04 0C 80 80 80 80 … 58` | `0x0C` | `0x58` | 手柄开机（73%） |
| 17:03 ~ 17:12+ | `04 04 80 80 80 80 … 50` | `0x04` | `0x50` | **手柄关机，只剩 dongle** |

结论：**`byte23 == 0x50` ⟺ 手柄没连上**（开机的两段都是 `0x58`，关机/休眠的两段都是 `0x50`）；
`byte[1]` 在 `{0x02, 0x04, 0x0C}` 之间乱变，**不能当判据**。

**为什么只认 `0x50` 这一个值、而不是按"低位/标志位"猜**：`0x50` 与 `0x58` 只差最低位，因此有两种自洽读法 ——
① 等级×8（`0x50` = 等级 10 = 67%）；② 高 4 位是等级、低位 `0x08` 是"链路有效"标志（`0x50` = 等级 5 + 标志清零）。
两种读法下 `0x50` 都只可能是"没连上"（开机态永远是 `0x58`），所以认 `0x50` 是**零风险**选择；
而按"低位=标志"判，若实际是读法 ①，则所有偶数等级（`0x40`/`0x60`/`0x70`…）都会被误判离线 —— 等于打掉一半正常读数。
**宁可漏判、不可误判**，故只认 `0x50`。
> 留待验证：**充满（`0x78`）后再关机**，若 dongle 报 `0x70` 则读法 ② 成立，可据此把判据一般化成 `(byte23 & 0x08) == 0`。

**实现**：`BetopCodec.ParseT9Status` 返回 `T9Status(Percent, Charging, Linked)`，占位帧 `Linked = false`；
`BetopPlugin` 据此：探测阶段**仍算探测成功但电量留空**（基类按"无读数 = 离线"认领 → 列表显示「北通 T9 · 离线 · --%」），
轮询阶段 `RequestOffline` 立即标离线（不等 3 次失败 = 3 分钟）。手柄再开机后下一轮自动回到在线。
> 探测阶段"算成功"是为了**如实列出「离线」**（而不是让设备消失），不是为了省时间 ——
> 基类的 toProbe 列表在任何探测之前就收集完了，同一轮里其它候选接口照旧会被探测。
> 那 ~4 秒（`0x0001` 配置流 / `0x0003` 摇杆流 / `5075` 全零帧各一个 2 秒窗口）是**既有开销**：
> 旧版日志（17:19:30）同样是 `05 → 00 → 04` 三段。要消除得收敛 `IsCandidate` 或给失败路径加负缓存，尚未做。


### 4.5 为什么标准 API 读不到

接收器在与 Windows 的标准通道上把自己报告成"有线设备"：
`XInputGetBatteryInformation() → BatteryType = WIRED / BatteryLevel = FULL`。这**不代表真的满电**，
只是不走标准通道上报 —— 所以必须像本插件这样直接与厂商接口通信。

### 4.6 已知行为

- **手柄休眠时无响应**：按一下任意按键即恢复；此时插件表现为离线，属预期（与雷柏鼠标睡着同理）。
- **手柄关机、只剩 dongle 插着**：dongle 仍推流，但电量字节换成占位值 `0x50` → 插件判**离线**
  （列表显示「北通 T9 · 离线 · --%」），不会再把占位值当 67% 报在线。见 §4.4.1。
- **充电时电量显示 100%**：手柄自己上报的原始数据就是 100%（BMS / 充电电路把测量电压抬高），非解析错误；
  据充电标志判"充电中"，`percent >= 100 && 未充电` 判"已充满"。
- **官方客户端可同时开着**（工具作者实测不冲突；若遇到厂商接口被独占打不开，关掉官方客户端再试）。
- **协议可能随固件更新变化**；适配新型号一般只需改 report_id / 偏移（同一协议家族）。

### 4.7 安全与开关

- 写入受插件开关 `PluginEnabled["Betop"]` 控制（**默认开启**——查询即官方客户端自己用的只读命令，风险低）。
  ⚠️ **关掉只挡住轮询写入，不挡探测**：该开关经 `BetopPlugin.WritesEnabled` → 基类 `CanWrite` 生效，而**探测路径**（`BatteryPluginBase.RunProbe` → `BetopPlugin.Probe`）目前**仍会写帧**——「关掉即完全静默」尚不成立，**待修**（应让探测与轮询共用同一写入闸门）。
- 连续 3 次查询失败由基类自动熔断（**递增退避**：30 秒起、封顶 5 分钟，见 safety.md §3 规则 3）。
- 品牌级总开关 `PluginEnabled["Betop"]`（默认开）。
- 迈从插件已按 VID 排除北通接口（`MchosePlugin.IsCandidate`），避免对北通 dongle 发 QHW / 0x13 帧。

## 6. 英菲克 ZHEN（接收器 VID_1D57&PID_FA65）—— ✅ 被动电量帧已确认

### 6.1 实测身份与状态帧

英菲克官方 ZHEN 网页驱动在 2.4G 模式下通过 WebHID 连接。设备名为 `Inphic KP 8K`，VID/PID 为 `1D57:FA65`。Windows 将它枚举成多个 HID collection：系统控制 `0x0001/0x0080`（输入长度 2）、consumer `0x000C/0x0001`（长度 3）、电量输入 `0xFF00/0x0001`（输入长度 5，Report ID `0x03`）和厂商输出接口 `0xFF01/0x0002`（双向长度 64，Report ID `0x04`）。电量插件必须匹配 `0xFF00/0x0001` 的输入 collection；不能按网页显示的系统控制 collection 来筛选。


### 6.2 安全边界

## 14. MCHOSE A5 V2 Ultra（接收器 3837:100C）

仅匹配 `usage=FF01/0001` 的配置 collection。设备还有 `FF0B/0104`、键盘、鼠标和 consumer collection，都不是本插件的查询通道。它使用官方旧代鼠标反码 Feature 协议，不是现有 QHW，也不是 G87 的 `13 4A` 协议。

该 collection 最大 Feature 长度为 65，但单独的 report `11` 只有 **21 字节（含 ID）**。SetFeature 和 GetFeature 必须按 21 字节调用，不能按 collection 最大长度填充。`HidDeviceHandle` 为此新增可选 `reportLength`，其他调用保持原默认行为。

官方 `11 06 + 19 个 00` 的命令数据逐字节取反，report ID 不取反，因此实际发送：

```
11 F9 + 19 个 FF
```

发送后等待 Input 通知（实测开头 `13 1A F9`）再 GET Feature `11`；提前 GET 会读到未完成的命令回显。实现每次仅发送一次，最多等待 600ms，失败由基类熔断/退避处理，不追加其他命令。

本机 100% 放电响应（21 字节）：

```
11 F9 1B BE FE EE F9 FD F9 FF F6 9B FF 9B FF FF FF FF FF FF FF
```

除 report ID 外按字节 XOR `FF` 解码。`[2..3]` 为鼠标本体 VID、`[4..5]` 为本体 PID（小端）；样本为 `41E4:1101`，与 dongle 的 `3837:100C` 不同，官方设备表还列出 `41E4:1102`，后者未真机验证。`[11]` 解码后是百分比，`[12]` 解码后为充电状态（0 放电 / 1 充电 / 2 充满）。其他命令、本体 ID 不匹配、截断、百分比 >100 或充电值 >2 均拒绝。充电编码依据官方解析器，当前只真机确认放电。

统一由 `MchosePlugin` 按品牌管理，`PluginEnabled["Mchose"]` 默认关闭；内部 `MchoseMouseProtocol` 仅负责鼠标协议，不是独立插件。鼠标显示鼠标图标、过滤下界为 0；键盘仍显示键盘图标、保留原下界 2。鼠标失败探测冷却为 60 秒，避免合并后跟随键盘 15 秒发现节拍增加写入。

保留试用版 `mchosemouse:` 设备 ID，避免历史记录和自定义名称断开；归属解析将此前缀映射到 Mchose，关闭品牌时一并撤掉。配置加载/保存移除废弃的 `MchoseMouse` 开关，保留现有 Mchose 选择，不以型号开关自动授权整个品牌。键盘候选仅允许 `41E4:2001`、`3837:3033` 的已知尺寸厂商接口，A5 只走其精确接口，其他设备不接收迈从查询。当前不扩展到其他 A5 版本、蓝牙或有线模式。

## 15. Haute Adapter 4DS + DualSense（054C:0CE6）

本机接收器在 DS5 模式下使用 Sony 的 VID/PID，游戏控制器 collection 为 `usage=0001/0005`。同设备的键盘和鼠标 collection 不参与。不能只凭 Sony ID 就认领：先 GET Feature `F8`，仅当返回字符串以 `Haute42 ` 开头才继续。

本机固件：`F8 48 61 75 74 65 34 32 20 33 2E 32 33`，即 `Haute42 3.23`。随后只 GET Feature `F9`（官方网页的运行状态接口），原始样本：

```
F9 FB 80 00 00 00 00 00 00 00 00 00 46 00
```

包含 report ID 时，`[12]=0x46=70%`；`[12]=FF` 为手柄未连接，必须显示离线而非 0%。`[13]` 低四位为供电状态：0 放电，2 充满，其他非零值按官方网页解释为充电；高四位忽略。截断、报告 ID 不符或非 FF 的百分比 >100 均拒绝，不能夹到 100 后误报满电。

插件默认开启，`WritesEnabled=false`、`ProbeWrites=false`，不调用 SetFeature 或 WriteOutput，不读取/改写配置和固件更新接口。新设备参与 15 秒发现节拍，已认领后的状态每分钟刷新。仅验证 Haute42 3.23 的 DS5 模式；其他固件、原生 Sony 连接、DualSense Edge、Xbox/GIP 模式不在声明范围。

设备身份取官方 `readDeviceInfo` 的 GET Feature `FA`；官方 `fc=250`、`Wc` 取前 8 字节为芯片标识，注册标志另占一字节。Windows 响应含 ID 时 `[1..8]` 按原顺序转小写十六进制，组成 `haute:chip-<16hex>`；`[9]` 注册标志不参与身份。本机已读到 10 字节有效响应并确认重开后标识一致。截断、错误报告 ID、全零或全 FF 标识拒绝，不能让未知设备都落到一个固定 ID。

接收器重连可让路径从含 `&Col01` 变成不含 collection，甚至改变实例前缀；本机 ContainerId 也发生过变化，不能把这些值当芯片身份。新 ID 不受 USB 路径影响，恢复句柄时再次核对芯片标识；如果换成另一接收器，旧设备离线并在下次发现重新认领，不强行合并同型号设备。旧 `haute:<路径哈希>` 记录无可信物理身份映射，保留在历史页面，不再恢复成设备列表占位；不改写旧采样或按名称猜测归并，因此旧曲线与自定义名称仍属于原 ID。

三种新协议都保留真实 0/1% 的数值范围，因此基类读数过滤器的最小有效值允许由插件配置；现有插件仍使用默认下界 2，原有休眠占位保护不变。新协议继续使用原来的骤变过滤、低电量提醒和历史流程。

2026-10-19 21:03:50 的离线是连续三次查询失败触发，日志不是 `FF` 无线断开通知。随后独立 GET `F9` 返回 70%；同一原生 API 的 64/128 字节缓冲均成功，不能据此断言长度错误或手柄关机。旧版没有记录错误码，首次失败原因尚未定位。21:23:07 的运行日志已确认 Win32 1167 后重开成功。现实现读取失败时仅重开同一个已认领接口，重新确认固件和芯片身份后再 GET `F9`；成功替换句柄并释放旧句柄，否则保留失败计数与离线兜底，不改成永久在线。长期复验见 BACKLOG CR-74。

## 16. 雷蛇 Kraken V4（接收器 1532:056C）—— ✅ 已真机验证（2026-10-19）

### 16.1 接口与来源

`USB\VID_1532&PID_056C` 是 2.4G 接收器（官方清单里 `productId 1388 = 0x056C` 是 dongle，`wiredProductId 1387 = 0x056B` 是有线版；有线版无电池，不接入）。复合设备：MI_00 / MI_03 是音频，**MI_05 是 HID 控制集合**，共 5 个 collection：

| collection | usage | 报告长度 | 用途 |
|---|---|---|---|
| **col04** | `FF14/0001` | IN=64 / OUT=64 / FEAT=9 | ⭐ **电量通道**，report ID `0x02` |
| col01 | `FF13/0001` | IN=62 / OUT=62 | 另一条控制通道，本插件不碰 |
| col05 | `0059/0001` | FEAT=51 | 不参与 |
| col02 / col03 | `000C` / `000B` | IN=2 | 媒体键 / 耳机按键，不参与 |

**依据**：本机 Razer Synapse 4（`RazerAppEngine` 4.0.827）自身的运行日志 `%LOCALAPPDATA%\Razer\RazerAppEngine\User Data\Logs\products_1387_mw*.log` 记录了 `protocolAudio.getBatteryStatus` / `getDeviceChargingStatus` 的收发帧与"命令→描述"表；请求帧构造与应答校验取自其前端缓存里的 `AudioBillieT2Dongle` / `AudioMxicDevice` / `protocolAudio` 模块（`_createDataSendGeneral`、`_getElectronTransferInResult`）。取法见 [debugging.md](debugging.md) §1.6。只参考互操作协议，自行实现，未复制厂商代码。

### 16.2 查询帧（64 字节，report ID `0x02`）

| 字节 | 值 | 含义 |
|---|---|---|
| [0] | `0x02` | report ID |
| [1] | `0x00` | 方向：主机→设备 |
| [2] | `0x60` | 事务 ID（固定） |
| [6] | 头长 + 数据长 + 1 | 查询恒为 `0x04` |
| [9] | `0x80` | 经接收器下发给耳机（接收器自身命令为 `0x00`） |
| [10] | 命令 | 见下表 |
| [11] | `0x00` | 方向 |
| [12] | 数据长度 | 查询为 `0` |
| [62] | XOR([0..61]) | 校验和 |
| [63] | `0x00` | 填充 |

| 命令 | 含义 | 应答载荷 |
|---|---|---|
| `0x21` | Get Battery Status | 1 字节，0~100 直接是百分比 |
| `0x2A` | Get charging status | 1 字节：`0` 未充电、`1` 充电中 |

实测请求：`02 00 60 00 00 00 04 00 00 80 21 00 00 … C7 00`。

### 16.3 应答帧与实测样本

```
02 02 60 00 00 00 05 00 80 80 21 01 01 3F … 79 00     ← 63% 放电
02 02 60 00 00 00 05 00 80 80 2A 01 01 00 … 4D 00     ← 未充电
```

- `[1]` 状态：`0x02` 成功；`0x01` / `0x03` 官方解析为"重发"；其余失败。
- `[10]` 命令、`[11]` = `0x01`（设备→主机）、`[12]` 载荷长度、`[13..]` 载荷。
- **应答校验和 = XOR([1..61])**（不含 report ID；与请求从 [0] 起算不同，两帧真机样本逐字节核对）。

插件要求长度 64、report ID、事务 ID、状态、命令、方向、载荷长度、校验和全部匹配；电量 >100 或充电值 >1 一律拒绝，不做截断容忍或自动续读。

### 16.4 轮询、限频与离线

- **没有自发推送**：被动监听 45~60 秒零帧（Synapse 日志里的事件帧只在它自己的会话里出现），所以必须有源查询。
- **限频**：电池与充电是两条命令，按 safety.md §3 规则 4 每轮只发 1 帧，插件按设备交替 ⇒ 两项各自约 **2 分钟**刷新一次（60 秒轮询）。
- 探测只发 1 条电池查询；认领后按上面的交替节奏。关闭 `PluginEnabled["Razer"]`（默认 false）后探测与轮询都不发帧。
- 充电只观察到 `0` / `1`：`1` = 充电中；`0` 且 100% 按公共规则记"已充满"；其余值保留 `Unknown`，不猜。
- 连续 3 次无应答走基类熔断 + 递增退避；设备移除由基类释放句柄。
- 未验证：蓝牙模式、Kraken V4 之外的雷蛇耳机、其他固件版本。
