## 2. 传输层：官方怎么认设备

每个型号脚本启动时调用：

```js
betoplib.Invoke("JoypadConnHelper", "RegisterDev2", 0x20bc, JOYPAD_PID, 0xff, 0x3, -1, 64, "", "", "");
betoplib.Invoke("JoypadConnHelper", "RegisterAlterDev", 0x20bc, DONGLE_PID, 0xff, 0x3, -1, 64, "", "", "", 0);
betoplib.Invoke("JoypadConnHelper", "SetHidWriteDelay", 16);
betoplib.Invoke("JoypadConnHelper", "SetHidWriteEnc", 0x0);
betoplib.Invoke("JoypadConnHelper", "InitThreads");
```

参数含义：`VID, PID, usagePage, usage, reportId, reportLength`。**`reportId = -1` 表示「自动」**
——由原生层从 HID caps 读，不硬编码。这和我们 `Hid/NativeHid.cs` 的 `ReadReportId` 是同一套思路，
也解释了为什么硬编码 report id 会 `ERROR_INVALID_FUNCTION`。

### 2.1 三套接口页（不是一套）

| 代际 | usagePage / usage | 报文长 | 典型型号 |
|---|---|---|---|
| 鲲鹏 / 盘古 | `0x00FF` / `0x0003` | 64 | KP20/40/50/70 全系、PG01A 部分 |
| 宙斯系 | `0xFF00` / `0x0001`、`0x0002`、`0x0003` | **24** | 宙斯2（含我们的 T9 5073）、宙斯Pro |
| 盘古（另一路） | `0xFF80` / `0x0001` | 64 | PG01A |
| 项目机 | `0xFF7A` / `0x0001` | 64 | 海心桥（hh30） |
| **鲲鹏50 第二身份** | `0xFF00` / `0x0001` | 64 | KP50 全系，但 **VID = `0x0517`**（不是 `0x20BC`） |
| 老一代 | `0x0003` / `0x0002` | 64 | 阿修罗 / 斯巴达 / 蝙蝠 |

> ⚠️ **VID 不止 `0x20BC` / `0x20DD`**：KP50 系列（`kp50p/kp50c/kp50d1/kp50d2`）额外注册
> `RegisterDev2(0x0517, 0x5350, 0xff00, 0x1, -1, 64)`。我们的目录和 `betop.protocols.json` 的 `vendors`
> 只有 `0x20BC`/`0x20DD`，接 KP50 时会漏。另外这一路是 **`0xFF00` 页 + 64 字节**，
> 说明「页」和「报文长」不是一一对应的，判据必须按三元组而不是单看页。

> ⚠️ 现有 `betop.protocols.json` 只认 `0x00FF`（及颠倒写法）。**宙斯系走的是 `0xFF00` + 24 字节**，
> 判据里没有这条，所以 5073/5074/5076/5077/5104-5107 这批宙斯设备在「接口页」这一步就不该命中——
> 现在能工作是因为 T9 的 `0x04` 帧恰好落在 `0xFF00` 页且我们另有专门分支。全量接入时必须按页分流。

### 2.2 `0x20DD` 是什么

官方对 **同一 PID** 同时注册 `0x20BC` 与 `0x20DD` 两个 VID（见 `kp20.js` 的 `RegisterDev2(0x20dd, JOYPAD_PID, ...)`）。
`0x20DD` 不是新型号，是**同一设备的另一套 USB 身份**（底座 / 配置口）。这解释了 §1.8.4 里
「`20BC:5130` 正常、`20DD:5130` 只回 `02 CD`」——两个身份对外暴露的帧不是一回事。

## 3. 帧格式与命令表

### 3.1 帧头

```js
let header = hextoChar(data.substr(2, 2));   // 第 2 字节；第 1 字节是 report id
let cmd    = header & 0xf;
let subcmd = (header >>> 4) & 0xf;           // header = (subcmd << 4) | cmd
```

组帧（官方写法，`kp20d.js`）：

```js
let data = chartoHex(CONFIG_REPORT_ID);      // 0x02
data += chartoHex(0x5 | (0x5 << 4));         // 0x55 = 固件信息请求
sendPack(devid, "", data);
```

**与我们现有实现完全一致**。注意官方**只发 2 字节**（`02 15`），补零到报文长是原生层做的。

### 3.2 命令表（按官方实际发送统计，65 个脚本汇总）

| header | cmd/sub | 语义 | 出现型号数 |
|---|---|---|---|
| `0x13` | 3/1 | 读配置类 | 32 |
| `0x14` | 4/1 | 读配置类 | 32 |
| **`0x15`** | **5/1** | **状态报告（含电量、充电）** | **32** |
| `0x16` | 6/1 | 配置类 | 32 |
| `0x17` | 7/1 | 进入工厂模式 | 29 |
| `0x18` | 8/1 | 状态报告（新一批型号） | 7 |
| `0x23` | 3/2 | 写配置类 | 32 |
| `0x25` | 5/2 | 按键报告（持续上报） | 27 |
| `0x27` | 7/2 | 工厂 | 85（含重复） |
| `0x2F` | f/2 | 特殊（KP50 系） | 4 |
| `0x31` | 1/3 | 对端 MAC | 29 |
| `0x33` | 3/3 | 配置 | 13 |
| `0x35` | 5/3 | 状态报告扩展 | 27 |
| `0x36` | 6/3 | 配置 | 29 |
| `0x37` | 7/3 | 工厂 | 58 |
| `0x45` | 5/4 | 状态报告扩展 | 29 |
| `0x55` | 5/5 | 固件版本 | 29 |
| `0x65` | 5/6 | 信息报告（PG01A） | 1 |

接收侧语义（源码注释原文）：

- `cmd 0x1` = 同步（当前模式 / 档位）
- `cmd 0x2` = profile 操作（读 / 写配置）
- `cmd 0x5` = 状态报告；`subcmd 0x1` 状态、`0x2` 按键、`0x5` 固件信息
- `cmd 0x7` = 工厂模式
- `cmd 0x8` = 状态报告（新）
- **`cmd 0xD` = 全局配置报告**（见 §5.3）

> 结论：**我们只发 `0x15` 是对的**。官方 32 个型号都发它，`getBaseInfo()` 在同步循环里周期性调用。

## 4. 电量字段：三代三种读法

### 4.1 鲲鹏 / 盘古系（`0x00FF` / `0x0003`，64 字节）

`kp20d.js`（KP20D，已真机验证的 5158/5159）：

```js
appset.baseinfo.bat_level    = hextoChar(data.substr(4, 2));           // 第 2 字节 = 百分比 0~100
appset.baseinfo.charge_state = (hextoChar(data.substr(8, 2)) & 0xf);   // 第 4 字节低 4 位 = 充电
```

**和我们 `BetopCodec.ParseStatus` 完全一致** ✅

但型号之间有差异，必须注意：

| 脚本 | 充电字段写法 | 含义 |
|---|---|---|
| `kp20d.js` / `kp20dl.js` / `kp20eb.js` / `kp40d.js` / `kp70*.js` / `pgv1.js` | `data[4] & 0xf` | 低 4 位 |
| **`kp20.js`（KP20A）** | `data[4]`（**整字节，不取低 4 位**） | 高 4 位是别的标志 |
| `kp20.js` / `kp30.js` / `kp40.js` / `kp401.js` / `kp40v1r.js` | 无 `charge_state` 解析 | 该型号不报充电 |

→ 全量接入时「充电」要按型号分支，不能一律 `& 0xf`。现有实现只验过 5158（`& 0xf` 路径），
碰到 5125/5126/5127/5128 会读错。

### 4.2 宙斯系（`0xFF00`，24 字节）——**我们目前读错了**

`t9.js` 注册的 PID 包含 **0x5073**，正是我们的 T9。它的状态帧按**位域**解析：

```js
var extkeyevent_o = {
    batlevel: 3, reserve1: 1, volup: 1, voldown: 1, headphone: 1, mode: 1,   // byte0
    lx: 8, ly: 8, rx: 8, ry: 8, lt: 8, rt: 8,                               // byte1~6
    up: 1, down: 1, left: 1, right: 1, start: 1, back: 1, ls: 1, rs: 1,     // byte7
    lb: 1, rb: 1, home: 1, record: 1, a: 1, b: 1, x: 1, y: 1,              // byte8
    m1: 1, m2: 1, m3: 1, m4: 1, m5: 1, m6: 1, ai: 1, reserve2: 1,           // byte9
    kb: new Array(64).fill(1),                                              // byte10~17
    mouse_left: 1, mouse_right: 1, mouse_mid: 1, reserve3: 5,               // byte18
    mouse_x: 8, mouse_y: 8, mouse_wheel: 8,                                 // byte19~21
    lt_level: 1, rt_level: 1, mouse_mode: 1, connect_24g_fail: 1,
    dongle_mode: 1, program_mode: 1, connect_24g: 1, shell_flag: 1,         // byte22
};

appset.baseinfo.bat_level = [0, 50, 80, 100, 100][extkeyevent.batlevel];
```

`convProfile` 是 **LSB-first** 打包（`tmp = (tmp >> bitoff) & mask`），所以：

- **电量 = 帧第 1 字节（raw[1]）的低 3 位**，取值 0~4，映射 `[0, 50, 80, 100, 100]`
- **帧第 23 字节（raw[23]）= 状态标志字节**（`connect_24g` / `dongle_mode` / `program_mode` …），**不是电量**

而我们现在的实现（`BetopCodec.ParseT9Status`）把 **raw[23] 当「等级×8」算百分比**。
真机日志把这件事钉死了：

| 日期 | raw[1] | raw[23] | 我们现在报 |
|---|---|---|---|
| 10-29 19:25 | `0x03` | `0x58` | 73% |
| 10-29 20:38 | `0x02` | `0x58` | 73% |
| 10-30 19:37 | `0x00` | `0x10` | 13% |
| 10-30 19:39 | `0x02` | `0x58` | 73% |
| 10-31 10:51 | `0x00` | `0x10` | 13% |

248 条样本里 **241 条 `raw[23] = 0x58`（旧实现报 73%）、7 条 `0x10` 空帧（报 13%）**——一块用了三天的
电池纹丝不动，本身就不合理；而 raw[1] 在这批样本里只有 `0x03`（73 条）/ `0x02`（168 条）/ `0x00`（7 条）
三种取值。按官方口径，这三者分别是 **100% → 80% → 0%（未开机）**。

**另外两个被推翻的旧结论**：

- `0x78` 曾判为「满电」：`0x78 ^ 0x58 = 0x20` = **bit5 = `program_mode`**。0x78 更可能是「处于编程/宏模式」，
  与电量无关。
- `0x50` / `0x10` 判「未连接」：按位域，`0x50` = bit4+bit6、`0x58` = bit3+bit4+bit6，**差别只有 bit3**；
  `0x10` = bit4、`0x18` = bit3+bit4，同样只差 bit3。**bit3 才是「链路有效」位**（0x58/0x18 置位、0x50/0x10 清零），
  与「开机 / 关机」完全对应。也就是说现有的占位值特判可以换成读位——更稳、也不用逐个值登记。

> ⚠️ 保留意见：厂商把这一位命名为 `connect_24g_fail`，与实测极性相反（置位=已连上）。
> 位名不可全信，**极性以实测为准**。落地前建议做一次 15 分钟对照：官方客户端界面显示的百分比
> vs 同刻我们的 raw[1] 低 3 位。

### 4.3 老一代（阿修罗 / 斯巴达 / 蝙蝠）

`bat_level` 在第 5 或第 6 字节，**没有充电标志**，且多为有线（USB 供电，无电池上报）：

| 脚本 | 电量字节 | 备注 |
|---|---|---|
| `a1_ns.js`（阿修罗2NS） | 5 | |
| `axl2_new.js` / `axl2prow_new.js` / `bd2w.js` / `sbd2.js` | 6 | |
| `sbd3*.js`（斯巴达3） | 由变量 `bat` 赋值，非直接偏移 | 需单独看 |

这批设备**不建议纳入电量接入范围**（无电池或无线型号极少），成本高收益低。

## 5. `02 CD` 是什么（CR-106 结案）

`t6p2a.js`（宙斯 Pro）里有唯一一处 `cmd 0xD` 处理：

```js
else if (cmdtype == 0xd) {
    appset.globalconfig.highfre_flag = hextoChar(data.substr(4, 2));
    appset.globalconfig.disglobal_l = hextoChar(data.substr(6, 2));
    appset.globalconfig.disglobal_r = hextoChar(data.substr(8, 2));
    appset.globalconfiginit = incSeq(appset.globalconfiginit);
}
```

**`cmd 0xD` = 全局配置报告**（高频标志、左右摇杆全局死区），不是电量。

所以 `02 CD 09 0A 08 08 …` 的定性是：**dongle 在报自己的全局配置**。
其余 64 个脚本（含鲲鹏全系）**根本不解析 `cmd 0xD`**——官方自己也把它丢掉。

**对 VigilWatt 的结论**：`20DD` 那几个接口不该当电量口。
- 不要再为 `02 CD` 补解析器（它没有电量）
- 现有「探测失败 → 设备不进列表」是**正确行为**，不是缺陷
- CR-106 可以从「电量格式未知」改判为「**不是电量帧，忽略**」；`20DD` 仅作为身份存在即可
  （已按此口径改文档，见 §10.2；BACKLOG 里仍是 `open`，结案要人工确认）

## 6. 写入加密：只影响写，不影响读

8 个脚本调用 `SetHidWriteEnc(0x1)`（`kp20` `kp40` `kp401` `kp40b` `kp40b1` `kp40b1w` `kp40b2` `kp40v1r`），
原生层链接 `libmcrypt` 做加解密。

**关键判断**：这些脚本的**读**路径仍然直接按明文解析（`kp20.js` 里 `data.substr(2,2)` 直接取 header，
没有解密步骤）→ **读方向是明文，加密只作用于写方向**。

对我们的影响：

- 2.4G 广播 / 被动流：**零影响**（纯读）
- 有线静默接口（要发明文 `02 15`）：**可能有影响**——`enc=0x1` 的型号可能不认明文写

而我们唯一验证过的有线型号 5158（KP20D）恰好是 `enc=0x0`；未验证的 5125/5126/5127/5145 都是 `enc=0x1`。
**这正好解释了为什么这几台的有线通道一直没人验成功。**

⚠️ 更麻烦的是：**同一 PID 可能对应两个脚本、enc 不同**（`0x5125` 同时被 `kp30.js`(`enc=0x0`) 与
`kp40.js`(`enc=0x1`) 认领）。所以 **enc 不能按 PID 判定**，只能在真机上试：明文 `02 15` 有回帧就走明文，
无回帧再考虑逆向加密。

## 7. 与现有实现的差距

| 项 | 现状 | 官方 | 影响 |
|---|---|---|---|
| 接口页判据 | 只认 `0x00FF` | 还有 `0xFF00`(宙斯)、`0xFF80`(盘古)、`0x0003`(老一代) | 宙斯全系、盘古部分接不进 |
| T9 电量字节 | raw[23] × 100/120 | raw[1] 低 3 位 → `[0,50,80,100,100]` | **读数错误，恒定 73%** |
| T9 在线判定 | 特判 `0x50` / `0x10` | raw[23] 的 bit3 | 换固件就失效 |
| 充电字段 | 一律 `& 0xf` | 鲲鹏系 `& 0xf`，KP20A 整字节，部分型号无 | 5125/5126 会读错 |
| PID 覆盖 | 运行目录 33 条（30 个不同 PID） | 66 个 PID / 118 条注册 | 官方 66 个 PID 已入目录的 `officialDevices`（P1-A），运行目录仍 33 条，**未认领的 36 个 PID 是有意为之** |
| `02 CD` | 待解（CR-106） | cmd 0xD 全局配置，官方也忽略 | 可以从待办里删掉 |
| 报文长 | 按 caps 读 | 64 / 24 两种 | 已正确（走 caps）✅ |
| report id | 从 caps 读 | `-1` 自动 | 已正确 ✅ |

## 8. 落地建议（按优先级）

**P0 — 修 T9 读数（影响现有用户可见数据）**
1. `BetopCodec.ParseT9Status` 改为 `percent = T9LevelMap[raw[1] & 0x07]`，映射 `{0,50,80,100,100}`
2. 在线判定改读 `raw[23] & 0x08`（bit3 = 链路有效），保留 `0x50`/`0x10` 作为兼容兜底
3. 补单测：用 §4.2 表格里 5 条真机样本钉住
4. 发版前做一次与官方客户端界面的百分比对照

> **落地状态（2026-11-16）**：1、3 已完成；**2 未做**——本轮只修电量解析，按任务要求保留原占位帧
> 判定、不改在线/离线与轮询行为；4 待真机对照。

**P1 — 补全设备目录**
1. 把附录 A 的 66 个 PID 并进 `betop-catalog.json`（[betop-official-client.devices.json](betop-official-client.devices.json) 已备好机器可读版）
2. 型号名直接用厂商 `title`（「北通鲲鹏70 AI旗舰」等），比产品串猜更准
3. 冲突 PID（5125/5127/5145/5146）保留「型号由产品串判定」，因为**厂商自己也是两个脚本认领同一 PID**

> **落地状态（2026-11-16，P1-A）**：1、2 已完成，但落在 `officialDevices[]` 而不是运行时的 `devices[]`——
> 认领集合、`group`、能力声明、协议判据全部未动（理由见 §10）。3 保留。

**P2 — 全量接入的架构改动**
1. `IsCandidate` 改成按 `(usagePage, usage, reportLength)` 三元组匹配，而不是只看页
2. 协议规格拆成三代：`betop-status15`(64B 鲲鹏)、`betop-zeus-keyevent`(24B 宙斯)、`betop-legacy`
3. 充电字段按型号表分支（附录 A 的「充电字节」列）

**不做**
- 不解析 `cmd 0xD`（无电量）
- 不逆向写加密（我们不发写帧；有线型号优先走「能读就读，读不到就离线」）
- 不接入老一代阿修罗/斯巴达/蝙蝠（无电池通道）

## 10. P1-A 复核结果（2026-11-16）

本节是**对上面结论的二次核对**，不是新逆向。做法：用脚本把附录 A 与
[betop-official-client.devices.json](betop-official-client.devices.json) 的 118 条注册逐条比对
（PID 集合、型号代码、标题、脚本、接口页、usage、报文长、写加密）。

### 10.1 核对通过

| 项 | 结果 |
|---|---|
| PID 集合 | 附录 A 66 行 ↔ 注册表 66 个唯一 PID，**双向无差集** |
| 型号代码 / 官方标题 / 脚本名 | 66/66 一致 |
| 接口页 / 报文长 / 写加密 | 66/66 一致（合并口径下） |

### 10.2 核对中发现、但没写进目录的问题

| # | 问题 | 影响 |

| 1 | `0x5161`（盘古）两套身份接口页不同：`20BC` 只注册 `0xFF80/0x01`，`20DD` 只注册 `0x00FF/0x03`；同族 `0x5162` 两边都是 `0xFF80` | 按"三元组"判据接入时，这两个身份会落到不同分支；原因未查明 |

### 10.3 为什么 66 个 PID 没并进运行时的 `devices[]`

`ProtocolEngine.Resolve` 是**目录优先**：`devices[]` 里有的 `VID:PID` 会先用目录定协议，再校验接口形态。
把这 66 个 PID 直接写进 `devices[]` 会有两个后果，都不是本阶段想要的：

1. **新设备被认领**：`0x0517:0x5350`（vendor 不在 `vendors` 里，今天不会认领）、`0xFF80` 页的盘古、
   `0xFF7A` 页的海心桥——一旦进目录就会开始探测、出现在列表里，而它们的电量解析还没验过。
2. **显示名变化**：今天靠 fallback 认领的宙斯系 PID 会从「北通手柄 (VID:PID)」变成官方标题，
   这属于运行时行为变化，不该夹在"只补目录"的提交里。

所以 P1-A 的做法是：**同一份 JSON、两层数据**。`officialDevices[]` 只记录事实与状态，
`devices[]` 保持 33 条条目不动（只更新了 3 条 `note` 文案，见 betop-catalog.md §3），认领集合与行为零变化。
P1-B 再按协议族把型号逐条迁进 `devices[]`，每迁一条都要先有真机或明确判据。
