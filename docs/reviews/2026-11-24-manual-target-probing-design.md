# 手动目标探测设计（2026-11-24）

> 状态：设计稿，待审查；未实施。
>
> 性质：对 M2 主动查询治理中“手动目标探测”路径的补充与修订。
>
> 基线：`dev` 分支 `447def5`。仓库内未找到原《M2 主动查询：手动目标探测方案》，本文按补充稿整理为可执行设计；原方案未修改部分以 [主动查询安全规范](../architecture/active-query-safety.md) 为准。

## 1. 目标与边界

手动目标探测用于自动识别无法确认目标时，由用户明确选择目标，执行一次范围受限、只读、可审计的已知查询。

它不是全面主动化，不替代自动发现，也不替代设备身份确认和能力证据审核。

最终行为：

`默认被动 → 自动识别 → 无法确认时等待用户 → 用户指定目标 → 检查全部授权条件 → 执行已知只读探测 → 记录设备实例证据 → 只更新实际验证的能力`

禁止：

- 未知命令枚举、Report ID 扫描、任意字节猜测；
- 未经审核的协议 fallback；
- 失败后自动扩大探测范围；
- 后台循环探测；
- 为手动探测新增绕过现有授权的通道；
- 新增一套独立的通用主动查询框架。

## 2. 身份模型

### 2.1 三个概念

| 概念 | 含义 | 不能做什么 |
|---|---|---|
| **TargetSelection** | 用户本次选择要探测的接口、接收器或槽位 | 不能直接证明型号、设备本体或协议身份 |
| **DeviceIdentity** | USB 枚举、协议自报、接收器/槽位等实际身份 | 不能因为用户选了品牌/型号就写成已确认 |
| **ProbeResult** | 对指定目标执行探测后实际观察到的结果 | 不能自动替代完整设备身份 |

关系：

`TargetSelection → ProbeExecution → ProbeResult → Evidence`

`DeviceIdentity` 只由实际身份信息建立或更新。禁止把 `TargetSelection` 直接写入 `DeviceIdentity`。

### 2.2 身份来源

- `Usb`：USB 枚举身份；
- `Reported`：协议主动上报的身份；
- `Receiver`：接收器及槽位身份；
- 其他已有的可靠身份来源。

身份来源必须保留实际证据。接收器槽位只能证明“目标槽位”，不能直接证明槽位上的具体型号。

## 3. 探测授权

一次手动探测必须同时满足：

1. 用户明确选择本次目标；
2. 目标接口当前真实存在；
3. 接口指纹满足对应插件已登记的匹配条件；
4. 对应插件已启用；
5. 当前插件的主动通信授权状态允许本次操作；
6. 用户显式点击探测按钮或完成等价的一次性确认；
7. 对应插件提供经过审核的探测计划；
8. 探测计划只包含已登记的只读查询；
9. 运行时未处于熔断、退避或官方客户端让位状态；
10. 目标接口、槽位和连接方式未发生失效或冲突。

任何一项不满足都必须拒绝发送，并记录具体原因。拒绝时不得静默降级到其他协议、接口或目标。

### 3.1 插件开关

- 插件开关仍是唯一持久授权入口。
- 不新增第二个全局写入开关。
- 用户选择目标和点击探测按钮属于本次操作授权，不构成持久授权。
- 如果现有开关只控制插件加载/展示而不控制主动通信，必须先核对真实语义，不能擅自把插件启用解释为主动通信授权。

### 3.2 只读查询与配置写入

允许的只读查询：设备信息、电量、充电、连接状态、DPI、回报率配置、其他已审核的设备状态。

禁止的配置写入：设置 DPI、设置回报率、灯效、设备参数、其他改变设备配置或运行状态的操作。

手动探测不得因为用户明确选择目标而获得任何配置写入权限。命令是否只读必须审核其实际语义，不能只看名称或调用位置。

### 3.3 自动发现与手动探测

| 操作 | 自动发现 | 手动探测 |
|---|---|---|
| USB/HID 枚举 | 允许 | 允许 |
| 被动接收设备上报 | 允许 | 允许 |
| 已登记主动只读查询 | 按现有门控 | 满足全部条件后允许 |
| 未知命令/命令枚举/Report ID 扫描/字节猜测 | 禁止 | 禁止 |
| 配置写入 | 按现有授权 | 不获得额外权限 |

自动发现阶段继续保持未验证设备零主动查询。手动探测是一次受控只读例外，不是全面主动化。

## 4. 探测计划 ProbePlan

每个品牌插件自行提供经过审核的探测计划。UI 不允许自由构造命令，也不允许用户输入命令码、Report ID 或任意字节。

### 4.1 必要信息

- 唯一计划标识；
- 所属品牌插件；
- 适用协议及版本；
- 适用设备接口条件；
- 适用连接方式；
- 目标类型：设备本体、接收器或槽位；
- 是否要求明确槽位；
- 允许执行的查询操作；
- 每项操作的命令及必要参数；
- 只读语义审核结论；
- 单次操作最大发送次数；
- 整个计划最大发送次数；
- 单项操作超时；
- 预期响应类型；
- 响应解析及有效性判断；
- 失败处理方式。

### 4.2 帧与次数限制

- 只允许预先登记的已知查询帧。
- 所有命令必须能追溯到现有插件实现、可靠参考实现或实际协议证据。
- 失败后立即结束本次探测。
- 不得自动更换命令、切换协议、切换槽位或扩大接口范围。
- 不得后台循环探测，也不得因一次失败自动启动第二次完整探测。
- 用户重新探测必须重新执行明确操作，并重新检查全部授权条件。

### 4.3 运行时检查

执行前和执行过程中必须检查熔断、退避、官方客户端让位、设备断开、接口访问冲突和插件授权状态。条件不再满足时立即停止后续操作，不得为完成手动探测而绕过已有安全机制。

### 4.4 不新增通用策略层

不新增通用 `ActiveQueryPolicy`，不另建第二套协议实现体系。探测计划复用现有厂商插件、协议解析器、接口匹配和主动查询门控。

## 5. 证据与能力状态

### 5.1 能力状态不变

能力仍只有：

- `supported`
- `unverified`
- `unsupported`

`ProbeVerified` 是证据来源，不是第四种能力状态，不改变现有能力数据模型。

### 5.2 成功必须精确到能力

| 实际探测结果 | 可以记录的结论 |
|---|---|
| 有效电量响应 | 当前设备实例可读取电量 |
| 有效充电状态响应 | 当前设备实例可读取充电 |
| 有效连接状态响应 | 当前设备实例可读取连接 |
| 有效 DPI 响应 | 当前设备实例可读取 DPI |
| 有效回报率响应 | 当前设备实例可读取回报率配置 |
| 只有设备信息响应 | 只能记录设备信息查询成功 |

禁止因为一项能力成功就把其他能力一起升级为 `supported`。

### 5.3 失败不等于 unsupported

超时、无响应、休眠、未连接、槽位错误、连接方式不符、固件差异、接口匹配错误、解析失败，都不能单独作为 `unsupported` 的证据。除非有可靠明确否定证据，否则失败后保持 `unverified`。

### 5.4 ProbeVerified 的适用范围

`ProbeVerified` 只对当前设备实例有效，至少关联：

- 设备实例标识；
- 连接方式；
- 接口或槽位标识；
- 品牌插件；
- 协议及版本；
- 实际验证的能力；
- 探测时间；
- 探测结果。

禁止自动推广到同品牌其他设备、同型号其他设备、同 VID/PID 设备、同一接收器的其他槽位、其他连接方式或其他固件版本。

参考实现支持仍是候选证据；没有本项目真机探测结果，能力继续保持 `unverified`。证据等级继续遵循 S1/S2/S3 体系。

## 6. 设备实例绑定

### 6.1 不以 VID/PID 作为唯一持久化键

VID/PID 只能作为接口匹配线索。必须避免：

- 相同 VID/PID 的不同接收器被认作同一实例；
- 接收器身份错误继承给设备本体；
- 一个槽位的证据应用到其他槽位；
- 相同接口下不同型号被错误合并。

### 6.2 身份分层

| 层 | 内容 |
|---|---|
| 稳定身份线索 | USB Container ID、序列号、其他稳定硬件标识 |
| 接口指纹 | VID/PID、Usage Page/Usage、报告长度、Feature、接口编号等 |
| 当前访问定位 | 当前 HID Path、当前枚举接口信息 |
| 协议目标身份 | 接收器身份、槽位、协议自报身份、连接方式 |

不能假设所有设备都有稳定序列号或 Container ID。

### 6.3 持久化键与失效

建议优先使用“可用的接收器稳定身份 + 接口指纹 + 协议槽位/目标标识”。当前 HID Path 只作访问定位，不应默认作为唯一长期身份；没有可靠稳定身份时允许只建立会话级绑定。

接收器更换、槽位设备变化、固件变化、连接方式变化、接口指纹变化、重新枚举后无法匹配、协议身份冲突时，必须重新检查绑定有效性。旧证据可以保留为历史记录，但不能无条件继续授权主动查询。

## 7. 日志、诊断与 UI

每次手动探测至少记录：

- 用户选择的目标；
- 实际匹配的接口；
- 接口指纹摘要；
- 当前设备实例标识；
- 品牌插件；
- 探测计划标识及版本；
- 实际执行的只读查询；
- 发送次数、发送时间、响应时间；
- 响应与解析结果；
- 最终结论；
- 拒绝或失败原因。

原始帧按现有日志规范处理，避免无限制记录。拒绝原因至少覆盖：插件未启用、主动通信授权不满足、目标接口不存在、接口指纹不匹配、目标身份冲突、槽位无法确认、无可用探测计划、计划不满足只读要求、熔断/退避、官方客户端让位、设备断开、超过次数限制。

探测结束后至少显示：目标、品牌和协议、实际探测类型、成功/失败、成功确认的能力、未确认的能力、失败原因、证据适用范围。必须明确告诉用户：成功只证明当前实例在本次连接条件下通过了对应查询验证，不代表该型号全部能力已验证。

UI 不允许手动输入 VID/PID、命令码、Report ID 或任意帧。

## 8. 实施阶段

### 阶段一：现有架构核对

只读检查设备身份、接收器/槽位、型号与协议关系、能力数据、S1/S2/S3 证据、插件开关与主动通信授权、现有门控、熔断/退避/让位、日志与诊断。输出已有能力、缺失能力、可复用部分、必须修改部分和不应新增的架构层。本阶段不改代码。

### 阶段二：参考实现证据审计

优先研究：

- 罗技：Solaar、OpenLogi、Linux hid-logitech-hidpp；接收器/槽位身份、HID++ Feature 查询、动态 Feature 发现、查询与写入区别。
- 迈从：官方 M HUB WEB、cardList、Vb、rateMap、mouseDiffConfig、getPassWord、qhw 及公开社区协议实现；0x4D 接收器身份、0x0900 设备信息、V1 会话、型号识别、连接方式差异、只读语义。

只登记协议事实、来源、版本、许可证和证据等级；不得直接复制代码，也不得把参考实现支持写成设备级 `supported`。

### 阶段三：最小探测模型设计

只定义必要模型：`TargetSelection`、`ProbePlan`、`ProbeResult`、设备实例绑定、探测证据登记。优先复用现有身份、能力、证据和插件模型。

不新增通用 `ActiveQueryPolicy`、不新增全局能力 JSON、不复制独立协议实现、不为 UI 提前设计大规模持久化结构。

### 阶段四：选择一个品牌试点

初步建议先评估迈从 0x4D，再考虑罗技。迈从重点：指定已知接收器、限定接口、使用已知 0x0900 或已审核只读查询、明确本体/接收器身份、记录当前实例证据。罗技重点：接收器身份、槽位选择、HID++ Feature 查询、设备身份消歧、多槽位证据隔离。

最终顺序以阶段一、阶段二审计为准，不因预设顺序强行选择。

### 阶段五：验证后实现 UI

先通过自动化测试验证安全边界，再设计 UI。UI 提供真实枚举接口、品牌选择、接收器/接口/槽位选择、必要的型号辅助、计划说明、一次性探测、结果和绑定清除/重新探测。UI 不允许手动输入命令或帧。

### 阶段六：逐品牌扩展

按证据与身份复杂度推进：专用 PID 单设备 → 专用接收器 → 共享 PID 多型号 → 多接口 → 多槽位接收器 → 复杂动态协议。每个品牌单独验收，不因一个试点成功就自动开放所有插件。

## 9. 验收与禁止事项

功能验收：

- 自动发现未验证设备仍不主动查询；
- 选择目标本身不发帧；
- 插件关闭、授权不满足、接口不存在/不匹配时不能探测；
- 只能执行预先登记的计划；
- 计划只含审核过的只读操作；
- 次数/超时有上限；
- 失败立即停止，不切换协议/命令/接口/槽位，不后台循环，不绕过熔断/退避/让位。

身份验收：

- 用户选择不能直接确认型号；
- 接收器身份不能直接继承为设备本体；
- 槽位身份和证据隔离；
- 不以 VID/PID 作为唯一实例键；
- 无法可靠定位时允许会话级绑定；
- 关键身份条件变化后旧证据不能无条件生效。

能力与证据验收：

- `ProbeVerified` 不是能力状态；
- 成功只影响实际验证的能力；
- 成功只对当前实例有效；
- 不自动推广到同型号；
- 失败不直接 `unsupported`；
- 参考实现不能替代本项目真机验证；
- 证据等级遵循现有规范。

日志验收：能记录目标、接口、协议、计划、发送、响应、解析、成功/失败/拒绝原因、实例和计划版本。

明确禁止：未知命令枚举、Report ID 扫描、任意字节猜测、未经审核的 fallback、失败后扩大范围、自动继承接收器能力、实例证据推广到型号、用户选择型号直接授权能力、参考实现直接转 `supported`、新增绕过现有授权的通道、为手动探测新增独立通用框架、未经审计大规模修改厂商插件。
