## 2. 逐条发现

### CR-84 · P1 · 官方后启动时没有释放已有接口

证据：`DarkrimPlugin.IsCandidate`、`DarkrimPlugin.PollDevice`；基线 `BatteryPluginBase.AttachAsync`、`ReconcileRemovals`、`StartPassiveListen`。

触发顺序：先由 VigilWatt 认领并启动被动监听，再启动官方 DARKRIM 客户端。补丁让 `IsCandidate` 返回 false，但基类只是跳过本轮认领，不会从 `_devices` 删除原设备。`ReconcileRemovals` 仅释放已从扫描结果消失的路径，官方启动不使 HID 路径消失，因此不会关闭该句柄。`PollDevice` 返回 null 也不会停止被动监听或释放中央认领。

结果：补丁只能阻止部分新认领和主动查询，原监听仍可能消费输入，与 PR 声称的“不打开句柄才是真让位”不一致。还可能保留旧在线状态，无法向用户准确表达让位。

合入前应补完整的释放、状态通知及恢复流程，并验证“VigilWatt 先启动 → 官方启动 → 官方退出”和相反启动顺序；仅测进程检测函数不足以覆盖此问题。

### CR-85 · P1 · 进程检测失败反而允许接管

证据：`OfficialAppGuard.IsRunning` 的异常分支，以及 `DarkrimOfficialGuardTests.IsRunning_TreatsProbeFailureAsNotRunning`。

`Probe()` 抛异常后，补丁将 `running` 设为 false，并缓存 5 秒。调用方据此继续认领或查询。若官方实际仍运行，则检测失败会撤掉用于避免冲突的保护；已有缓存为 true 时也会被改成 false。

“未知”不能直接作为“确认未运行”的证据。应在无法判断时暂缓接管或保持保护，并在后续检测成功后自动恢复。5 秒后仍可重查，不需要用放行来避免永久停用。

该发现证明的是保护条件在异常路径被撤掉；是否必然造成断连仍需对应真机验证，不能由静态代码推出。

### CR-86 · P2 · 真机回归用例没有独立固定帧

证据：`GameSirCodecTests.ParsesRealFrameFromPid0575`。

测试新建全零数组，再用 `GameSirCodec.ChargeStateOffset` 与 `BatteryOffset` 填充关键字节。若生产代码将偏移改错，测试会在相同错误位置写入，解析仍通过，无法防止它声称覆盖的帧布局回归。

应使用脱敏的固定抓包字节向量，关键字节位置不引用被测偏移常量；未拿到完整原帧前，应将现有用例如实称为合成样本测试。

## 3. 需要修正或遗漏的部分

- 作者的两种“官方运行 / 关闭”对照不能替代运行中切换的生命周期验证，特别是既有句柄是否释放。
- `ProbeWrites` 描述的是协议是否会写帧。补丁按进程状态动态改变它，混淆了协议事实与是否允许执行；后续修复应保持该事实不变，将让位放在生命周期及执行许可处。
- GameSir 增加 report ID 分布有排障价值，但只有 report ID 不能证明是集合选错或布局变化，还应结合帧长度、解析拒绝原因与独立样本。
- 修改默认值只影响缺失配置键或新配置；已保存的 GameSir 开关不会被默认表覆盖，发布说明应区分这两种用户。

## 4. 未能证实的部分

- GameSir PID 0575 的历史解析失败未复现，日志增强不能据此称为已修复解析故障。
- 本机未复测耳机长期使用，也未运行该 PR 的构建与测试；没有确认合入安全性。
